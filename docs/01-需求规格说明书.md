## 2. 项目背景与目标

### 2.1 背景

求职需要一份能体现**工程能力**而非**教程完成度**的项目。市面上的「商城项目」泛滥，绝大多数是跟着视频敲完的 CRUD，特征是：只有功能列表、没有取舍、没有数据、没有踩坑。

本项目的差异化定位是：**用一个真实的电商业务闭环，承载一次完整的高并发性能优化过程。**

### 2.2 目标

| 层级 | 目标 | 衡量方式 |
|---|---|---|
| 业务目标 | 跑通「浏览商品 → 加购 → 下单 → 支付 → 发货 → 收货 → 售后」全闭环 | 能现场演示全流程 |
| 技术目标 | 在秒杀场景下产出**可复现的性能优化数据** | JMeter 压测报告：优化前后 QPS / TP99 对比 |
| 求职目标 | 支撑简历 1 个项目条目 + 20 分钟技术深聊 | 模拟面试能扛住 30 个追问 |

### 2.3 成功标准（Definition of Success）

1. 项目能 `docker compose up` 一键起全栈，或至少一条命令起后端；
2. 有一个**能演示、能讲 5 分钟**的秒杀场景，且**有真实压测数字**；
3. 有 3 个以上「我踩了坑，是这么定位和解决的」故事；
4. 面试官问「为什么不用微服务 / Seata / 分库分表」，你能给出一段有说服力的回答。

## 4. 范围（Scope）

### 4.1 范围总表

| Phase | 主题 | 核心交付 | 是否必须 |
|---|---|---|---|
| **Phase 0** | 设计 | 需求 / 架构 / 数据库设计、Maven 多模块骨架、DDL 落库 | 必须 |
| **Phase 1** | 用户与商品 | 认证授权、用户中心、商品中心、系统管理 | 必须 |
| **Phase 2** | 交易闭环 | 购物车、库存、订单、支付、售后 | 必须 |
| **Phase 3** | 营销与高并发 | 优惠券、**秒杀**、压测与优化 | 必须 |
| **Phase 4** | 平台化扩展 | 多商户、店铺、结算 | 选做 |

### 4.2 明确不做（Out of Scope）

这一节比上一节更重要，面试时会被问到。

| 不做 | 理由 |
|---|---|
| 微服务拆分（Spring Cloud / Nacos / Gateway） | 单体足够承载本项目数据量；拆分收益低于运维与调试成本 |
| Seata 等分布式事务框架 | 单机单库不存在分布式事务；一致性用本地消息表解决，实现简单且更能讲清原理 |
| 分库分表（ShardingSphere） | 数据量在百万级以下，分表只会增加复杂度而没有收益 |
| 读写分离 / 多数据源 | 无真实主从环境，做了也无法验证 |
| Elasticsearch 全文检索 | 商品搜索先用 MySQL `LIKE` + 类目筛选；ES 放 Phase 4 备选 |
| 自建网关 | 单体不需要；Nginx 做反向代理与限流入口即可 |
| 移动 App / 小程序原生开发 | 前端只做 Web（后台管理 + 商城 H5），不投入移动端 |
| 真实支付通道直连 | 自建**模拟支付网关**（接口契约对标支付宝），规避商户资质与公网回调调试 |
| Kubernetes | 运维成本远超收益 |
| 推荐算法 / 大数据 | 与目标岗位无关 |

| PROD-06 | 商品图片管理 | M | 主图 + 相册，关联 SPU/SKU |

**关键业务规则**：

- **SPU/SKU 模型**：SPU 是「iPhone 15」，SKU 是「iPhone 15 / 128G / 黑色」。SKU 的价格与库存是**独立的**；SPU 只展示价格区间（`min_price` ~ `max_price`）。
- **规格属性**参与 SKU 组合，**参数属性**只用于详情页展示，不参与组合。
- 只保留**两级规格**（如「颜色 + 容量」），不做任意级组合——限制复杂度，避免界面和算法复杂化。

> **设计取舍**：购物车存 **Redis Hash** 还是 **MySQL**？
> 本项目选 **MySQL 落库 + Redis 缓存热点**。理由：购物车需要长期保存、需要和订单关联、数据量不大；纯 Redis 方案在 Redis 故障时丢数据。面试时能讲这个取舍比用 Redis 更值钱。

### 5.6 `inventory` 库存中心（Phase 2）

| 编号 | 功能 | 优先级 | 说明 |
|---|---|---|---|
| INV-01 | 库存查询 | M | |
| INV-02 | 下单**锁定库存** | M | `stock` 减、`locked_stock` 加 |
| INV-03 | 支付后**扣减锁定** | M | `locked_stock` 减 |
| INV-04 | 超时/取消**回滚库存** | M | **必须幂等** |
| INV-05 | 库存流水记录 | M | `wms_stock_log`，唯一索引防重复回滚 |
| INV-06 | 库存预警 | C | |

**关键业务规则**：

- 库存扣减**永远不允许出现负库存**，SQL 层用 `where stock >= #{num}` 兜底；
- 所有库存变动必须写 `wms_stock_log`，且以 `(biz_type, biz_no)` 建唯一索引实现幂等。
  其中 `biz_no` 必须是**业务单据号**（`order_no` / `payment_no` / `order_no + "_CANCEL"` / `refund_no`），
  **绝不能包含时间戳或随机数**——否则重试时算出来的值不同，幂等就失效了。详见 `04-数据库设计.md` §3.4.3；
- 管理端手工改库存也必须走 Service 层写流水，不允许直接 UPDATE。

### 5.7 `trade` 交易中心（Phase 2）

| 编号 | 功能 | 优先级 | 说明 |
|---|---|---|---|
| TRADE-01 | 确认订单页 | M | 地址 + 商品清单 + 金额明细 |
| TRADE-02 | **提交订单** | M | 核心链路，见下 |
| TRADE-03 | 订单列表 / 详情 | M | 按状态筛选 |
| TRADE-04 | 取消订单 | M | 仅「待付款」可取消 |
| TRADE-05 | **超时自动关单** | M | MQ 延迟消息，30 分钟 |
| TRADE-06 | 确认收货 | M | |
| TRADE-07 | 订单状态机 | M | 非法流转必须被拒绝 |
| TRADE-08 | 管理端订单查询/发货 | M | |
| TRADE-09 | 订单操作流水 | S | `oms_order_operate_history` |

**下单主链路（TRADE-02）业务规则**：

1. 校验收货地址归属当前用户；
2. 校验商品状态（上架）、SKU 有效性；
3. **校验库存充足并锁定库存**；
4. 计算价格：`商品总额 = Σ(SKU 单价 × 数量)`，`应付 = 商品总额 + 运费 - 优惠`；
5. 生成订单（状态 `待付款`），**金额在生成时快照，不随商品后续改价变化**；
6. 清理已下单的购物车项；
7. 发送延迟消息（30 分钟后检查是否仍待付款）。

**订单状态机**：

```
待付款(0) ──支付成功──> 待发货(1) ──发货──> 待收货(2) ──确认收货──> 已完成(3)
    │                                              │
    └──取消/超时──> 已取消(4)                       └──申请售后──> 售后中(5) ──> 已退款(6)
```

**防乱改规则**：所有状态变更必须走 `update oms_order set status = #{new} where id = #{id} and status = #{expected}`，受影响行数为 0 即说明状态已被改变，抛业务异常。**这是状态机的落地方式，也是高频面试题。**

### 5.8 `payment` 支付中心（Phase 2）

| 编号 | 功能 | 优先级 | 说明 |
|---|---|---|---|
| PAY-01 | 创建支付单 | M | 一次订单可能多次发起支付，`pay_payment` 允许多条 |
| PAY-02 | 发起模拟支付 | M | 自建模拟网关返回支付页链接 / 二维码 |
| PAY-03 | **支付回调处理** | M | 验签 → 幂等 → 更新支付单 → 更新订单 |
| PAY-04 | 支付结果主动查询 | M | 回调丢失时的补偿 |
| PAY-05 | 退款 | M | 全额退款；部分退款 C |

**幂等要求（硬性）**：

- 回调必须**验签**，验签失败直接拒绝；
- 同一 `trade_no` 重复回调**只能生效一次**——用 `pay_payment` 的状态条件更新 + `pay_notify_log` 唯一索引双重兜底；
- 回调处理成功后必须返回渠道要求的成功响应，否则渠道会一直重推。

| 编号 | 功能 | 优先级 | 说明 |
|---|---|---|---|

| PROMO-05 | **秒杀活动管理** | M | 活动时间、秒杀价、秒杀库存 |
| PROMO-06 | **秒杀下单** | M | 全项目最大亮点，见下 |
| PROMO-07 | 秒杀结果查询 | M | 异步下单，前端轮询结果 |
| PROMO-08 | 秒杀活动预热 | M | 定时任务把库存加载到 Redis |
| PROMO-09 | 拼团 / 砍价 | C | 不做 |

**秒杀链路业务规则（PROMO-06，核心）**：

必须按顺序通过以下关卡，**任何一层拦下都直接返回失败**：

1. **活动有效性校验**（是否开始/结束，读本地缓存不查库）；
2. **限流**：接口级令牌桶（Redis + Lua），超过阈值直接拒绝；
3. **用户级去重**：`SETNX shopping:seckill:user:{activityId}:{userId}`，防同一用户重复提交；
4. **Redis Lua 原子预扣库存**：`stock > 0` 才扣减，扣减与判断在同一脚本内保证原子性；
5. **发送 MQ 消息**（带唯一 `seckillRecordId`）——**立即返回「排队中」**，不阻塞用户；
6. **消费者落库**：插入 `sms_seckill_record`（唯一索引兜底去重）+ 条件更新 `wms_stock`；
7. **创建订单**，推送结果，前端轮询拿到订单号。

**必须保证**：
- 绝不超卖（Redis 预扣 + DB 条件更新 + 唯一索引三层）；
- 不重复下单（用户去重 + 唯一索引幂等）；
- Redis 与 DB 最终一致（定时对账任务 + 失败回滚 Redis 库存）；
- 单机压测下，相对「直接查库下单」有**可量化的 QPS 提升**。

## 6. 非功能性需求

### 6.1 性能

| 指标 | 目标 | 测量方式 |
|---|---|---|
| 商品详情接口 QPS（单机） | ≥ 2000（走缓存） | JMeter |
| 商品详情 TP99 | ≤ 50 ms | JMeter |
| 普通下单接口 TP99 | ≤ 500 ms | JMeter |
| **秒杀接口 QPS（单机）** | ≥ 1000 | JMeter，需产出优化前后对比 |
| 秒杀 TP99 | ≤ 200 ms（异步返回） | JMeter |
| 秒杀不超卖 | **100% 正确** | 压测后核对库存与订单数 |
| 慢 SQL | 无 > 200ms 的业务查询 | 慢查询日志 |

> **重要**：这里的数字是**目标**。真实数字必须自己压测得到，不能照抄。文档 `06` 会告诉你每个数字怎么测。

### 6.2 安全

| 项 | 要求 |
|---|---|
| 密码存储 | BCrypt（不可逆 + 加盐），禁止 MD5 |
| 认证 | JWT 双 Token；access 短效、refresh 可吊销 |
| 授权 | 接口级 RBAC，默认拒绝 |
| 传输 | HTTPS（部署时）；敏感字段脱敏（手机号 `138****8888`） |
| 注入 | 全部走 MyBatis 参数绑定，禁止 `${}` 拼接 |
| XSS | 富文本输入过滤；前端输出转义 |
| 越权 | **必须做**：查询/修改订单、地址时校验归属（水平越权是高频考点） |
| 防刷 | 秒杀接口限流 + 用户去重 + 验证码 |
| 敏感信息 | 数据库密码、AppSecret 走环境变量，**不进 Git** |

### 6.3 可用性与容错

| 项 | 要求 |
|---|---|
| Redis 故障 | 缓存层降级直查 DB（加熔断保护），不能导致服务不可用 |
| MQ 故障 | 消息落本地消息表，重试投递 |
| 支付回调丢失 | 定时主动查询补偿 |
| 重复请求 | 关键写接口全部幂等 |

### 6.4 可维护性

- 分层清晰：Controller 不写业务，Service 不碰 `HttpServletRequest`；
- 统一异常体系与统一响应体；
- 关键业务逻辑有单元测试（覆盖率目标 ≥ 40%，不追求数字，追求关键路径覆盖）；
- 接口文档用 Knife4j 自动生成，**不允许手写与代码脱节的文档**。

### 6.5 兼容性

- 浏览器：Chrome / Edge 最新版（不做 IE 兼容）；
- 分辨率：管理端 ≥ 1280px，商城前台做移动端适配（H5）。

## 7. 关键业务规则汇总

面试常问，集中列出：

1. **金额**：全部以 `bigint` 存**分**，禁止 `double`；计算在 Service 层用 `long`/`BigDecimal`；前端展示时除以 100。
2. **价格快照**：订单一旦生成，`oms_order_item` 里的单价与商品名**永久固化**，商品后来改价改名不影响历史订单。
3. **库存**：只允许「锁定 → 扣减（支付后）」或「锁定 → 回滚（取消/超时）」两条路径，且都幂等。
4. **订单状态**：只能按状态机流转，且所有变更带 `where status = 期望值`。
5. **优惠券**：领券限量（Redis 预扣），下单锁券，取消订单回退券，券与订单一一绑定。
6. **下单与支付的解耦**：订单创建成功 ≠ 支付成功；支付回调只更新支付单和订单状态，**不重复创建订单**。
7. **超时关单**：延迟消息触发，触发时先校验订单是否仍为「待付款」，是才关。
8. **秒杀与普通下单分离**：秒杀走独立链路（`promotion`），不污染普通下单代码；两者最终都调用同一套库存与订单服务。

| Q7 | 部署上线 | 先本地演示，有余力再上云 | 不阻塞主线 |

### 9.1 前端范围的分期结论

| 优先级 | 内容 | 说明 |
|---|---|---|
| **P0** | 管理后台（Vue3 + Element Plus） | 演示刚需：能建商品、看订单、看库存 |
| **P0** | 商城前台（Vue3 + Vant）**4 个页面**：商品列表、商品详情、购物车、下单结算 | 这 4 页足以演示完整购物动线 |

### 9.2 关于「尽快」的排期结论

**可以压缩到 6 周**，但前提是：① 商城前台只做 P0 四页；② 砍掉 Phase 4；③ 每周投入 20 小时以上。

详细路线见 `00-蓝图与术语表.md` §11.4 与 `05-开发里程碑与排期.md` **§0.1 六周压缩版**。

**无论怎么压缩，以下三件事不能砍**：
1. **秒杀模块 + 真实压测数据**（唯一差异化亮点）；
2. **端到端可演示**（面试官要看能跑的东西）；
3. **文档与面试稿**（最后一周）。

### 9.3 一个必须澄清的概念：MQ ≠ 微服务

需求确认时暴露出一个混淆：**「用了 RocketMQ」不等于「用了微服务」**。

- **消息队列是中间件**，解决异步、削峰、最终一致；**微服务是架构风格**，解决独立部署与扩缩容。
- 本项目是**单体应用**，用 MQ 是「一个进程往中间件发消息」，与「拆成多个服务互相调用」是两件事。
- **单体 + MQ 恰恰是最经典、最容易讲清的秒杀方案。**

完整论证与面试话术见 `00-蓝图与术语表.md` §11.1。
