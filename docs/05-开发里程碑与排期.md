# 05 · 开发里程碑与排期（10 周执行手册）

> 前置阅读：`docs/00-蓝图与术语表.md`。本文的模块名、表名、技术版本、Phase 划分全部沿用 00 号文档，不自创。
> 本文面向**你本人**：每周 12-15 小时（课余 / 实习之余），总周期 10 周。
> 本文不是甘特图，是**可以直接照着打勾的 checklist**。每一条 `- [ ]` 都对应一次能独立提交的 commit。

## 0. 三条执行铁律（先看这个，再看排期）

1. **每周必须留下可演示的东西。** 哪怕只做了一个接口，也要有 Postman 截图 / curl 输出 / 日志截图。面试是「演示 + 讲」，不是「我说我写完了」。
2. **文档和笔记与代码同步产出，不许攒到最后。** 每周的「要写进笔记/简历的亮点」是硬性交付物，不是建议。
3. **超时了就砍功能，不砍质量。** 每周都给了「砍什么」的备选方案，砍的时候按顺序砍，别自己发挥。

关于时间：**12-15 小时是一个很紧的预算**。下面所有估算都按「你已经会 Spring Boot 基础、但没写过完整电商」这个水平给，宁可保守。如果你某周发现自己只用了估算的一半时间，说明你状态好，把省下的时间投给秒杀和文档；如果超了 30% 以上，立刻按「风险与备选方案」执行降级，不要硬扛。

### 0.1 想「尽快」完成？先看 6 周压缩版（入口）

**读这张表的三个提醒**

1. 6 周版**不砍核心内容**（秒杀、交易闭环、文档与面试稿全在），靠的是把 10 周的内容合并进更少的周次 + **提高每周投入**（20h+）。11~15h/周 的节奏下，6 周是排不出来的。
2. 6 周版的 W3 合并了原 W5，因此**管理后台 + 商城前台（Vant 4 页）两套前端都压进 W3**（见 §2 的 W5 章节与 00 号文档 §11.2）。

- **砍什么**：先砍售后模块（`oms_aftersale` 只留表和提交接口，不做审核流），再砍退款单（`pay_refund` 只记录不调真实退款）。**绝不允许砍**：回调幂等 + 超时关单——这是简历上的核心亮点。

3. Redis 中 `seckill:stock:*` 的值在活动结束后为 0，与实际成功数一致。
4. 秒杀接口在没有 Redis 的情况下（手动停 Redis）返回「系统繁忙」而不是 500 或超卖，**截图**。

**本周要写进笔记/简历的亮点**

- 「秒杀三层防超卖：Redis Lua 原子预扣（挡 99% 流量）→ MQ 削峰异步落单（把瞬时写压摊平）→ DB 条件更新 + `sms_seckill_record` 唯一索引兜底，任何一层单独失效都不会超卖（ADR-6、ADR-10）」。
- 「库存预热 + Lua 脚本把『校验库存、校验重复、扣减、记录用户』四步合成一个原子操作，避免 `GET`+`DECR` 的竞态」。

**风险与备选方案**

- **风险**：Lua 脚本调试困难（Redis 报错信息不友好）。**应对**：先在本地用 `redis-cli --eval` 单独跑通脚本，再放进 Java；脚本里每一步加注释，用 `redis.call` 返回值判断，不要写复杂逻辑。
- **风险**：MQ 消息堆积 / 消费失败导致库存扣了单没落。**应对**：消费端做幂等 + 失败重试 + 最终对账（用 `sms_seckill_record` 与 `oms_order` 对比）。面试时把「对账任务」当成设计的一部分讲出来，这是加分项。
- **风险**：本周时间不够，秒杀做不完。**备选（按顺序降级）**：
  1. 砍掉优惠券模块，全部时间给秒杀（优惠券挪到 W9 或不做）。

  3. 最差情况：秒杀只保留 Lua 预扣 + 库存校验，落单复用普通下单链路。
- **绝不允许砍**：不超卖的正确性验证 + 压测数据。没有数据的秒杀模块在面试里等于没做。

### W9 · Phase 3 — JMeter 压测 + 性能优化 + 缓存三大问题治理 + 链路追踪

- [ ] 采集**优化后**数据，写 `docs/07-性能压测报告.md`：优化项、前后对比表、瓶颈分析、下一步优化方向（2.0h）

**涉及技术点**：JMeter 5.x、Redis 7.x（缓存三问题）、Redisson 3.x（锁重建缓存）、MyBatis-Plus 慢 SQL、`common.trace` MDC、Logback 日志格式、MySQL `EXPLAIN` 与索引。

2. 秒杀接口 QPS 有可解释的提升（如 300 → 1200），并能一句话说清提升来自哪里。

4. 用一个不存在的商品 ID 打 100 次，数据库查询日志只有 1 次（空值缓存生效），**截图**。
5. 热点商品缓存过期瞬间 50 并发，只有 1 个线程查库（分布式锁生效）。
6. 一次秒杀请求的日志中，Controller / Service / MQ 生产 / MQ 消费四条日志的 traceId 完全一致，**截图**。

**本周要写进笔记/简历的亮点**

- 「秒杀接口 QPS 从 X 提升到 Y，TP99 从 A ms 降到 B ms；优化手段为 Redis 缓存预热 + Lua `EVALSHA` 复用 + 连接池参数调优 + 索引补齐」。
- 「缓存三大问题逐项治理：穿透用空值缓存、击穿用分布式锁重建、雪崩用随机 TTL，均有对应测试用例」。
- 「traceId 通过 MDC + MQ 消息头跨进程传递，一次秒杀请求的四段日志可完整串联，问题定位时间从分钟级降到秒级」。

**风险与备选方案**

- **风险（高）**：压测数据不好看，优化陷入死胡同。**应对**：
  1. **先设一个可达成的目标**：秒杀 QPS 上到 1000+ 就算成功，不要和互联网大厂比。
  2. 数据难看时**先定位再优化**：用 `jstack` 看线程卡在哪、用 `EXPLAIN` 看 SQL 走没走索引、看 Redis 的 `SLOWLOG`。不要盲目加缓存。
  3. **压测机和你本机是同一台机器**时，压测工具本身会抢资源——数据失真。**在报告里明确写出这个局限**，这本身就是加分（说明你懂压测的基本要求）。
  4. 实在优化不动，就把「优化前后对比 + 瓶颈分析 + 如果给我更多时间我会怎么做」写成报告。**有数据但没优化成功**比**没数据**好得多。
- **风险**：本周任务太满。**备选**：砍掉 Caffeine 本地缓存、砍掉布隆过滤器（用空值缓存替代即可）。**绝不允许砍**：压测数据 + 缓存击穿/穿透至少一项的验证 + traceId 串联。

## 6. 降级方案

**降级的总原则**：砍模块，不砍链路。宁可 5 个模块端到端跑通，不要 11 个模块各自半成品。面试官要的是「你能把一件事从头到尾讲清楚」，不是「你列了多少模块」。

### 6.1 如果只剩 5 周（压缩版 MVP）

**总周期**：5 周 × 12-15h = 60-75h。

| 周次 | 内容 | 保留的模块 |
|---|---|---|
| **W1'** | Phase 0 压缩到 1 天（环境 + 骨架 + DDL 只建必需表），剩下 4 天做认证 + RBAC（Phase 1 核心） | `auth`、`system`（只做用户/角色/菜单） |
| **W2'** | 商品中心：类目 + 品牌 + **SPU/SKU 必须做**（多规格降级为「单规格 + 可选规格」，见下） | `product` |
| **W3'** | 购物车 + 库存 + 下单主链路 + 订单查询（**不看支付，下单即结束**） | `cart`、`inventory`、`trade` |
| **W4'** | 秒杀模块（**只做 Lua 预扣 + 同步落单**，不做 MQ 削峰）+ 一次小规模压测（200 并发） | `promotion` |
| **W5'** | Docker Compose（只容器化 MySQL + Redis）+ 文档 + 简历 + 面试稿 + 录屏 | — |

**保留**

- ✅ 认证 + RBAC（面试必问「权限怎么做」）
- ✅ 商品 SPU/SKU（电商项目的骨架，没有它讲不下去）
- ✅ 库存条件更新 + 库存流水（防超卖的基础）
- ✅ 下单主链路 + 订单状态机（**核心可演示链路**）
- ✅ 秒杀 Lua 预扣 + **不超卖验证数据**（唯一的高并发亮点，必须保住）
- ✅ 一次压测数据（哪怕只有一个接口的 QPS）

**砍掉**

- ❌ 模拟支付网关（订单止于「待支付」，在面试稿里说明「支付模块设计已完成，见 `notes/design/支付.md`」）
- ❌ RocketMQ 全套（超时关单用 `@Scheduled` 扫表替代，**但必须在笔记里写明为什么真实场景该用延迟消息**——这反而是一个好的对比话题）
- ❌ 售后模块 `aftersale`
- ❌ 优惠券 `sms_coupon`（秒杀优先）
- ❌ 管理后台前端（**只在「只剩 5 周」这个应急版里**全部用 Knife4j 演示；主线排期里它是 P0 必须做，商城前台 4 页同理）
- ❌ 缓存三大问题的完整治理（只做缓存穿透 + 空值缓存一项）
- ❌ 多规格 SKU 复杂场景：降级为「单规格必做 + 规格值只做展示」，SKU 与 SPU 一对一

**5 周版的关键取舍话术**（面试时用）

> 「我用 5 周做了核心交易链路和秒杀，支付和 MQ 我评估过时间后决定不做，但我把设计方案写在了文档里。如果要补，我会先补支付回调幂等，因为它和秒杀的防超卖是同一类问题——都是『同一请求重复到达如何保证结果一致』。」

### 6.2 如果只剩 3 周（最小可演示版本）

**总周期**：3 周 × 12-15h = 36-45h。**目标只有一个：一条能演示、能讲清、有数据的链路。**

| 周次 | 内容 |
|---|---|
| **W1''** | 环境 + 骨架（1 天内完成）+ 认证（登录 + JWT 单 Token 即可，RBAC 降级为「写死角色判断」）+ 商品（**类目 + SPU + SKU，只做单规格，只做新增和列表**） |
| **W2''** | 库存（条件更新 + 流水）+ 下单主链路（下单 + 订单列表，**状态机降级为状态枚举 + 一个校验方法**）+ 秒杀（Redis Lua 预扣 + 同步落单，不做 MQ） |
| **W3''** | 压测（**只压秒杀一个接口**，200 并发）+ Docker Compose（**只容器化 MySQL + Redis**）+ 文档 + 简历 + 面试稿 + 录屏 |

**保留的模块（就这 5 个）**

1. `auth` — 登录 + JWT
2. `product` — 类目 + SPU + SKU（单规格）
3. `inventory` — 库存条件更新 + `wms_stock_log`
4. `trade` — 下单 + 订单查询
5. `promotion` — 秒杀 Lua 预扣

**砍掉的一切**

- ❌ RBAC 完整模型（`sys_role_menu` 不用，用注解写死 `@PreAuthorize("hasRole('ADMIN')")`）
- ❌ 购物车（**下单接口直接传 skuId + 数量**，跳过 `oms_cart_item`）
- ❌ 支付、售后、超时关单、MQ、优惠券、前端、缓存治理、链路追踪
- ❌ 所有管理端 CRUD 中「修改」和「删除」（**只做新增 + 分页查询**）
- ❌ Docker Compose 里的 RocketMQ 和 Nginx

**3 周版必须做到的三件事**（做不到就等于项目没做）

1. **秒杀不超卖有数据**：200 并发抢 100 件，`sms_seckill_record` 恰好 100 条，有 SQL 截图。
2. **有一个可演示的端到端链路**：登录 → 查商品 → 下单 → 秒杀 → 查订单，5 分钟能演完。
3. **有一份能讲 5 分钟的文档**：架构图 + 数据库 ER 图 + 秒杀防超卖的三层设计 + 压测数据 + 3 篇踩坑记录。

**3 周版面试怎么讲**（坦诚 + 有判断力）

> 「时间只有 3 周，我做了取舍：优先保证交易主链路和秒杀这个高并发场景，因为它们是这个项目唯一不能被替代的部分。支付、MQ、多商户我都设计了但没实现，文档在仓库里。我知道『没做』和『做错』的区别，所以我宁可少做也不做半成品。」

## 7. Git 工作流与提交规范

### 7.1 分支策略

| 分支 | 用途 | 规则 |
|---|---|---|
| `main` | 可运行、可演示的稳定版本 | 只接受 `dev` 的合并；每次合并打 tag（`v0.1-phase1`、`v0.2-phase2`…） |
| `dev` | 日常开发主线 | 每周开始时从 `main` 同步；每周结束合并回 `main` 并打 tag |
| `feature/xxx` | 单个功能 | 从 `dev` 切出，完成后合并回 `dev` 并删除 |
| `fix/xxx` | 修 bug | 同上 |

**分支命名示例**：`feature/auth-jwt`、`feature/product-spu-sku`、`feature/order-state-machine`、`feature/seckill-lua`、`fix/stock-concurrent-deduct`。

**每周节奏（和排期对齐）**

```
周一：git checkout dev && git merge main        # 同步
周一：git checkout -b feature/xxx-yyy          # 开本周第一个功能分支
周三：git checkout dev && git merge feature/xxx-yyy   # 功能完成就合
周日：git checkout main && git merge dev && git tag v0.1-phase1 && git push --tags
```

**为什么这套分支策略对求职有用**：面试官打开你的仓库，看到 `main` 上有一串 tag（`v0.1` → `v0.5`），能一眼看出**你真的按阶段交付了 5 个里程碑**，而不是最后一次性 push 上来。这是「工程习惯」的直接证据。

### 7.2 Commit Message 规范（Conventional Commits）

格式：`<type>(<scope>): <subject>`

| type | 用于 |
|---|---|
| `feat` | 新功能 |
| `fix` | 修 bug |
| `docs` | 只改文档 |
| `refactor` | 重构（不改行为） |
| `test` | 加测试 |
| `chore` | 构建/依赖/配置 |
| `perf` | 性能优化 |
| `style` | 格式（不影响逻辑） |

**scope 用 00 号文档的模块名**：`auth`、`user`、`product`、`cart`、`inventory`、`trade`、`payment`、`aftersale`、`promotion`、`system`、`merchant`、`common`、`web`、`build`、`docs`。

**写 subject 的三个要求**：用祈使句（「实现」不是「实现了」）、不超过 50 字、**说清改了什么而不是「更新代码」**。

### 7.3 让 git 提交记录本身成为加分项

面试官真的会看 `git log`。他们看三件事：

1. **提交粒度**：一条 commit 是不是只干一件事。如果你有一条 commit 叫「完成商品模块」改了 47 个文件，说明你没有版本管理意识。
2. **提交节奏**：`git log --date=short --pretty=format:'%ad %s'` 能看出你是不是每天/每几天都在推进。10 周有 150+ 条提交，和 10 周只有 12 条提交，给人的印象完全不同。
3. **提交信息质量**：能不能从 message 看出这个人知道自己在干什么。**`feat: 更新代码` 是减分项，`fix(inventory): 修复并发扣减下 stock 为负的问题，改用条件更新影响行数判定` 是加分项。**

**加分技巧**

- 一条 commit 里如果**包含了关键取舍**，把它写进 body（不只是 subject）：

```
fix(inventory): 库存扣减改用条件更新防超卖

原实现先 SELECT 再 UPDATE，在 10 线程并发下单时出现 stock = -1。
改为 UPDATE ... WHERE stock - locked_stock >= #{n} 并按影响行数判定，
失败直接抛 BizException。附并发测试：10 线程各扣 1，最终库存恰为 9。

Refs: notes/design/库存并发问题.md
```

- **`Refs:` 指向笔记**。面试官点开 commit 能看到你的踩坑记录，这比任何自夸都有说服力。
- **每周打 tag**，tag 名带 Phase：`v0.1-phase0`、`v0.2-phase1`。
- 保留 `.gitignore` 干净（不要提交 `target/`、`.idea/`、`application-local.yml` 里的密码）。

### 7.4 至少 15 条可直接复制的 commit message

**W1 · Phase 0**

```
chore(build): 初始化 Maven 多模块骨架并锁定 Java 17 与 UTF-8 编码
docs(docs): 补充需求规格说明，明确 C 端与管理端用例及不做范围
docs(docs): 完成数据库设计文档，金额字段统一 bigint 存分
docs(docs): 完成系统架构设计文档与 ADR-1~ADR-10 决策记录

```

**W2 · 认证与系统管理**

```

feat(auth): 新增 accessToken 刷新接口，refreshToken 一次性轮换
feat(auth): 基于 sys_menu.perms 实现接口级 RBAC 权限校验
feat(system): 新增用户/角色/菜单三个模块的 CRUD 与分页查询

```

**W3 · 用户与商品基础**


**`docs/` 和 `notes/` 的分工**（必须分清）

- `docs/` 是**给别人的**：结构完整、结论明确、没有废话、可以当作交付物。面试官会看这个。
- `notes/` 是**给你自己的**：可以有推演过程、走过的弯路、未经验证的猜想、甚至情绪。**面试时的素材几乎全部来自这里**。

**为什么 `notes/pitfalls/` 是最重要的目录**：面试官不会问你「商品模块有什么功能」，会问「做这个项目你遇到最难的问题是什么，怎么解决的」。答案只可能在踩坑记录里。第 8.3 节给了写法。

### 8.3 踩坑记录的写法（STAR 结构）

**核心观点：面试讲的是踩坑，不是功能列表。**

「我实现了商品模块的增删改查」——面试官听了一百遍，没有任何区分度。
「我的库存扣减在并发下出现了 -1，我排查了 3 小时，最后发现是先查后改的竞态，改成条件更新 + 影响行数判定后，10 线程并发测试结果恰为 9」——这条能讲 5 分钟，而且能引出乐观锁、`UPDATE` 原子性、事务隔离级别、压测方法等一串追问，**面试节奏就由你掌握了**。

**模板（每个坑一个文件，放 `notes/pitfalls/`）**

```markdown
# {编号} · {一句话标题，含现象}

- **日期**：{日期}
- **关联模块**：{auth/user/product/cart/inventory/trade/payment/aftersale/promotion/system/common}
- **关联 commit**：{hash}
- **耗时**：{n} 小时

## S · 场景（Situation）

{当时在做什么，上下文是什么。要具体到能复现的程度：什么接口、什么并发量、什么数据。}

## T · 任务（Task）

{我原本想达成什么。一句话。}

## A · 行动（Action）

{我做了什么。这里要有排查过程，不要只写最终答案——面试官最想听的是你怎么定位问题的。}
1. 我先看日志，发现…
2. 用 {工具} 验证了猜想…
3. 排除了 {错误猜想}，因为…
4. 最后定位到…

## R · 结果（Result）

{最终怎么解决的，有数据。}

- 修复方式：
- 验证方式：{如「10 线程各扣 1，最终库存恰为 9」}
- 数据对比：{优化前 vs 优化后}

## 面试延伸（这个坑能引出哪些追问）

- {追问1}：
- {追问2}：
- {追问3}：
- 我目前还没完全搞懂的：
```

**「面试延伸」这一节是关键**。它把一次踩坑变成了一次**主动出题**——你先把追问方向列出来，等于把面试官引到你准备好的战场上。

### 9.3 三条使用建议

1. **每日模板的「编码前先想清楚」三问不要跳过**。3 分钟能省掉 30 分钟返工——想清楚涉及哪几张表，就不会写到一半发现要改 DDL。
2. **每周看板周一早上就复制出来**，不要等周日补。看板的价值在于随时能看到「还剩多少」，而不是事后记录。
3. **验收标准一定要在周日逐条亲自验证**，不许凭印象打勾。你在这一步偷的懒，会在面试官问「你这个接口的返回结构是什么」的时候加倍还回来。
