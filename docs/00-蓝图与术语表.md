## 1. 项目一句话定位

**一个「单体分层 + 模块化」的 B2C 自营商城，具备秒杀高并发场景，用于应届生 Java 后端求职的全流程可演示项目。**

- 项目代号：`shopping-mall`
- Maven `groupId`：`com.shopping`
- 根包名：`com.shopping`
- 目标岗位：**Java 后端开发 — 校招 / 实习**

### 1.1 为什么不是微服务

求职目标是**校招**。校招面试官考察的是：

1. Java / JVM / 并发 基础是否扎实；
2. Spring 全家桶的使用与**原理理解**；
3. MySQL / Redis 的**真实使用经验**，而不是背八股；
4. 能不能把一件事**讲清楚**（需求 → 设计 → 取舍 → 踩坑 → 数据）。

微服务（Spring Cloud + Nacos + Gateway + Seata）在这个阶段是**减分项**：组件多、调试成本高、极易做成「分布式单体」，而且面试官一追问「为什么拆、拆的边界是什么、一致性怎么保证」，答不上来比不做还糟。

因此本项目：**单体多模块**，但在架构上**预留演进路径**（见 `03-系统架构设计.md` 的演进章节），面试时主动讲「如果要做微服务我会怎么拆」，效果远好于硬上微服务。

## 2. 范围结论：你选的三个业务模式，怎么落地

你在需求确认时选了 **B2C 自营 + 秒杀 + B2B2C 多商户**。三者的真实成本差异很大：

| 业务模式 | 新增复杂度 | 对应届生的价值 | 结论 |
|---|---|---|---|
| B2C 自营单商户 | 基准 | ★★★★★ 面试官最熟，必做 | **Phase 1-3 主线** |
| 秒杀 / 抢购 | +30% | ★★★★★ 唯一能讲出「并发/性能数据」的模块 | **Phase 3 亮点，必做** |
| B2B2C 多商户入驻 | +80% | ★★☆ 加分有限，但会挤占主线时间 | **Phase 4 扩展：证书设计到位，UI 后置** |

**落地策略（重要）**：

> **从第一行 DDL 开始，就在商品/订单/库存相关表上带 `merchant_id`（商家ID）字段并写入默认商家 `1`。**
> 这样 Phase 1-3 你做的是纯自营 B2C，代码里没有多商户的复杂度；
> 到 Phase 4 只需补 `mms_*` 三张表 + 商家后台接口 + 按 `merchant_id` 的数据隔离，
> 就能自然演进成多商户，而**不用重构核心表**。

这么做的好处：

- 简历上可以写「设计时预留多商户维度，支持从自营平滑演进到平台模式」——体现**架构预判能力**，这比真的写完多商户更打动面试官；
- 不牺牲主线质量，秒杀模块的时间保住了；
- 如果时间充裕，Phase 4 真做出来就是额外加分。

### 阶段划分（贯穿全套文档的统一口径）

| 阶段 | 名称 | 内容 | 是否必须 |
|---|---|---|---|
| **Phase 0** | 设计 | 需求、架构、数据库设计、工程骨架 | 必须 |
| **Phase 1** | 用户与商品 | 认证授权（RBAC+JWT）、用户中心、商品中心（类目/品牌/SPU/SKU/属性）、后台管理端 | 必须 |
| **Phase 2** | 交易闭环 | 购物车、库存、订单状态机、支付（**自建模拟支付网关**）、超时关单、售后退款 | 必须 |
| **Phase 3** | 营销与高并发 | 优惠券、**秒杀模块**、压测与优化、缓存/限流/防超卖 | 必须（核心亮点） |
| **Phase 4** | 平台化扩展 | 多商户入驻、店铺、结算分账、数据隔离 | 选做（加分） |

### 4.1 明确「不引入」的技术（以及为什么）

| 不引入 | 理由 |
|---|---|
| Spring Cloud / Nacos / Gateway | 单体不需要注册中心；见 §1.1 |
| Seata / 分布式事务框架 | 单机单库无分布式事务；用**本地消息表 + 最终一致**替代，更好讲 |
| Elasticsearch | 校招非必须；商品搜索先用 MySQL，Phase 4 再考虑 |
| ShardingSphere 分库分表 | 没有数据量支撑，硬上就是「为了技术而技术」 |
| Kubernetes | 运维成本远超收益 |
| 多数据源 / 读写分离 | 无真实主从环境，讲了也没数据 |

> 面试话术：**「我评估过 X，但基于当前数据量和团队规模我选择不做，因为它会带来 A/B 成本而收益是 C」** —— 这比堆技术栈高级得多。

## 6. Maven 多模块结构

```
shopping-mall/                    # 父 POM，只做依赖与版本管理
├── shopping-common/              # 通用：Result/异常/枚举/工具/注解/常量
├── shopping-model/               # 数据模型：DO(Entity) + DTO + VO + Query
├── shopping-dao/                 # 持久层：Mapper 接口 + XML + 分页配置
├── shopping-service/             # 业务层：Service 接口 + 实现
└── shopping-web/                 # 接入层：Controller(app/admin) + 启动类 + 配置
```

依赖方向（**严格单向，不得反向**）：

```
web ──> service ──> dao ──> model
                 └────────> common  (所有层都可见)
```

**为什么 `model` 单独拆**：避免 `dao` 与 `service` 循环依赖，也让 `common` 保持零业务。

### 包结构（以 `shopping-service` 为例）

```
com.shopping.service
├── auth/        # AuthService,  impl/
├── user/        # UserService,  impl/
├── product/     # ProductService, SkuService, impl/
├── inventory/   # StockService, impl/
├── cart/
├── trade/       # OrderService, impl/
├── payment/
├── promotion/   # CouponService, SeckillService, impl/
├── merchant/    # Phase 4
└── system/
```

`shopping-web` 的 Controller 按端拆分：

```
com.shopping.web
├── ShoppingApplication.java     # 启动类
├── controller
│   ├── app/       # C 端（会员侧）接口，前缀 /api/app/**
│   └── admin/     # 管理端接口，前缀 /api/admin/**
├── config/        # SecurityConfig / RedisConfig / MybatisPlusConfig / Knife4jConfig
├── interceptor/   # traceId、限流
└── handler/       # 全局异常处理
```

接口前缀约定：C 端 `/api/app/**`，管理端 `/api/admin/**`。

## 7. 关键技术决策记录（ADR 简版）

| # | 决策 | 备选 | 理由 | 面试追问点 |
|---|---|---|---|---|
| ADR-1 | 单体多模块 | 微服务 | 见 §1.1 | 「你为什么不拆微服务」 |
| ADR-2 | MyBatis-Plus | JPA / 纯 MyBatis | 国内主流、CRUD 快 | 「MP 的 `saveBatch` 底层怎么做的」「为什么不用 JPA」 |
| ADR-3 | 金额用 `bigint` 存分 | `decimal` / `double` | 避免浮点精度；`decimal` 也行但要统一 | 「为什么不用 double」「和 decimal 比呢」 |
| ADR-4 | 订单状态用**状态机** | 到处 if-else | 避免非法流转、易扩展 | 「订单状态怎么保证不被乱改」 |
| ADR-5 | RocketMQ 延迟消息做超时关单 | 定时任务轮询 | 精度高、无空扫 | 「为什么不用 `@Scheduled` 扫表」 |
| ADR-6 | 库存扣减：Redis 预扣 + DB 条件更新 | 悲观锁 / 纯乐观锁 | 三层防超卖，性能与正确性兼顾 | 「怎么防超卖」「Redis 挂了怎么办」 |
| ADR-7 | 最终一致性：本地消息表 | Seata AT | 单库无分布式事务；实现简单可讲 | 「幂等怎么做的」「消息丢了怎么办」 |
| ADR-8 | 逻辑删除 `deleted` | 物理删除 | 数据可追溯 | 「唯一索引和逻辑删除冲突怎么办」 |
| ADR-9 | 主键雪花 ID | 自增 | 分布式友好、不暴露业务量 | 「时钟回拨怎么处理」 |
| ADR-10 | 秒杀三层限流 | 只做 Redis 扣减 | 层层过滤，保护 DB | 「100 万人抢 100 件怎么扛」 |

## 8. 术语表（全套文档统一用词）

| 术语 | 含义 | 备注 |
|---|---|---|
| **SPU** | Standard Product Unit，标准商品单元 | 如「iPhone 15」 |
| **SKU** | Stock Keeping Unit，最小库存单元 | 如「iPhone 15 128G 黑色」 |
| **DO** | Data Object，与数据库表一一对应的实体 | 放 `model` 的 `entity` 包 |
| **DTO** | 入参对象 | 放 `model` 的 `dto` 包 |
| **VO** | 出参对象 | 放 `model` 的 `vo` 包 |
| **Query** | 查询条件对象 | 放 `model` 的 `query` 包 |
| **预扣** | 秒杀时先在 Redis 扣减库存 | 挡住绝大部分流量 |
| **削峰** | 用 MQ 把瞬时流量摊平 | 秒杀核心手段 |
| **超卖** | 卖出数量 > 实际库存 | 必须杜绝 |
| **幂等** | 同一请求执行多次，结果一致 | 支付回调、库存回滚的关键 |
| **最终一致** | 允许中间态不一致，最终一致 | 用本地消息表 + 重试实现 |
| **traceId** | 贯穿一次请求的链路标识 | 放 MDC，打在每条日志上 |
| **Phase 0-4** | 见 §2 阶段划分 | 不得另立口径 |

### 必须处理的三个环境坑

**坑 1 — JDK 版本不一致**
`PATH` 上的 `java`/`javac` 指向 JDK 8，而 `JAVA_HOME` 指向 JDK 17。Maven 编译走 `JAVA_HOME`（17），命令行 `javac` 走 PATH（8）——会出现「Maven 编译通过但命令行报 `class file version 61.0` 错误」这类诡异问题。

处理方式二选一：
- 把 `PATH` 中 `C:\ProgramData\Oracle\Java\javapath` 提到 `C:\jdk-17.0.12\bin` 之后（推荐）；
- 或者所有命令统一用 `mvn` 驱动，不直接调 `javac`。

**坑 2 — 系统编码 GBK**
Maven 输出显示 `platform encoding: GBK`。项目必须在父 POM 里锁定：

```xml
<properties>
```

**坑 3 — MySQL root 密码**

### 11.1 澄清：**消息队列 ≠ 微服务**

这是需求确认时暴露出的一个概念混淆，**必须澄清，因为它同时是一个高频面试考点**。

| | 消息队列（MQ） | 微服务 |
|---|---|---|
| 它是什么 | **一个中间件**，提供异步通信能力 | **一种架构风格**，把应用拆成多个独立部署的服务 |
| 解决什么问题 | 异步解耦、流量削峰、最终一致 | 独立部署、独立扩缩容、团队并行开发 |
| 单体应用能用吗 | ✅ **能，而且很常见** | ❌ 用不上，微服务的前提就是「多服务」 |
| 本项目用吗 | ✅ **用**（RocketMQ） | ❌ **不用** |

**关键认知**：

> 引入 RocketMQ **不等于**引入微服务。
> 本项目是**单体应用**，它调用 RocketMQ 只是「一个进程往一个中间件发消息」，和「拆成多个服务互相调用」是两件完全不同的事。
> 事实上，**单体 + MQ 才是最经典、最容易讲清楚的秒杀方案**：请求进来 → Redis 预扣 → 丢进 MQ → 立即返回 → 消费者在同一个应用里慢慢落库。全程只有一个应用，不需要服务发现、不需要网关、不需要分布式事务。

**面试如果被问「你用了 MQ，那算微服务吗」**，标准答法：

> 不算。MQ 是中间件，微服务是架构风格，两者维度不同。我的项目是单体应用，用 RocketMQ 是为了两件事：一是**削峰**，秒杀请求异步落库；二是**延迟消息**，做订单超时关单。这两件事在单体里做和微服务里做，代码几乎一样——区别只在微服务里消费者会独立部署。我之所以不拆微服务，是因为单人开发、单机部署的场景下拆分的收益远小于它的运维和调试成本。

### 11.3 Docker 端口冲突警告（动手前必看）

你选择用 Docker Compose 统一管理中间件。但**本机 MySQL 与 Redis 已经在跑，且已占用 3306 / 6379**：

```
TCP  0.0.0.0:3306   LISTENING   ← 本机 MySQL80 服务
TCP  0.0.0.0:6379   LISTENING   ← 本机 redis-server
```

如果 Docker Compose 里再把 MySQL 映射到 3306，会**启动失败或端口冲突**。二选一：

**方案 A（推荐，改动最小）**：本机 MySQL/Redis 继续用，Docker **只跑 RocketMQ**。

```yaml
services:
  namesrv:
    image: apache/rocketmq:5.1.4
    command: sh mqnamesrv
    ports: ["9876:9876"]
  broker:
    image: apache/rocketmq:5.1.4
    command: sh mqbroker -n namesrv:9876 -c /home/rocketmq/broker.conf
    environment: ["JAVA_OPT_EXT=-Xms512m -Xmx512m"]
    ports: ["10911:10911", "10909:10909"]
    volumes: ["./broker.conf:/home/rocketmq/broker.conf"]
```

**方案 B**：全部容器化，需要先**停掉本机服务**，并把端口错开：

```powershell
Stop-Service MySQL80
Stop-Service Redis
```

```yaml
  mysql:  { ports: ["13306:3306"] }   # 错开端口，避免和本机服务打架
  redis:  { ports: ["16379:6379"] }
```

> 面试话术：「我本地为了不破坏已有的 MySQL 服务，把容器端口错开到 13306，这样两套环境可以共存。」——这种细节能体现工程习惯。

### 11.5 工时冲突裁决 —— ✅ **已决定：选 A（六周压缩版）**

**冲突事实**：你选了「双前端」（§11.2）又希望「尽快」（§11.4）。加入商城前台后，**W5 的单周工时从约 18h 涨到约 26.5h**，而排期是按 **12-15h/周** 编制的。这个缺口是真实的，不能装作不存在。

三个选项，**必须选一个**：

| 选项 | 做法 | 代价 | 适合谁 |
|---|---|---|---|
| **✅ A（已选定）走六周压缩版** | 每周投入 **20h+**，按 `05` §0.1 执行 | 每周很累；但周期最短、范围不缩水 | 时间紧、能高强度投入 |

> **判断依据**：如果这是你唯一的求职项目，选 B（稳）。如果你还有别的项目或实习经历可以撑场面，选 A。无论如何**不要选「什么都想要」**。
