## 1. 选型原则

按优先级排序，冲突时前者胜：

| 优先级 | 原则 | 说明 |
|---|---|---|
| 1 | **匹配求职目标** | 目标是校招 Java 后端 → 选国内主流、面试官熟悉、八股覆盖密集的技术 |
| 2 | **不引入无法解释的复杂度** | 你用不上的组件，就是面试时答不上来的定时炸弹 |
| 3 | **能产出可讲的数据** | 能压测、能对比、能优化 → 秒杀 + Redis + MQ 是刚需 |
| 4 | **本地能跑起来** | 环境成本要低，不能因为装不上而卡住一周 |
| 5 | **文档与社区活跃** | 出问题能搜到答案，对应届生尤其重要 |

**反面原则**：不追求「新技术」「全家桶」「简历关键词密度」。用 Spring Boot 2.7 还是 3.2 都能拿 offer，但说不清为什么用 Nacos 会直接挂。

## 3. 逐项选型论证

### 3.1 语言与运行时：**Java 17**

| 候选 | 优势 | 劣势 |
|---|---|---|
| Java 8 | 国内老系统主流，面试八股覆盖面最广 | 已停止商业支持；无法用 Spring Boot 3；本机 `PATH` 上恰好是它，容易踩坑 |
| **Java 17（选）** | LTS，支持到 2029；Spring Boot 3 的硬性要求；record / 文本块 / switch 表达式 | 部分老教程基于 8，需要自己辨析 |
| Java 21 | 最新 LTS，虚拟线程（Loom）是热点 | 虚拟线程与 MyBatis 阻塞式驱动的配合还不成熟，容易讲不清 |

**决策**：Java 17。本机 `JAVA_HOME=C:\jdk-17.0.12` 已是它，Maven 直接可用。

**代价**：`javax.*` → `jakarta.*` 包名迁移，网上老代码直接抄会编译不过。

> **面试问答**
> Q：为什么用 Java 17 而不是 8？
> A：两个理由。一是 Spring Boot 3 的硬性要求，我需要它带来的 Jakarta EE 9+ 和 Spring 6；二是 LTS 支持周期，Java 8 的商业支持已经结束。至于 Java 21 的虚拟线程，我评估过，但我的持久层是 MyBatis 阻塞式 JDBC，虚拟线程的收益主要体现在 IO 密集的异步编排上，在我这个场景下提升有限，还会引入「虚拟线程 + synchronized 固定载体线程」这类新的排查成本，所以我选择先不引入。

---

### 3.2 应用框架：**Spring Boot 3.2.x**

| 候选 | 优势 | 劣势 |
|---|---|---|
| Spring Boot 2.7 | 教程最多、生态最成熟、Java 8 可用 | 已 EOL；`javax.*`；简历上略旧 |
| **Spring Boot 3.2（选）** | Spring 6 + Jakarta；可观测性（Micrometer Observation）内置；GraalVM 支持 | 部分第三方 starter 尚未适配 |
| 裸 Spring | 控得住一切 | 配置量爆炸，与求职目标无关 |

**决策**：Spring Boot 3.2.x。理由：与 JDK 17 天然匹配，且能在面试中自然引出「Jakarta 迁移」「自动装配原理」等话题。

**代价**：第三方 starter 需要挑支持 Boot 3 的版本（见 §5）。

> **面试问答**
> Q：Spring Boot 3 和 2 最大区别？
> A：三块。① 基线升到 Java 17 和 Jakarta EE 9，`javax.*` 全换 `jakarta.*`；② Spring 6 全面转向 AOT 和 GraalVM 原生镜像支持；③ 可观测性从 Spring Cloud Sleuth 回归到 Micrometer Observation，`@Observed` 注解 + ObservationHandler 统一了指标和链路。
> Q：自动装配原理？
> A：`@SpringBootApplication` 内含 `@EnableAutoConfiguration`，它通过 `@Import(AutoConfigurationImportSelector.class)` 读取所有 jar 包 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` 文件（Boot 2.7 之前是 `spring.factories`），拿到候选配置类，再用 `@ConditionalOnClass` / `@ConditionalOnMissingBean` 等条件注解过滤，最后注册成 Bean。

---

### 3.3 Web 层：**Spring MVC（而非 WebFlux）**

| 候选 | 优势 | 劣势 |
|---|---|---|
| **Spring MVC（选）** | 同步阻塞，模型直观；与 MyBatis/JDBC 阻塞驱动天然契合；调试简单 | 高并发下线程占用多 |
| WebFlux | 少量线程扛高并发，压测数据好看 | 全链路必须响应式，MyBatis 是阻塞的会破坏优势；调试栈极深；面试讲不透反而减分 |

**决策**：Spring MVC。

**关键理由（面试要用）**：**「响应式是传染的」**。只要链路上有一处阻塞（MyBatis 查库），整个响应式的收益就没了，除非换 R2DBC。为了压测数字引入 WebFlux + R2DBC，会牺牲秒杀之外所有模块的开发效率，得不偿失。

**那高并发怎么办**：用**架构手段**解决而不是换 Web 框架——Redis 预扣挡住绝大多数请求、MQ 削峰摊平流量、限流保护后端。**这才是本项目秒杀模块的价值所在，也是面试真正想听的。**

> **面试问答**
> Q：为什么不用 WebFlux？
> A：响应式要求全链路非阻塞，而我的持久层是 MyBatis 的阻塞式 JDBC，混用会让阻塞调用占用事件循环线程，反而更糟。我的高并发是靠在入口做 Redis 预扣和 MQ 削峰解决的，请求根本没打到 MVC 的线程池上，所以换 WebFlux 收益很低。如果真要做，正确路径是 R2DBC + 全链路响应式，那是一次重构而不是一次替换。

---

### 3.4 持久层：**MyBatis-Plus**

| 候选 | 优势 | 劣势 |
|---|---|---|
| 纯 MyBatis | SQL 完全可控；面试官最认 | CRUD 样板代码多，单表查询要写大量 XML |
| **MyBatis-Plus（选）** | 单表 CRUD 零 SQL；条件构造器；分页插件；逻辑删除开箱即用 | 容易让人只会 `QueryWrapper` 不会写 SQL；复杂查询仍要手写 |
| Spring Data JPA | 领域模型优雅、方法名派生查询 | 复杂查询别扭；国内中小厂用得少，面试话题度低 |

**决策**：MyBatis-Plus，但**强制约束用法**：

- **单表简单查询**用 MP 的 `LambdaQueryWrapper`；
- **多表关联、复杂聚合**必须**手写 XML SQL**（放 `resources/mapper/`），禁止用 `@Select` 拼长 SQL；
- 禁止在 Controller 里出现 `QueryWrapper`；
- 分页一律用 MP 的 `PaginationInnerInterceptor`，禁止手写 `limit`。

**代价**：若使用 MP 3.5.9 及以上版本，分页插件所需的 JSqlParser 依赖被拆成独立坐标，需额外引入 `mybatis-plus-jsqlparser`（本项目父 POM 锁定 3.5.7，暂不需要；升级时注意，见 §5 坑 2）。

> **面试问答**
> Q：MyBatis-Plus 的 `saveBatch` 底层怎么实现的？
> A：它拿到 `SqlSessionFactory` 后开启批处理模式（`ExecutorType.BATCH`），把多条 insert 攒在同一个 `SqlSession` 里，默认每 1000 条 `flushStatements()` 一次，最后统一提交。所以它**不是**拼成一条 `insert into ... values (...),(...)` 的多值插入，而是 JDBC 的 `addBatch/executeBatch`。要更快应该手写多值 insert 并控制单批大小。
> Q：MyBatis 的 `#{}` 和 `${}` 区别？
> A：`#{}` 走 `PreparedStatement` 的参数占位符，能防 SQL 注入；`${}` 是字符串直接拼接，只用在动态表名、动态排序字段这类无法参数化的地方，且必须做白名单校验。我项目里全用 `#{}`，排序字段做了枚举白名单。

### 3.5 数据库：**MySQL 8.0**

| 候选 | 优势 | 劣势 |
|---|---|---|
| **MySQL 8.0（选）** | 国内绝对主流；面试八股（B+ 树、MVCC、间隙锁）全部围绕它；本机已装 | 复杂查询与分析能力弱于 PG |
| PostgreSQL | 功能更强、JSON 支持好 | 国内中小厂占有率低；面试官可能不熟，白讲了 |
| Oracle | 企业级 | 授权成本，求职场景无意义 |

**决策**：MySQL 8.0。

**关键配置**（本地开发）：

```ini
[mysqld]
character-set-server = utf8mb4
collation-server     = utf8mb4_0900_ai_ci
default-time-zone    = '+08:00'
slow_query_log       = 1
long_query_time      = 0.2
log_queries_not_using_indexes = 0
```

`long_query_time = 0.2` 是为了配合 §6.1 的「无 > 200ms 业务查询」目标，让慢 SQL 主动暴露出来。

> **面试问答**
> Q：为什么 InnoDB 用 B+ 树而不是 B 树 / 哈希 / 跳表？
> A：① 相比 B 树，B+ 树非叶子节点只存键，同样大小的页能放更多键 → 树更矮 → 磁盘 IO 更少；且数据全在叶子节点，查询性能稳定。② 相比哈希，哈希只支持等值查询，不支持范围查询和排序，而业务里 `where create_time between` 这类范围查询极多。③ 相比跳表（Redis 用的），跳表是内存结构，无法利用磁盘预读的局部性原理。④ B+ 树叶子节点用双向链表串起来，天然支持范围扫描。

### 3.6 连接池：**HikariCP**

| 候选 | 优势 | 劣势 |
|---|---|---|
| **HikariCP（选）** | Spring Boot 默认；字节码精简、性能最好；配置项少不易配错 | 监控面板弱于 Druid |
| Druid | 自带监控页、SQL 防火墙、慢 SQL 统计；国内常见 | 代码量大；部分高级功能在 Boot 3 下适配滞后 |

**决策**：HikariCP。监控改用 **`p6spy` 或 MySQL 慢查询日志** 解决，更符合「用数据库自己的能力」的思路。

**关键配置**（必须显式设置，Boot 默认值偏小）：

```yaml
spring:
  datasource:
    hikari:
      minimum-idle: 10
      maximum-pool-size: 20        # 经验公式：CPU核数*2 + 磁盘数
      connection-timeout: 3000
      idle-timeout: 600000
      max-lifetime: 1800000        # 必须小于 MySQL 的 wait_timeout
      connection-test-query: SELECT 1
```

> **面试问答**
> Q：连接池大小怎么定？越大越好吗？
> A：不是。连接数超过数据库的并发处理能力后，多出来的连接只会在 DB 侧排队并持有内存，反而降低吞吐。经验公式是 `CPU核数 × 2 + 有效磁盘数`。我设 `maximum-pool-size=20`。另外 `max-lifetime` 必须小于 MySQL 的 `wait_timeout`，否则会拿到已被服务端断开的连接，报 `Communications link failure`——这是我踩过的一个坑。

### 3.7 缓存：**Redis 7 + 少量 Caffeine 本地缓存**

| 候选 | 优势 | 劣势 |
|---|---|---|
| **Redis（选）** | 数据结构丰富（String/Hash/ZSet）、支持 Lua 原子脚本、可做分布式锁、可持久化 | 网络 IO 开销；单点故障需考虑降级 |
| Caffeine 本地缓存 | 纳秒级、无网络开销 | 多实例不一致；容量受 JVM 堆限制 |
| Redis + 本地二级缓存 | 兼顾 | 一致性复杂 |

**决策**：**以 Redis 为主**，仅对**极热且容忍短暂不一致**的数据（秒杀活动配置、类目树）加一层 Caffeine。

**为什么秒杀必须用 Redis**：核心是 **Lua 脚本的原子性**。判断库存和扣减库存必须在一次网络往返里原子完成，否则会产生竞态导致超卖。这是本项目选 Redis 而非本地缓存的**决定性理由**。

**Redis key 规范**（详见 `03-系统架构设计.md`）：

```
shopping:product:detail:{spuId}                 # String, JSON, TTL 30min + 随机
shopping:seckill:stock:{activityId}:{skuId}     # String, 整数, 活动结束+1h
shopping:seckill:user:{activityId}              # Set, 用户去重, TTL 活动结束
shopping:lock:order:{orderNo}                   # Redisson 锁
```

> **面试问答**
> Q：为什么秒杀的库存扣减要用 Lua？
> A：因为「读库存 → 判断 > 0 → 减一」这三步如果不是原子的，两个并发请求可能都读到 1，都判断通过，导致超卖。用 Redis 的 `EVAL` 执行 Lua 脚本，Redis 单线程串行执行脚本，天然保证这三步原子。另一种做法是 `DECR` 后判断返回值是否 < 0，如果 < 0 再 `INCR` 补偿——也能实现，但有一次无效扣减和补偿，Lua 更干净。

### 3.8 分布式锁：**Redisson**

| 候选 | 优势 | 劣势 |
|---|---|---|
| 手写 `SETNX` + `EXPIRE` | 面试常问，能体现理解 | 容易踩坑：加锁与设过期非原子、业务超时导致锁提前释放、误删他人锁 |
| **Redisson（选）** | 看门狗自动续期；可重入；`tryLock` 支持等待；已封装 Lua 保证原子 | 引入一个较重的依赖 |

**决策**：Redisson，但**必须能讲清它解决了什么问题**（否则就是「调 API 工程师」）。

**Redisson 的关键机制**：

1. 加锁：Lua 脚本内 `hset` + `pexpire`，原子完成；
2. value 用 Hash 结构存 `线程ID → 重入次数`，实现可重入；
3. **看门狗（WatchDog）**：默认锁 30 秒，后台线程每 10 秒（`leaseTime/3`）续期一次，业务没执行完也不会提前释放；
4. 解锁：Lua 脚本校验 value 是否是当前线程，是才删，避免误删他人锁。

**注意**：只有在 `tryLock()` **不指定 `leaseTime`** 时才启用看门狗；一旦显式指定 `leaseTime`，看门狗失效，业务超时仍会提前释放锁。**这是高频追问点。**

> **面试问答**
> Q：Redisson 的看门狗机制说一下。
> A：见上。补充一点：看门狗续期依赖客户端存活，如果客户端进程被 kill -9，续期线程停了，锁最多在 30 秒后自动过期——这个降级是可接受的。另外如果是 Redis 主从架构，主节点加锁成功后宕机、锁还没同步到从节点，就会出现两个客户端同时持锁。要彻底解决得用 RedLock，但 RedLock 本身也有争议（依赖时钟、性能差），生产上更常用的是「加锁 + 业务层幂等」双重保障，而不是只依赖锁。

### 3.9 消息队列：**RocketMQ 5.x**

| 候选 | 优势 | 劣势 |
|---|---|---|
| **RocketMQ（选）** | **延迟消息**（超时关单刚需）、**事务消息**、消息可查询、Java 生态、阿里系背景 | 需要 NameServer + Broker，本地部署略重 |
| RabbitMQ | 轻量、路由灵活、社区大 | 延迟消息要靠死信队列 + TTL 插件模拟；无事务消息 |
| Kafka | 吞吐最高、生态最强 | 不支持延迟消息；偏日志/流处理场景；本地跑要 ZooKeeper/KRaft |

**决策**：RocketMQ。**决定性理由是「延迟消息」**——订单超时关单需要「30 分钟后触发一次」，RocketMQ 原生支持 18 个延迟级别，一行代码搞定；RabbitMQ 要绕一大圈；Kafka 根本不支持。

**本项目 MQ 的三个用途**：

| 用途 | 消息类型 | Topic |
|---|---|---|
| 订单超时关单 | 延迟消息（level 16 = 30min） | `order-timeout-topic` |
| 秒杀异步下单 | 普通消息（削峰） | `seckill-order-topic` |
| 本地消息表投递 | 普通消息（最终一致） | `payment-success-topic` |

**本地部署**（Docker Compose，需先启动 Docker Desktop）：

```yaml
services:
  namesrv:
    image: apache/rocketmq:5.1.4
    command: sh mqnamesrv
    ports: ["9876:9876"]
  broker:
    image: apache/rocketmq:5.1.4
    command: sh mqbroker -n namesrv:9876 -c /home/rocketmq/broker.conf
    environment:
      - JAVA_OPT_EXT=-Xms512m -Xmx512m
    ports: ["10911:10911", "10909:10909"]
    volumes: ["./broker.conf:/home/rocketmq/broker.conf"]
```

`broker.conf` 里必须设 `brokerIP1=127.0.0.1`，否则宿主机连不上 Broker——**这是本地部署最常见的坑**。

> **面试问答**
> Q：为什么不用 `@Scheduled` 扫表关单？
> A：可以，但有两个问题。① **精度**：每分钟扫一次，订单最长可能等 31 分钟才关，对用户体感不好；② **空扫成本**：绝大多数轮次扫不到数据，随着订单表增长，`where status=0 and create_time < ?` 的扫描代价越来越高。延迟消息是服务端精确触发，没有空扫。当然，延迟消息也会丢，所以我**额外加了一个兜底的定时对账任务**，扫「超过 1 小时仍是待付款」的异常订单——**双保险**。生产上不能只信任一种机制，这是我在这个项目里学到的。

### 3.10 认证授权：**Spring Security 6 + JWT**

| 候选 | 优势 | 劣势 |
|---|---|---|
| **Spring Security（选）** | 事实标准；过滤器链 / 方法级权限 / 六边形架构完善；面试必问 | 学习曲线陡，配置繁琐 |
| Sa-Token | 中文文档好、上手极快 | 面试话题度低于 Spring Security |
| Shiro | 老牌、简单 | 生态停滞，Boot 3 适配一般 |

**决策**：Spring Security 6 + JWT。**「学习曲线陡」正是选它的理由**——校招面试几乎必问 Spring Security 的过滤器链和认证流程，用过才有话说。

**方案要点**：

- **双 Token**：access（30 分钟，无状态验签）+ refresh（7 天，存 Redis 可吊销）；
- **刷新轮换**：用 refresh 换新 access 时，旧 refresh 立即失效，防止 refresh 泄露被长期利用；
- **登出**：把 access 的 `jti` 加入 Redis 黑名单，TTL 设为 access 剩余有效期（避免黑名单无限膨胀）；
- **C 端与后台分离两套 UserDetailsService**：`ums_user` 与 `sys_user` 是两套体系，用不同的 `AuthenticationProvider`，避免权限串台；
- **无状态**：`SessionCreationPolicy.STATELESS`，禁用 CSRF（用 JWT 而非 Cookie）。

> **面试问答**
> Q：JWT 有什么缺点？怎么解决？
> A：最大缺点是**无法主动失效**——签发后在过期前一直有效。解决方案有几种：① 缩短有效期 + refresh token 换发（我用的方案）；② 维护黑名单（Redis 存 jti），代价是每次请求多一次 Redis 查询，退化成了有状态；③ 双 Token 里 access 短到 5 分钟，把失效延迟控制在可接受范围。我选了 ① + ③ 的组合，登出场景额外用黑名单兜底。另一个缺点是 JWT 体积大，放在 Header 里每次请求都会带上，比 SessionId 费带宽。
> Q：Spring Security 的过滤器链说一下。
> A：核心是 `FilterChainProxy`，它内部维护多个 `SecurityFilterChain`，按 `@Order` 和 `securityMatcher` 匹配。常用过滤器顺序：`SecurityContextPersistenceFilter` → `UsernamePasswordAuthenticationFilter`（登录）→ `JwtAuthenticationFilter`（我自定义，插在这里）→ `ExceptionTranslationFilter`（异常转 401/403）→ `FilterSecurityInterceptor`（最终授权决策）。我自定义的 JWT 过滤器继承 `OncePerRequestFilter`，解析 Token 后把 `Authentication` 放进 `SecurityContextHolder`，后面的授权才能生效。

## 4. 明确不引入的组件（附论证）

这一节是你面试时的**护城河**。面试官问「为什么不做 X」，你答得出来，就证明了你在做技术决策而不是抄教程。

### 4.1 不引入微服务（Spring Cloud / Nacos / Gateway / OpenFeign）

| 维度 | 分析 |
|---|---|
| 微服务解决什么 | 独立部署、独立扩缩容、技术异构、团队并行开发 |
| 我的场景需要吗 | **不需要**。单人开发、单机部署、代码量 3 万行以内，拆开只会让「改一个需求要动 4 个工程 + 重启 4 个服务」 |
| 引入的代价 | 注册中心、配置中心、网关、链路追踪、分布式事务全是新增复杂度；本地开发要起 5+ 进程 |
| 什么情况下该拆 | 当出现「不同模块的扩缩容需求差异巨大」（如秒杀要 50 个实例、商品管理只要 2 个），或「团队超过 10 人互相踩代码」 |
| 如果拆我会怎么拆 | 见 `03-系统架构设计.md` 的演进章节——**先拆秒杀，再拆商品，最后拆订单**，因为秒杀的扩缩容诉求与主站差异最大 |

#### ⚠️ 常见误解：**用了消息队列 ≠ 用了微服务**

需求确认时暴露出这个混淆，这里专门澄清，因为它同时是**高频面试考点**。

| | 消息队列（MQ） | 微服务 |
|---|---|---|
| 本质 | **中间件**，提供异步通信能力 | **架构风格**，把应用拆成多个独立部署的服务 |
| 解决的问题 | 异步解耦、流量削峰、最终一致 | 独立部署、独立扩缩容、技术异构、团队并行开发 |
| 单体能用吗 | ✅ **能，而且很常见** | ❌ 用不上，微服务的前提就是「多服务」 |
| 需要服务发现/网关吗 | 不需要 | 需要 |
| 本项目 | ✅ 用 RocketMQ | ❌ 不用 |

**为什么单体 + MQ 反而是最好的秒杀方案**：

```
用户请求
  └→ 单体应用 shopping-web
       ├→ Redis Lua 预扣库存（挡住 99% 流量）
       ├→ 往 RocketMQ 发一条消息（几毫秒）
       └→ 立即返回「排队中」                    ← 请求到此结束，不占线程
                                                    ↓
              RocketMQ 按自己的节奏投递
                                                    ↓
  └→ 同一个单体应用里的消费者
       ├→ 落库 sms_seckill_record（唯一索引防重）
       └→ 条件更新 wms_stock
```

**注意看**：发消息的和消费消息的**是同一个应用**。没有服务发现、没有网关、没有 Feign 调用、没有分布式事务。MQ 在这里的作用纯粹是「**把瞬时洪峰摊平成一条平缓的消息流**」。

如果硬要拆成微服务，你会额外得到：注册中心、配置中心、网关、链路追踪、跨服务事务——**而秒杀的性能一分都不会提升**。

> **面试问答**
> Q：你用了消息队列，那你这算微服务吗？为什么不用微服务？
> A：不算。MQ 是中间件，微服务是架构风格，两者维度不同。我这是单体应用，用 RocketMQ 是为了两件事：**削峰**（秒杀请求异步落库）和**延迟消息**（订单超时关单）。这两件事在单体里做和微服务里做代码几乎一样，区别只在微服务里消费者会独立部署。我之所以不拆微服务，是因为单人开发、单机部署的场景下，拆分的收益（独立扩缩容）远小于它的成本（注册中心、网关、分布式事务、本地要起 5 个进程才能调试）。**我判断当前阶段「能不能跑通并讲透」比「架构先不先进」更重要。**
>
> Q：那什么时候该拆？
> A：当**不同模块的扩缩容诉求出现数量级差异**时。比如秒杀活动需要 50 个实例，而商品管理只需要 2 个——这时候不拆就是在为秒杀浪费 48 个实例。或者团队超过 10 个人，代码互相踩踏的沟通成本超过拆分的成本。我现在两个条件都不满足。

#### 详细程度自检：MQ 的三种消息类型对应本项目的三个用途

| 用途 | 消息类型 | Topic | 为什么必须是 MQ |
|---|---|---|---|
| 订单超时关单 | **延迟消息**（level 16 ≈ 30min） | `order-timeout-topic` | 定时扫表精度差且有大量空扫 |
| 秒杀异步下单 | 普通消息（削峰） | `seckill-order-topic` | 同步落库扛不住瞬时并发 |
| 支付成功后通知下游 | 普通消息（最终一致） | `payment-success-topic` | 与本地消息表配合，保证不丢 |

### 4.2 不引入 Seata（分布式事务）

- 分布式事务的前提是**分布式**。我是**单机单库**，一个 `@Transactional` 就能覆盖下单的全部写操作，不存在跨服务事务。
- 唯一需要「最终一致」的场景是**支付回调 → 更新订单 → 通知下游**，我用**本地消息表**解决：在同一个本地事务里写业务数据 + 写消息表，再由定时任务投递 MQ，下游幂等消费。这个方案的好处是**不依赖任何中间件的可靠性**，消息不丢的原因写在数据库里。
- **面试价值**：本地消息表比 Seata 更容易讲透，且能引出「幂等」「重试」「死信」一串追问，反问空间大。

### 4.3 不引入 ShardingSphere（分库分表）

- 分库分表解决的是**单表数据量过大导致索引深度增加、查询变慢**的问题，通常在**单表千万行以上**才明显。
- 我的 `oms_order` 预估最多几十万行，加了索引后查询在毫秒级，分表是纯粹的负收益。
- 更重要的是：**分表会引入分布式主键、跨分片查询、跨分片分页、扩容迁移等一堆问题**，而这些问题的解决方案我讲不深，反而暴露短板。
- **面试时的正确答法**：承认知道分表方案（如按 `user_id` 取模分 16 表、用 ShardingSphere-JDBC、基因法保证同用户订单落同库），然后说明「我判断当前数据量不构成瓶颈，所以没做；如果要做，我的分片键会选 `user_id`，因为 C 端查询 99% 是『查我的订单』，能避免跨分片」。

### 4.4 其它不引入

| 组件 | 不引入的理由 | 面试话术 |
|---|---|---|
| Elasticsearch | 商品搜索用 MySQL `LIKE` + 类目筛选可满足；ES 需要独立集群和数据同步链路 | 「ES 我了解，倒排索引 + 分词，适合全文检索和聚合。我的商品量在千级，`LIKE` 配合索引够用，引入 ES 还要维护 MySQL→ES 的同步，我用 Canal 或双写都能做，但当前不值得。」 |
| 读写分离 / 多数据源 | 无可验证的真实主从环境 | 「读写分离的核心是主从延迟导致的一致性问题，我没有真实从库，做了也无法验证延迟影响，属于纸上谈兵。」 |
| Kubernetes | 单机部署无调度需求 | 「K8s 我了解 Pod/Service/Ingress 的概念，但它是为多机弹性伸缩设计的，我单机跑单体应用引它没有收益。」 |
| Prometheus + Grafana | 单体应用用 Actuator + 日志足够 | 「监控我用了 Spring Boot Actuator 暴露指标 + 慢 SQL 日志。如果多实例了，我会接 Micrometer + Prometheus。」 |
| 推荐系统 / 大数据 | 与 Java 后端岗位无关 | — |

### 4.5 能不能直接套用开源商城（mall4j 等）？

这是一个**必须正面回答**的问题，因为它同时涉及技术适配、开源协议和求职风险三件事。

#### 4.5.1 先看清 mall4j 的真实情况

以 [mall4j](https://github.com/gz-yami/mall4j) 为例（它是国内最知名的 Java 开源商城之一）：

| 项 | 事实 |
|---|---|
| **开源协议** | **AGPLv3** —— 强传染性协议。**分发（含部署到公网供他人访问）时，必须把你自己修改后的全部源码同样以 AGPLv3 开源**。闭源商用需另购商业授权 |
| 后端技术栈 | **Spring Boot 4.x** + **Sa-Token** + MyBatis / MyBatis-Plus + Redis + Redisson + Knife4j + Hutool |
| 前端仓库 | [mall4v](https://gitee.com/gz-yami/mall4v)（Vue3 管理后台）、[mall4uni](https://github.com/gz-yami/mall4uni)（uni-app 多端）、mall4m（微信小程序） |
| 业务范围 | 开源版是 **B2C 单商户**（商品、订单、会员、SKU、购物车、支付、权限、内容、统计）；多商户/SaaS/跨境属**商业版** |

> 有意思的是，mall4j 的技术选型和本项目**高度重合**（MyBatis-Plus + Redis + Redisson + Knife4j + Hutool），说明本项目的选型方向是行业主流。但有两处关键差异：它用 **Spring Boot 4**（本项目锁定 3.2），且用 **Sa-Token** 而非 Spring Security（本项目用 Spring Security，理由见 §3.10）。

#### 4.5.2 技术上"套"得动吗？

分两种理解：

**理解 A：把 mall4j 整套前端接到我的后端上**
- 前端是前后端分离的，理论上换个 baseURL 就行；
- **但接口契约完全不同**。mall4j 的接口路径、入参出参、分页格式都是它自己的规范，而本项目的表结构（`04-数据库设计.md` 的 41 张表）和模块划分与它不一致；
- 结果是：要么按 mall4j 的接口改自己的后端，要么写一层适配。**适配成本很可能高于自己写前端。**

**理解 B：把 mall4j 当前端脚手架/参考**
- 可行，且是推荐做法。

#### 4.5.3 真正的风险不在技术，在求职

| 风险 | 说明 | 严重程度 |
|---|---|---|
| **① 会被认出来** | mall4j 是知名项目，电商项目本就高度同质化。面试官一句「你这页面和 mall4j 一样啊」直接击穿 | 🔴 致命 |
| **② 面试深挖必挂** | 套来的代码你讲不出「为什么这么设计」。问「订单状态机怎么防止乱改」「SPU/SKU 为什么这么建模」「库存怎么防超卖」→ 当场答不上来 | 🔴 致命 |
| **③ STAR 讲不出故事** | 面试讲的是「我遇到什么问题、怎么权衡、怎么解决」。抄来的代码没有你的踩坑，**等于没有素材** | 🔴 致命 |
| **④ AGPLv3 传染** | 部署到公网 = 分发，需以 AGPLv3 开源全部代码。作品集通常无所谓，但**你得知道**这件事 | 🟡 中等 |
| **⑤ 技术栈错位** | 它用 Boot 4 + Sa-Token，本项目用 Boot 3.2 + Spring Security，直接抄会引入一套不兼容的依赖树 | 🟡 中等 |

#### 4.5.4 分层结论（**这是你要的答案**）

| 层 | 能否套用 | 理由 |
|---|---|---|
| **后端业务代码** | ❌ **绝对不能** | 这是 Java 岗的考察核心，也是面试深挖的地方。AGPL + 同质化 + 讲不出来，三重减分 |
| **后端分层与包结构** | ✅ **参考后自己写** | 学它的模块划分、命名规范、目录组织，然后自己实现 |
| **数据库表设计** | ⚠️ 参考可以，照抄不行 | 本项目已有自己的一套（`04` 文档），照抄会与后端代码脱节 |
| **管理后台前端** | ⚠️ 借用可以，**但优先选通用脚手架** | 前端不是 Java 岗考察点；但用 **vue-element-admin / vue-pure-admin / Vben Admin** 这类**与业务无关的通用脚手架**，适配成本远低于 mall4j 的业务前端 |
| **商城前台 H5/小程序** | ✅ 可以借用 | 同理；mall4uni / Vant 模板打底 |

#### 4.5.5 推荐的正确姿势：把 mall4j 当"参考实现"来读

这是**投入产出比最高**的用法，而且**本身是面试加分项**：

1. **读它的 SPU/SKU 建模** → 对比自己的设计 → 面试时讲「我读了 mall4j 的实现，它在 X 上这么做，但我选了 Y，因为我的场景是 Z」。**这证明你会读源码、有独立判断。**
2. **读它的表结构** → 用来校验自己有没有漏字段（比如运费模板、售后流程）。
3. **前端借它的组件写法与页面结构**，但接口层自己写。
4. **绝不复制粘贴后端代码进自己的仓库**——一旦复制，git 记录和你的理解都会出问题。

#### 4.5.6 面试话术模板

如果面试官直接问「你这项目是不是套的开源商城」：

> 「前端我基于开源的 Vue3 通用脚手架二次开发，主要工作在后端的接口设计和权限对接——这在行业里是常规做法。
> 后端是我自己写的。我确实**读过 mall4j 的实现作为参考**，用来校验我的表设计有没有遗漏，比如它的运费模板设计我就借鉴了思路。但核心链路是我自己设计的，因为我要能讲清楚每一个决策——比如它的 XX 我做了不同处理，因为……（讲一个你真实改过的地方）。
> 而且它是 AGPLv3，真要商用还得买授权，所以我只是当参考资料读。」

**关键**：这段话之所以有说服力，是因为你能**当场讲出一个你改过的地方**。所以读完参考实现后，**一定要留下自己的判断记录**（写进 `notes/`）。

> **一句话原则**：**可以借"脚手架"和"思路"，不能借"业务代码"和"设计决策"。** 前者是行业惯例，后者是你的面试答案。

## 5. 版本兼容性坑（**落地前必读**）

这是本文**最实用**的一节。Spring Boot 3 生态里，很多依赖的坐标和 API 都变了，直接抄老代码会踩坑。

| # | 坑 | 现象 | 解法 |
|---|---|---|---|
| 1 | **MyBatis-Plus 的 Boot 3 坐标不同** | 用 `mybatis-plus-boot-starter` 启动报 `NoClassDefFoundError: javax/...` | Boot 3 必须用 `mybatis-plus-spring-boot3-starter` |
| 2 | **MP 3.5.9+ 分页插件被拆出** | 分页失效，`PaginationInnerInterceptor` 找不到类 | 额外引入 `com.baomidou:mybatis-plus-jsqlparser`（或 jsqlparser-4.9 变体） |
| 3 | **`javax.*` → `jakarta.*`** | `import javax.servlet.*` 编译不过 | Servlet / Validation / Annotation 全部换 `jakarta.*` |
| 4 | **Spring Security 6 移除了 `WebSecurityConfigurerAdapter`** | 老教程代码编译不过 | 改为声明 `SecurityFilterChain` Bean，用 Lambda DSL |
| 5 | **Spring Security 6 授权写法变化** | `antMatchers` 已废弃 | 改用 `requestMatchers`；方法级用 `@PreAuthorize` |
| 6 | **jjwt 0.12.x API 大改** | `setSubject`/`parseClaimsJws` 找不到 | 用 `Jwts.builder().subject(...).signWith(key)` 与 `Jwts.parser().verifyWith(key).build().parseSignedClaims(token)` |
| 7 | **Knife4j 坐标要带 jakarta** | 文档页 404 或启动报错 | 用 `knife4j-openapi3-jakarta-spring-boot-starter`，且 springdoc 版本需与 Boot 3.2 匹配（2.3.x） |
| 8 | **Lombok + MapStruct 一起用时注解处理器顺序** | MapStruct 生成的实现类里字段全是 null | 加 `lombok-mapstruct-binding` 依赖，并在 `maven-compiler-plugin` 的 `annotationProcessorPaths` 中按 Lombok → binding → MapStruct 的顺序声明 |
| 9 | **RocketMQ starter 对 Boot 3 的支持** | 自动装配失效或报 javax 错误 | 必须挑支持 Boot 3 的 starter 版本（2.3.x 起）；**落地前先写一个最小 demo 验证能收发消息** |
| 10 | **HikariCP `max-lifetime` > MySQL `wait_timeout`** | 偶发 `Communications link failure` | `max-lifetime` 设为 MySQL `wait_timeout` 的 2/3 以内 |
| 11 | **系统编码 GBK 导致中文乱码** | 控制台/日志/DB 中文变问号 | 父 POM 设 `project.build.sourceEncoding=UTF-8`；启动加 `-Dfile.encoding=UTF-8`；JDBC URL 加 `characterEncoding=utf8&serverTimezone=Asia/Shanghai` |
| 12 | **`PATH` 上的 `javac` 是 JDK 8** | 命令行编译报 `class file version 61.0` | 见 `00-蓝图与术语表.md` §9 坑 1 |
| 13 | **`spring.data.redis.password` 写成 `${REDIS_PASSWORD:}`** | 启动报 `Unable to connect to Redis server`，根因是 `ERR Client sent AUTH, but no password is set` | **空字符串不是"没密码"**！占位符无默认值时解析成 `""`，Redisson 视为已配置密码并发送 `AUTH ""`。**正确做法：本机无密码就整行不写**；需要密码用环境变量 `SPRING_DATA_REDIS_PASSWORD` 注入（松绑定） |
| 14 | **PowerShell 下 `java -Dfile.encoding=UTF-8` 被拆参数** | 报 `ClassNotFoundException: /encoding=UTF-8` / `找不到或无法加载主类 .encoding=UTF-8` | 带点的 `-D...` 参数被 PowerShell 拆开了。改用环境变量：`$env:JAVA_TOOL_OPTIONS='-Dfile.encoding=UTF-8'`（`SPRING_PROFILES_ACTIVE` 同理，比 `--spring.profiles.active=dev` 更稳） |
| 15 | **本机 Redis 是 3.0.504（Windows 移植版）** | 与规划中的 Redis 7 有代差 | `EVAL`/Lua 在 2.6+ 就支持，秒杀预扣**不受影响**；但 Streams（5.0+）、部分 `OBJECT`/`ACL` 命令（6.0+）不可用。若 Phase 3 遇到怪问题，优先怀疑版本，用 Docker 起 `redis:7` 即可（注意端口与 6379 冲突，见 `00` §11.3） |
| 16 | **本机只有 Windows PowerShell 5.1，没有 pwsh 7**；且 ANSI 代码页是 936(GBK) | 写好的 `.ps1` 报一堆「意外的标记」「哈希文本不完整」，中文全变乱码 | **含中文的 `.ps1` 必须存成「UTF-8 带 BOM」**。PowerShell 5.1 对**无 BOM** 的脚本按 ANSI(GBK) 解码，中文注释会被拆成非法 token。另：5.1 默认禁止运行脚本，需 `Set-ExecutionPolicy -Scope Process Bypass`；`pwsh` 命令不存在，直接 `& script.ps1` 调用 |
| 17 | **`spring-boot-starter-validation` 未引入** | `@Valid` / `@NotBlank` **完全不生效，且不报任何错** —— 校验被静默跳过，请求直接打到业务逻辑 | Spring Boot **2.3 之后** `spring-boot-starter-web` 不再传递引入 Hibernate Validator。光有 `jakarta.validation-api`（只有注解、没有实现）等于没写校验。**必须显式加 `spring-boot-starter-validation`**。本项目的验收脚本就是这么抓出来的：密码传 1 位竟然没被拦下 |
| 18 | **`javax.validation` 与 `jakarta.validation` 混用** | 校验不生效、或启动报找不到校验器 | Boot 3 必须全用 `jakarta.validation.*`。老代码里的 `javax.validation.constraints.NotBlank` 编译不过（好在这个会立刻暴露），但**从 `javax` 换成 `jakarta` 时容易漏掉一两个**，漏掉的那个注解就静默失效 |
| 19 | **PowerShell 5.1 的 `Invoke-WebRequest` 把请求体中文变成 `?`** | 接口测试出现**假象**：发 `甲`/`乙` 两个值，服务端收到的都是 `?`，于是报「属性值重复」——看起来像后端 bug | `ContentType` 不含 charset 时，PS 5.1 按 Latin1/ASCII 编码字符串。**必须** `$params['Body'] = [Text.Encoding]::UTF8.GetBytes($json)` 且 `ContentType = 'application/json; charset=utf-8'`。`tools/ApiTestCommon.ps1` 已封装正确写法 |
| 20 | **逻辑删除 + 唯一索引带 `deleted` 时，同名删两次会撞唯一键** | 删除接口返回 `6001`（DuplicateKey），正常使用即可触发 | 见 `docs/04` §1.7 **方案 C**：删除时同时改写唯一列，如 `name = CONCAT(LEFT(name,36),'_del_',id)`。已作用于 `pms_attribute` / `pms_attribute_value` / `pms_brand` / `pms_sku`。**面试价值高**——这是「逻辑删除与唯一索引冲突」的真实案例 |
| 21 | **唯一索引的两个唯一列都是「关联 ID」时，方案 C 也救不了** | `pms_sku_attribute_value` 唯一键是 `(sku_id, attribute_id, deleted)` —— 两列都是 ID，**无法靠改名逃逸**；反复保存商品时删除接口报 `6001` | **对「可完全重建的派生数据」改用物理删除**。判断标准：**数据有独立业务含义 → 逻辑删除保历史；数据能 100% 重建 → 物理删除**。已作用于 `pms_spu_attribute` / `pms_sku_attribute_value`。⚠️ MP 的 `@TableLogic` 会把 `delete()` 变成 UPDATE，所以物理删除必须走**手写 XML** |
| 22 | **PowerShell 把单元素数组解包成裸字符串** | `$result[0]` 取到的是**首字符**而非首行 —— 表现为 `price=1`、`sum=1` 这种诡异值，极易误判成后端 bug | 函数内用逗号运算符强制保持数组：`return ,$lines`。另外 `mysql -B` 输出是 **TAB 分隔多列**，PowerShell 只按换行切分，取值必须 `-split "`t"` |
| 23 | **详情接口依赖某个冗余字段一定有值** | 种子数据的 `pms_spu_attribute.value_json` 为 NULL，导致详情接口回填不出规格属性的 `valueIds` | 读路径要**从权威来源兜底推导**：`value_json` 为空时从 `pms_sku_attribute_value` 反查该 SPU 选过哪些属性值。原则：**冗余字段只能是加速手段，不能成为唯一数据来源** |
| 24 | **JWT 过滤器不限定路径** ⚠️ **安全漏洞** | 后台令牌打到 `/api/app/**` 时，后台过滤器照样把 `LoginUser` 塞进 `SecurityContext` → `authenticated()` 判定通过 → **C 端接口接受了后台身份**（实测返回 200） | 每个 JWT 过滤器都必须用 `shouldNotFilter()` 限定只处理自己那一端的路径（`/api/admin/` vs `/api/app/`）。**再加一道 scope 校验**（令牌里的 `userScope` 声明）作为第二防线。两层叠加才是真正的「两条认证链」 |
| 25 | **容器里有两个 `AuthenticationManager` bean** | 启动失败：`Found 2 beans for type AuthenticationManager, but none marked as primary` —— Spring Security 内部的 `HttpSecurityConfiguration` 需要唯一一个 | 给其中一个加 `@Primary`（本项目给后台那个），并在**所有业务代码里用显式 `@Qualifier` 注入**，绝不依赖 primary。⚠️ 另外：字段上的 `@Qualifier` 能否被 Lombok 的 `@RequiredArgsConstructor` 复制到构造器参数，取决于配置——**认证链选错是安全事故级 bug，值得手写构造器** |
| 26 | **「删除时改写唯一列」必须算长度，否则撞 `varchar` 上限** | 测试脚本清理会员时报「数据过长」→ 清理静默失败 → 后续注册撞重复 → 报出一连串误导性错误 | 改写后的值必须放得进原列宽：`phone` 是 `varchar(20)`，而 `LEFT(phone,10) + '_del_'(5) + 19位雪花ID = 34` 字符 → **必然失败**。两个原则：① 用方案 C 前先算 `LEFT(x, N)` 里的 N（本项目的 `pms_attribute.name` 用 36、`pms_sku.sku_code` 用 36，都是算过的）；② **测试夹具直接物理删除**，不要给它套用生产数据的保留策略 |
| 27 | **`mysql -B` 把 `NULL` 输出成字符串 `"NULL"`，不是空串** | 断言「发货后 `finish_time` 应为空」失败，一度以为 `updateStatus` 把完成时间也写了 —— 实际是脚本拿 `"NULL"` 和 `""` 比较 | 用 mysql 客户端做 DB 断言时，**判空要写 `-eq 'NULL'`**。更稳的做法是让 SQL 自己输出判定结果（如 `SELECT IF(finish_time IS NULL,'PASS','FAIL')`），把「怎么判空」交给 SQL 而不是脚本 |
| 28 | **测试里依赖「前面步骤累加出来的状态」** | 断言金额 = 1000×2，实际是 1000×3：因为中途有一步「补一个商品回购物车」把同一个 SKU 的数量又加了一次 | 测试里的每个数字都要**在断言前显式设定**（如先 `PUT /quantity` 设成 2），不要依赖累积。隐式状态会让一次无辜的修改在不相关的位置爆出失败，排查成本极高 |
| 29 | **Docker 健康检查命令必须只用镜像里「确实存在」的工具** | `rmqnamesrv` 一直是 `unhealthy`，依赖它的 broker **根本不启动**；但看容器日志里明明写着 `The Name Server boot success` | 我写的 healthcheck 是 `netstat -an \| grep 9876`，而 RocketMQ 镜像基于精简 JRE，**既没有 netstat 也没有 grep** → 检查命令本身失败 → 永远 unhealthy。**症状极具误导性**：以为 NameServer 有问题，实际是检查脚本有问题。结论：要么用镜像内确实有的命令，要么**干脆不用 healthcheck**，用 `restart: unless-stopped` 让依赖方自己重试 |
| 30 | **Docker 里跑 RocketMQ：`brokerIP1` 必须写宿主机可达地址** | 不写时 broker 把**容器内网 IP**（如 172.17.0.2）注册到 NameServer，而该网段在 Windows/macOS 宿主机上**不可路由**。症状：NameServer 连得上、能拿到路由，但发消息报 `sendDefaultImpl call timeout` | 设 `brokerIP1 = 127.0.0.1`，配合 `ports: 10911:10911` 端口映射 |
| 31 | ⚠️ **支付回调的「按 notify_id 去重」必须在验签之后** | 一条**签名错误**的伪造通知也能占住某个 `notify_id`；渠道随后用**同一个 notify_id** 发来的**真通知**会被判成「重复」直接返回 success —— **我们没处理，但渠道以为处理了**，这笔钱收不到且渠道不再重试（**丢单**） | ① **先验签**，不过的一律不进业务分支；② 验签失败的记录用**派生 key**（`notifyId + ":INVALID"`）落库，**不占用渠道真正的 notify_id**，审计痕迹也保留。核心认识：**幂等键标识的应该是「通知被成功处理」，而不是「通知被收到」** |
| 32 | **`notify_id` 是参与签名的字段** | 测试里「拿到报文后改 notify_id 再重放」导致**连真通知都验签失败**，误以为代码有 bug | 要改变任何参与签名的字段，都必须**重新计算签名**（或让网关一开始就用目标值生成报文）。写测试时也要问一句：这个字段在签名范围内吗？ |
| 33 | **「读取」与「写入」不能共用一个接口** | 验收脚本为了「拿到渠道通知报文」而调了 `mock-gateway/pay` —— 结果**支付真的发生了**，后续所有篡改测试全部失去意义 | 拆成 `build-notify`（只生成报文）与 `pay`（生成并投递）。这也更贴近真实渠道：渠道先组报文，再按自己的节奏（含重试）投递 |
| 34 | **Lombok 对 `boolean` 字段生成的是 `isXxx()` 而不是 `xxx()`** | 编译报「找不到符号 `needsReturn()`」，而字段明明就叫 `needsReturn` | `@Getter` 给 `boolean` 字段生成 `isNeedsReturn()`。领域语言里 `type.needsReturn()`（是否要寄回）比 `isNeedsReturn()` 更自然 —— **这两个方法显式手写**，不要跟 Lombok 的命名规则较劲 |
| 35 | ⚠️ **「订单级状态」不能当作「商品级操作」的门槛** | 第一版把「必须是待收货/已完成」写成硬校验，结果**一笔订单只要有一个商品在售后中，其它商品就再也申请不了售后**（多商品订单无法逐个退） | 售后挂在**订单明细**上，所以 `售后中(5)` 也必须允许**继续申请其它明细**的售后；真正的重复防护是「同明细同类型只能一次」+ 唯一索引，而不是订单状态。<br>**通用教训：状态检查的粒度必须和业务操作的粒度一致。** |
| 36 | **多商品订单：退掉一件不能把整单标成「已退款」** | 若不判断，退掉商品 A 后订单直接变「已退款」，商品 B 的售后完成时发现订单已不在「售后中」→ 状态推不动，B 永远退不掉 | 退款完成时判断「是否所有明细都已全额退款」，是才把订单置为已退款，否则订单保持「售后中」并只记流水。同理，**售后被拒/撤销后还原订单状态前，也要检查是否还有其它进行中的售后** |
| 37 | **「仅退款」不补库存，「退货退款」才补** | 若一律回补库存：钱退了、货还在买家手里，库存却加回去了 → **账面凭空多一件货 → 最终超卖** | 把「是否需要回补库存」收敛到枚举里（`AftersaleType.refundsStock()`），**不要散落在业务代码的 if 中**。这是财务与库存的一致性底线 |
| 38 | ⚠️ **秒杀投放量必须 ≤ 真实可售库存** | 抢购在 Redis 层「成功」了，但消费者建单时 `lockStock` 失败 → 回滚 Redis → **表现成「抢到了但什么都没发生，库存还回到满」**。非常难查：接口返回过 200，但 DB 里既没有订单也没有记录 | ① 预热/开抢前校验 `seckill_stock <= wms_stock.available_stock`（本项目在压测脚本里加了这道守卫，直接 `exit 1`）；② **消费者失败必须回滚 Redis 占位**，否则库存永久泄漏。两条都要有 |
| 39 | ⚠️ **预热必须用 SETNX，不能无条件覆盖** | 活动进行中一次「重新预热」会把已扣掉的库存**重置回满** → 直接超卖 | `setIfAbsent(key, value, ttl)`。这个 bug 只在「活动已经开始」时才出现，本地刚启动时怎么测都是对的 |
| 40 | **不要断言异步链路的「中间态」** | 验收脚本断言「抢购后此刻 DB 还没有记录」「此刻 Redis 已扣 1」—— 消费者预热后几十毫秒就处理完了，这两个断言必然 flaky | 只断言**最终态**（轮询 Wait-Until）与**不变量**（库存不会变多、已售 ≤ 库存）。异步系统的测试必须按最终一致性写 |
| 41 | **压测的预热请求不能打在「会消耗资源」的接口上** | `--warmup 20` 打抢购接口 → 白吃掉 20 件库存 → 数字变成「1000 请求成功 80」，看起来像 bug | 预热只用来建立连接/预热 JIT，应打**只读**接口（如活动列表）。要动业务的压测，预热必须为 0 |
| 42 | ⚠️⚠️ **压测前必须清理「上一轮残留的状态」** | 第二次压测出现「1000 请求 227 成功、但 sold=0/订单=0/Redis 库存=100」。根因是上一轮的 100 笔订单**各锁了 1 件真实库存**，只删订单没释放 `locked_stock` → `available=0`；消费者全部失败并回滚 | 压测脚本的重置必须覆盖**全部**状态：秒杀已售、真实库存与锁定、库存流水、订单/记录、**Redis key**、一人一单标记。**「删了订单就等于重置了」是这个坑的核心错觉** |
| 43 | **压测工具的选择不必死守 JMeter** | 本机下载 JMeter（85MB）实测只有 **43KB/s**，要 30 分钟 | 用 JDK 单文件源码启动写一个压测器（`java LoadTest.java`），只依赖 JDK 自带的 `HttpClient`，同样能给出 QPS / P50 / P90 / P99 / 错误率。**压测的价值在测量方法与结论，不在工具品牌** |

| 44 | ⚠️⚠️ **开发期 CORS 白名单必须覆盖所有前端端口；`changeOrigin: true` 会让"同源代理"变成"跨域"** | 前端走同源相对路径 `/api/...` + vite 代理，直觉上后端看到的是同源请求。但代理配了 `changeOrigin: true` 会把 `Host` 改写成后端地址，而浏览器 POST 又带 `Origin: localhost:5174` → Spring 判定跨域 → 白名单里没有 5174 → **`403 Invalid CORS request`**。前端把 403 显示成"没有权限"，看着像权限 bug，实则是跨域被拒 | ① 白名单用 `setAllowedOriginPatterns` + `http://localhost:*` 做端口通配，别逐个枚举；② 生产环境换成真实域名，且前端与 API 同源（Nginx 反代）从根上不需要 CORS。**"加个代理就没跨域"是一种很常见的错觉** |
| 45 | ⚠️⚠️ **涉及 CORS 的自动化验收，必须带真实的 `Origin` 头** | 脚本用 `Invoke-WebRequest`/curl 裸打接口，不带 `Origin` 就没有 CORS 判断，**全绿**；真实浏览器一开就全站 403 —— 这条链路等于完全没测 | 请求里显式带 `Origin`（与前端地址一致），并补一条 **`OPTIONS` 预检断言**。注意**预检成功返回 204 而不是 200**。教训：**验收的"代表性"比"覆盖率"更重要** —— 请求头不对，测一百遍也测不到真实浏览器的路径 |
| 46 | **验收脚本要"早失败并说清原因"，不要级联失败** | 演示商品被下架后，脚本从"商品列表为空"开始一路报出 28 项失败（详情 2001 → 加购 skuId 空 → 下单 3004 → 支付 orderNo 空 → ……），一大片红字把真正原因（商品下架）埋掉了 | 关键前置条件为空时**立即终止**，并打印修复方式（如 `UPDATE pms_spu SET status=1 WHERE id=1`）。级联失败的噪音比失败本身更浪费时间 |

> **关于坑 2 的补充**：MyBatis-Plus 从 3.5.9 起把 JSqlParser 抽成独立坐标，`PaginationInnerInterceptor` 随之从主包移出，导致大量项目升级后报「找不到分页插件」。官方 issue 见 [baomidou/mybatis-plus#6557](https://github.com/baomidou/mybatis-plus/issues/6557#issue-2615655208) 与 [#6559](https://github.com/baomidou/mybatis-plus/issues/6559#issue-2617614181)，[v3.5.9 Release Note](https://github.com/baomidou/mybatis-plus/releases/tag/v3.5.9) 有说明。本项目锁定 **3.5.7** 规避此坑；若升级到 3.5.9+，必须同步加依赖。

### 5.1 最小验证顺序（强烈建议）

不要一次性把 12 个依赖全加上跑。按这个顺序**每加一个就跑一次**：

1. `spring-boot-starter-web` → 能起服务、能返回 Hello
2. `spring-boot-starter-test` → 能跑通一个测试
3. MySQL + MyBatis-Plus → 能查出一行数据（**这里最容易卡**）
4. Redis → `SET`/`GET` 通
5. Spring Security + JWT → 能登录拿 Token，能带 Token 访问受保护接口
6. Knife4j → 文档页能打开
7. RocketMQ（Docker）→ 能发一条消息并消费到
8. MapStruct → 转换结果字段不为 null

**每步验证通过后再继续**，这样出问题时一定是最新加的那个依赖引起的，排查成本极低。这是本项目最重要的一条工程经验。

## 8. 选型结论速查（面试前扫一眼）

| 决策 | 一句话理由 |
|---|---|
| Java 17 | Spring Boot 3 硬性要求 + LTS，且本机 `JAVA_HOME` 已是它 |
| Spring Boot 3.2 | 与 JDK 17 匹配，引出 Jakarta 迁移与自动装配话题 |
| Spring MVC | 响应式是传染的，MyBatis 阻塞会让 WebFlux 收益归零 |
| MyBatis-Plus | 单表零 SQL、复杂查询手写，兼顾效率与可控 |
| MySQL 8.0 | 国内主流，面试八股全围绕它 |
| HikariCP | Boot 默认且性能最好，监控交给慢查询日志 |
| Redis 7 | **Lua 原子性是秒杀防超卖的决定性理由** |
| Redisson | 看门狗解决锁续期，避免手写 SETNX 的经典坑 |
| RocketMQ | **原生延迟消息是超时关单的决定性理由** |
| Spring Security + JWT | 学习曲线陡正是选它的理由，面试必问 |
| 单体多模块 | 校招场景下微服务是减分项；预留 `merchant_id` 与演进路径 |
| 不引入 Seata | 单库无分布式事务，本地消息表更好讲 |
| 不引入分库分表 | 数据量不到千万级，负收益 |
