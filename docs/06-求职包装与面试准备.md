# 06 · 求职包装与面试准备

> 本文面向**正在投递 Java 后端校招 / 实习的应届生**，目标只有一个：**把 `shopping-mall` 这个项目变成 offer**。
> 全文的模块名、表名、技术栈、ADR 编号、Phase 划分一律以 `00-蓝图与术语表.md` 为唯一事实源。
> 技术栈口径固定为：**Java 17 / Spring Boot 3.2.x / MyBatis-Plus 3.5.x / MySQL 8.0 / Redis 7.x / RocketMQ 5.x / Redisson 3.x**。

## 0. 使用说明（先读这 10 行）

1. **本文只教「怎么把已经做出来的东西讲好」，不教你编。** 凡是简历里出现的功能、数据、指标，你**必须真的做过、真的测过**。面试官平均只花 3 分钟就能判断一个项目是不是自己写的——问一个你代码里的类名、一个你踩过的坑、一个表字段就够了。
2. 第 1 章改简历，第 2 章背口播稿，第 3 章是复习卡片（最厚，面试前反复刷），第 4 章是保命话术，第 5 章练演示，第 6 章收拾 GitHub，第 7 章投递，第 8 章前一天过一遍。
3. 文中的 `【填真实数字】` 是**必须你自己填**的占位符。填不出来的，**就把那句话删掉**，不要瞎写。
4. 时间建议分配：简历 1 天 → STAR 稿 2 天（录音纠正）→ 追问清单 7~10 天（每天刷一个主题，对着镜子讲）→ 演示与作品集 2 天 → 投递。
5. 一句总原则：**面试不是知识竞赛，是「你能不能让我放心把活交给你」的信任游戏**。讲清楚「我遇到什么问题 → 我怎么选 → 为什么这么选 → 代价是什么 → 结果如何」比背出 100 个八股名词有用得多。

## 1. 简历怎么写

### 1.1 位置与篇幅：项目经历放哪、写多少

**结论：一页简历，项目经历放中间偏上，占 40%~50% 篇幅。**

推荐的一页简历版式（从上到下）：

| 区块 | 建议篇幅 | 说明 |
|---|---|---|
| 个人信息 | 2 行 | 姓名、电话、邮箱、GitHub、求职意向、到岗时间（实习写「可实习 3 个月以上，每周 5 天」） |
| 教育背景 | 2 行 | 学校、专业、入学-毕业时间、GPA/排名（前 30% 才写）、相关课程只写 3~4 门核心课 |
| **专业技能** | **4~6 行** | 用「掌握/熟悉/了解」三档分层，别全都写"精通" |
| **项目经历** | **15~20 行（1~2 个项目）** | **校招简历的重心**，`shopping-mall` 放第一个 |
| 实习经历 | 5~8 行 | 有就放项目**之前**（实习 > 项目），没有就删掉这一栏 |
| 竞赛/奖项/证书 | 2~3 行 | 蓝桥杯、ACM、软考、英语等级 |
| 自我评价 | **不写或 1 行** | 99% 的自我评价是废话，占地方还减分 |

**关键判断：**

- **如果你是「无实习 + 一个项目」**：项目经历必须占满 20 行以上，用下面的「详版」；同时把「专业技能」写扎实，因为面试官会把追问火力全压在项目上。
- **如果你是「有实习 + 一个项目」**：项目用「标准版」10 行，实习经历写 8 行，两栏都要有量化数据。实习里做过的事优先展开。
- **别放两个都讲不清的项目**。一个能扛住 40 分钟深挖的项目，远胜三个"商城 + 博客 + 管理系统"。
- 简历**必须一页**（应届生）。超过一页说明你不会取舍，这本身就是减分项。
- 项目名不要写「电商项目」这种名字。写成：**`shopping-mall · B2C 自营商城（单体多模块 + 秒杀高并发）`**，一行就交代了业务、架构、亮点。

```
【三、核心工作】

1. 架构与分层
   拆分为 common / model / dao / service / web 五个 Maven 模块，依赖严格单向
   （web → service → dao → model，common 全层可见），避免 dao 与 service 循环依赖；
   Controller 按端拆成 app（/api/app/**，C 端会员）与 admin（/api/admin/**，管理端）。

   统一约定：主键 bigint 雪花 ID（不暴露业务量、分布式友好）、金额一律 bigint 存「分」、

   购物车 → 下单（校验库存 + 扣减 + 生成订单）→ 自建模拟支付网关支付（契约对标支付宝）→ 支付回调验签 → 发货 → 完成；

   所有流转写 oms_order_operate_history 流水。

   动静分离：秒杀商品信息、活动状态提前预热到 Redis；
   防超卖三层：① Redis + Lua 脚本在服务端原子完成「校验库存 → 校验一人一单 → 扣减」；

      作为最后一道防线，重复请求只会插入失败。
```

### 1.3 逐条讲解：每句话为什么这么写

写项目描述的公式只有一条：

> **动词开头 + 技术方案 + 解决的问题 + 量化结果**

| 要素 | 反例 | 正例 | 为什么 |
|---|---|---|---|
| **动词开头** | 「参与了电商项目的开发」 | 「独立完成 11 个业务模块的设计与开发」 | 面试官 8 秒扫一份简历，第一眼只看动词和名词。动词决定你的角色是"主力"还是"打杂" |
| **技术方案** | 「使用了 Redis」 | 「Redis + Lua 脚本原子预扣，脚本内一次性完成库存校验与扣减」 | 「用了 Redis」是任何人都会写的废话；写出**具体用法**才证明你懂原理 |
| **解决的问题** | 「优化了秒杀性能」 | 「解决 1000 并发下 Redis 预扣成功但 DB 扣减失败导致的少卖」 | 需求—方案—问题的因果链，才是面试官追问时的"钩子"，也是你准备过的战场 |
| **量化结果** | 「性能有明显提升」 | 「QPS 从 420 提升到 3100，TP99 从 850ms 降到 120ms」 | 没有数字的优化等于没做。数字还能帮你把话题引到你熟悉的压测细节 |

**简历上的每一行，都要能立刻回答三个问题**：

1. 这句话里有没有一个**技术名词**能让面试官顺着问下去？（有，且是你准备过的 → 好）
2. 这件事**如果没做会怎样**？说不出来 → 这行是凑数的，删掉。
3. 我能不能**当场给出代码量级**？（比如"秒杀下单链路大概 400 行，核心是 `SeckillServiceImpl#doSeckill` 加一个 Lua 脚本文件"）不能 → 说明这个模块不是你写的，或者你该回去看一眼代码。

**技能栏怎么写**（配套修改，别和项目割裂）：

```
专业技能
· 熟悉 Java 基础与集合、并发（JUC 线程池/AQS/CAS/ThreadLocal）、JVM 内存结构与 GC 调优；
· 熟悉 Spring / Spring Boot 3 核心原理（IOC、AOP、Bean 生命周期、三级缓存、自动装配、事务传播）；
· 熟悉 MySQL 8（InnoDB 索引与 B+ 树、MVCC、间隙锁、执行计划分析、慢 SQL 与深分页优化）；
· 熟悉 Redis 7（缓存三大问题、持久化、内存淘汰、分布式锁），了解 RocketMQ 5（削峰、延迟消息、
  顺序消息、事务消息、消息可靠性）与 Redisson；
· 熟悉 MyBatis-Plus、Maven 多模块、Docker Compose、Nginx、Git，能用 JMeter 做压测并分析瓶颈；
```

注意分层用词：**「熟悉」= 能讲原理、被追问三层不慌；「了解」= 知道概念和适用场景，被深挖会承认边界。** 不要写"精通"，应届生写精通基本等于自曝。

### 1.4 必须自己填的占位符清单 & 怎么压测拿到这些数字

> **红线：以下数字必须在你的机器上真实测出来。** 编造的数字是最容易被拆穿的——面试官只要问一句「你压测用的什么参数、几台机器、瓶颈在哪」，假的就露馅了。

**必须测出来的数字（对照标准版）：**

| 占位符 | 含义 | 怎么测 |
|---|---|---|
| `【__】个业务模块` | 真实完成的模块数 | 数自己写了几个 Service 包 / Controller，别把 Phase 4 没做的算进去 |
| `【__】张表` | 真实建表数 | `SELECT COUNT(*) FROM information_schema.tables WHERE table_schema='shopping_mall'` |
| `QPS 从【__】到【__】` | 优化前后吞吐 | JMeter 阶梯压测，取**稳定段**的平均 TPS，不是峰值瞬间值 |
| `TP99 从【__】ms 到【__】ms` | 优化前后长尾延迟 | JMeter 聚合报告（Aggregate Report）的 99% Line |
| `RT 从【__】ms 降到【__】ms` | 接口响应时间 | 同上，取 Average 或 90% Line 都可以，**注明取的是哪个** |
| `MySQL QPS 下降【__】%` | 缓存/削峰效果 | `SHOW GLOBAL STATUS LIKE 'Questions'` 隔 60 秒取两次差值，或看 MySQL 的 `Com_select` |
| `1000 并发下【__】件商品无超卖` | 正确性验证 | 压测前 `UPDATE wms_stock SET stock = 100`；压测后查 `SELECT stock FROM wms_stock` 与 `SELECT COUNT(*) FROM oms_order`，两者必须对得上 |
| `发现【__】次超卖`（优化前） | 说明真实存在过问题 | 优化前的版本故意压一次，记录 `订单数 - 库存消耗` 的差值 |
| `共【__】次有效压测记录` | 压测轮次 | 数一下你保存的 `.jtl` / 聚合报告截图 |

**JMeter 5 实操步骤（照做就能出数）：**

1. **装并起环境**：被测服务（`shopping-web`）+ MySQL + Redis 全在**同一台机器**上跑 → 记住，**结论里必须注明"单机自测"**，别对外说成"线上环境"。
2. **控制变量**：压测前清缓存（`redis-cli FLUSHDB`）、重启应用、固定库存（`UPDATE wms_stock SET stock = 100 WHERE sku_id = 1`）、把日志级别调到 `INFO`（`DEBUG` 会严重拖慢 QPS）。
3. **用非 GUI 模式**（GUI 只用来编脚本）：

   ```powershell
   # 线程组用 ${__P(threads,100)} 参数化，方便分档
   jmeter -n -t seckill.jmx -l result-100.jtl -e -o report-100 `
          -Jthreads=100 -Jramp=10 -Jloops=50
   ```

   - `-n` 非 GUI，`-t` 脚本，`-l` 原始结果，`-e -o` 生成 HTML 报告。
   - **必须删掉 GUI 里的"查看结果树""聚合报告"监听器**，否则 JMeter 自己先把内存吃满，你测的是 JMeter 不是你的服务。
4. **调 JMeter 自身**：`jmeter.bat` 同一目录的 `jmeter` 脚本里把 `HEAP="-Xms1g -Xmx1g -XX:MaxMetaspaceSize=256m"` 调大；线程数别一上来就 5000，压测机 CPU 先满就没意义了。
5. **分档加压**：100 → 500 → 1000 线程，每档跑 3 分钟以上，**取稳定运行段的数字**。看聚合报告里的 `#Samples / Average / 90% / 95% / 99% / Error% / Throughput`。
6. **压测正确性**（比 QPS 更重要的是这个）：

   ```sql
   -- 压测前后各查一次，必须完全对得上
   SELECT stock FROM wms_stock WHERE sku_id = 1;
   SELECT COUNT(*) FROM oms_order WHERE sku_id = 1 AND create_time > '【压测开始时间】';
   SELECT COUNT(*) FROM sms_seckill_record WHERE activity_id = 【】;   -- 一人一单是否生效
   ```
   **库存 + 已下单数量 = 初始库存**，这才叫"无超卖"。把这条 SQL 的结果截图放进 README，比 QPS 更有说服力。
7. **记录环境**：CPU/内存/磁盘类型、JDK 版本（`java -version`，注意 `00` 号文档里的坑：PATH 上的 `java` 可能是 8，压测前先 `echo %JAVA_HOME%` 确认）、MySQL 与 Redis 的版本和关键参数（`innodb_buffer_pool_size`、`maxmemory`）。**没有环境的性能数据等于没有数据。**
8. **每一轮只改一个变量**：优化前 → 加 Redis 预扣 → 加 MQ 削峰 → 加本地缓存（可选）。三轮数据列成一张表格，面试时直接口述，效果极好：

   | 轮次 | 变更点 | QPS | TP99(ms) | 错误率 | 是否超卖 |
   |---|---|---|---|---|---|
   | 0 | 直连 DB 扣减 | 【】 | 【】 | 【】 | 是（差【】件） |
   | 1 | + Redis+Lua 预扣 | 【】 | 【】 | 【】 | 否 |
   | 2 | + RocketMQ 异步削峰 | 【】 | 【】 | 【】 | 否 |

**没有条件压测怎么办？** 不要写性能数字。可以改成可验证的事实描述：

- 「通过压测定位到 MySQL 行锁竞争是瓶颈，加入 Redis 预扣后错误率从【】% 降到 0」——**错误率/正确性数据**比 QPS 更好测也更好讲。
- 「用 `EXPLAIN` 分析慢 SQL，把 `limit` 深分页改写成延迟关联，`rows` 扫描行数从【】降到【】」——**执行计划里的数字**同样真实可靠。
- 宁可只写 1 个真实数字，也不要写 5 个编的数字。

### 1.5 反面示例对照：5 条"学生味很重"的写法 vs 改写

> 对照原则：**左列是"流水账 / 形容词 / 无结果"，右列是"方案 + 因果 + 数据"。**

**① 流水账式堆功能**

- ❌ 「完成了电商系统的用户模块、商品模块、订单模块、购物车模块、支付模块的开发。」
- ✅ 「独立完成 11 个业务模块、65 张表的设计与开发，覆盖「下单 → 支付 → 超时关单 → 退款」完整交易闭环；订单状态用状态机管理，非法流转在 Service 层直接拦截。」
- **差在哪**：左边像课程设计的分工表，看不出难度和你的判断力；右边给出了**范围、闭环、设计手段**，面试官立刻知道该从"状态机"问起。

**② 只写"用了什么"，不写"为什么用、解决什么"**

- ❌ 「使用了 Redis 缓存、RocketMQ 消息队列、Redisson 分布式锁。」
- ✅ 「针对秒杀瞬时流量，用 Redis+Lua 完成原子预扣挡住 99% 无效请求，再经 RocketMQ 异步削峰后落库，把 MySQL 从【】QPS 的压力降到【】QPS。」
- **差在哪**：左边是技术名词堆砌，等于告诉面试官"我是照着教程搭的"；右边每个组件都**挂在一个具体问题上**，被追问时你有天然的答题顺序。

**③ 形容词代替结果**

- ❌ 「系统性能得到了很大的提升，用户体验良好，代码结构清晰。」
- ✅ 「秒杀接口 TP99 从【】ms 降到【】ms，1000 并发下错误率 0%，无超卖无少卖。」
- **差在哪**：「很大提升」无法被验证也不可追问，面试官只会追问"具体多少"，答不上来就变成负面印象。**形容词在简历上是负资产。**

**④ 把"我参与"写成"我负责"（或反之）**

- ❌ 「负责整个电商系统的架构设计与性能优化，主导技术选型。」
- ✅ 「独立设计并实现秒杀模块（约 400 行核心代码 + 1 个 Lua 脚本），独立完成 MySQL 表结构设计与 JMeter 压测；参考了【RocketMQ 官方文档/某开源项目】的延迟消息用法并做了本地适配。」
- **差在哪**：应届生说"主导架构"没人信，反而引起反感；说清**边界**（哪些是我做的、哪些是参考的）反而显得诚实可信。**敢说边界的人，才被认为"其他部分也是真的"。**

**⑤ 技术栈与业务脱节 / 无意义堆砌**

- ❌ 「采用 Spring Cloud + Nacos + Gateway + Seata 微服务架构，使用 Elasticsearch 做搜索，ShardingSphere 分库分表，Kubernetes 部署，支持千万级并发。」
- ✅ 「评估后**不引入**微服务与分库分表：当前是单机单库、数据量【】万级，引入 Nacos/Seata 只会让调试成本翻倍却无收益；改用**本地消息表 + 最终一致**解决跨模块一致性，用**单体多模块 + 预留 merchant_id**保留向多商户演进的路径。」
- **差在哪**：左边是**主动送人头**——面试官问一句「Seata 的 AT 模式 undo_log 怎么回滚」「分片键怎么选的」就崩了。右边展示的是**架构判断力和取舍能力**，这是校招面试官真正想看的东西（对应 `00` 号文档 ADR-1、ADR-7 和 §4.1）。

## 2. STAR 讲项目模板

> STAR = **S**ituation（背景）→ **T**ask（任务/目标）→ **A**ction（我做了什么）→ **R**esult（结果）。
> 校招面试里，几乎每场都会让你"介绍一下你的项目"，**这句话的答案直接决定后面 30 分钟的走向**。
> 下面两稿请**逐字背下来**，再用自己的话微调。背稿的目的是让你在紧张时也不卡壳，不是让你像念课文——**语速放慢，该停顿的地方停顿，给面试官插话的机会**。

### 2.1 两分钟项目总述口播稿（约 400 字，直接背）

> 【开场，10 秒】
> 我介绍一下我最近做的项目，叫 shopping-mall，是一个 B2C 自营商城，从数据库设计到部署上线都是我一个人做的，代码开源在 GitHub 上。技术栈是 Java 17、Spring Boot 3.2、MyBatis-Plus、MySQL 8、Redis 7 和 RocketMQ 5，架构上我用的是**单体多模块**，没有上微服务。
>
> 【S + T，30 秒】
> 做这个项目的起因是我想找一个能真正讲出"并发数据"的场景。电商的交易链路很完整——商品、购物车、库存、订单、支付、售后都能串起来，而秒杀又能把高并发、缓存、消息队列、分布式锁这些点全部压到一条链路上。所以我的目标是：**先做出一条完整可演示的交易闭环，再把秒杀做到有真实压测数据、且绝对不超卖**。
>
> 【A，60 秒】
> 具体做了三块。第一块是**分层和建表**：拆成 common、model、dao、service、web 五个模块，依赖严格单向；一共 65 张表，金额统一用 bigint 存「分」，主键用雪花 ID，全部带逻辑删除。设计的时候我在商品、订单、库存这六张核心表上预留了 merchant_id，后面要从自营演进成多商户不用改核心表。
> 第二块是**交易闭环**：下单会做库存校验和扣减、生成订单，订单用一个状态机管理流转，每次更新都用"where status 等于期望的旧状态"做 CAS，所有流转都写操作流水；支付这块我**没有对接真实渠道**，而是自建了一个模拟支付网关——真实渠道需要商户资质，但它的异步回调、验签、幂等、重推这些关键行为我都完整模拟了，因为这个模块真正要解决的就是幂等和验签；超时未支付用 RocketMQ 的延迟消息在 30 分钟后自动关单并回滚库存。前端我做了两套：管理后台用 Vue3 + Element Plus，商城前台用 Vue3 + Vant，**只做商品列表、详情、购物车、下单结算 4 页**——这 4 页是刻意选的，正好够走完一条完整的购物动线。
> 第三块是**秒杀**，也是这个项目投入最多的部分。我把防超卖做成了三层：第一层是 Redis 加 Lua 脚本，在服务端原子地完成"校验库存、校验一人一单、扣减"；第二层是 MySQL 的条件更新，`update wms_stock set stock = stock - 1 where sku_id = ? and stock >= 1`，看影响行数是不是 1；第三层是秒杀记录表的唯一索引，作为最后一道防线。预扣成功之后发 RocketMQ 消息异步落库，接口层再用 Redis 加 Lua 自己做了一个令牌桶限流。
>
> 【R，20 秒】
> 效果上，我在本机【__】C【__】G 的环境用 JMeter 非 GUI 模式分档压测：优化前直连数据库，QPS 只有【__】，还出现过超卖；加了 Redis 预扣之后 QPS 到【__】，MySQL 的 QPS 下降【__】%；再加上 MQ 削峰，接口 TP99 从【__】毫秒降到【__】毫秒，1000 并发下库存和订单数完全对得上，没有超卖也没有少卖。
> 我大概先讲这么多，您想深入了解哪一块？

**最后一句话是重点**：它把话语权交回给面试官，同时暗示"我有料可以深聊"。**永远不要一口气讲 10 分钟**。

> **💡 支付模块的诚实说明（话术模板，可直接背）**
>
> 「支付这块我没有对接真实渠道，而是自建了一个模拟网关，因为真实渠道需要商户资质。但我把它的异步回调、验签、幂等、重推这些关键行为都完整模拟了，因为幂等和验签才是这个模块真正要解决的问题。」
>
> **注意**：这句话是**加分项**，不是减分项——它同时展示了三件事：你知道真实渠道需要什么、你知道这个模块的技术内核是什么、你不吹牛。**反过来，如果说成「我对接了支付宝」，面试官一句「商户资质怎么申请的」就能让你当场卡住。**

### 2.2 五分钟技术深度版口播稿（约 1000 字，侧重秒杀链路）

> 使用场景：面试官说"你挑一个最有挑战的模块展开讲讲"，或者你在上一轮提到秒杀后对方说"细说一下"。

> 【定位问题，30 秒】
> 那我重点讲秒杀。秒杀的核心矛盾其实就一句话：**瞬时流量可能是库存的一万倍，但真正需要写数据库的只有库存那么多条**。所以我的整体思路不是"把数据库优化到能扛住百万 QPS"——那不可能——而是**分层过滤，让每一层都比上一层便宜，最后只有极少量请求能摸到数据库**。同时因为 Redis 不是可信存储，我还必须给这条链路配一个补偿和对账机制。
>
> 【第一层：接入与限流，40 秒】
> 请求进来先在 Nginx 做一层 `limit_req` 漏桶限流，这一层挡掉爬虫和明显异常的流量。到应用层，我写了一个 `@RateLimit` 注解，底层是 Redis 加 Lua 实现令牌桶，按 IP 和 userId 两个维度限流，Lua 保证"取令牌 + 判断 + 扣减"是原子的，不会因为并发读写出错。秒杀接口我还单独放了一个线程池做隔离，它和主站的下单、支付线程池是分开的，这样秒杀打满也不会把支付接口拖垮。这一层的作用是：**在业务逻辑之前就把大部分无效流量拒掉**。
>
> 【第二层：Redis 预扣，90 秒】
> 真正的第一道业务防线是 Redis。我在活动开始前把秒杀库存写进 Redis，然后用一个 Lua 脚本做预扣。这个脚本做了三件事：读库存、判断用户有没有下过单、库存大于 0 就扣减并记录用户。为什么必须用 Lua：因为 Redis 执行 Lua 是单线程原子的，一条脚本里做完这三次操作，不会出现"两个请求都读到库存为 1、都扣减"这种超卖。
> 这里有个容易忽略的点：**一人一单的判断也放在 Lua 里**。如果放在 Java 里先查再写，两个并发请求会同时通过检查。我在 Redis 里用 Set 结构存 activity_id 加 userId，脚本里用 `SISMEMBER` 判断、`SADD` 写入。库存数是 Key 的 value，直接 `DECR` 或者 `INCRBY -1`，但**必须在脚本里先判断库存大于 0**，不能只靠 DECR 之后看结果，否则会出现负库存。
> 预扣这一步的性能很高，因为它是纯内存操作，而且 Lua 脚本只有一次网络往返，我实测这一层能挡住绝大部分请求。
>
> 【第三层：DB 条件更新 + 唯一索引，90 秒】
> 预扣成功后，请求会发一条 RocketMQ 消息，消费端再去做真正落库。为什么是异步：因为要削峰，把瞬间的写请求摊平到一段时间里，MySQL 就不会被打穿。消费端落库时有三件事要做：扣库存、创建订单、写库存流水。
> 扣库存这里我用的是条件更新，`update wms_stock set stock = stock - 1 where sku_id = ? and stock >= 1`，然后判断 `affectedRows` 是不是 1。这条 SQL 的好处是：InnoDB 会在 sku_id 这个唯一索引上加行级排他锁，"库存大于等于 1"这个条件在最新已提交的数据上判断，**它本身就是当前读，不会受 MVCC 快照影响**，所以并发下天然安全，不需要我先 `select ... for update` 查一次再更新——那样反而是两次往返，还容易写错。
> 但异步消费意味着消息可能重复投递，RocketMQ 只保证至少一次。所以我在秒杀记录表 `sms_seckill_record` 上建了 `(user_id, activity_id, sku_id)` 的唯一索引，重复插入会直接报 Duplicate Key，我在消费端捕获这个异常当作"已经处理过"返回成功。**唯一索引是最后一道防线，比在 Redis 里做去重更可靠**，因为 Redis 可能丢数据或者 key 过期。
> 另外库存扣减我还写了一条 `wms_stock_log` 流水，用业务流水号做唯一索引，一方面幂等，一方面后面能对账。
>
> 【一致性与兜底，80 秒】
> 这条链路最大的风险是：Redis 预扣成功了，但后面消息丢了、或者数据库扣减失败，就会出现"少卖"——库存被占住了但没生成订单。我的处理是本地消息表：预扣成功的同时，在同一个事务里往 `sys_message` 表写一条待发送记录，发消息和定时重试都以这张表为准，成功之后把状态置为已发送。定时任务用指数退避重试，超过阈值就告警，交给人工对账。这样即使 MQ 挂了、应用重启了，消息也不会丢。
> 如果反过来，DB 扣减失败了，我会把 Redis 的库存加回去，但这个回滚必须幂等，我是按预扣时生成的流水号来做的，同一个流水号只会加回一次。
> 那 Redis 本身挂了呢？我的定位是：**Redis 是加速层，MySQL 是权威数据源**。Redis 挂了，预扣这一层就降级——要么直接限流拒绝，返回"活动太火爆"，要么把流量切成小批量直接走 DB 的条件更新，接受 QPS 大幅下降但不超卖。绝对不能用"Redis 是唯一库存来源"这种设计。
>
> 【结果与反思，30 秒】
> 最后压测的结果是：优化前 QPS【__】，有超卖；加 Redis 预扣后 QPS【__】，MySQL QPS 降了【__】%；再加 MQ 削峰后 TP99 从【__】ms 降到【__】ms，1000 并发下库存和订单完全对得上。
> 如果让我重做，我会把"库存流水 + 对账任务"提到一等公民的位置，因为它才是保证最终正确的最后一道保险；另外我会把 traceId 打通到 MQ 消费端，这样异步链路的排查会容易很多。

### 3.1 秒杀 / 高并发（10 题）

#### Q3.1.1 你怎么防止超卖？

- **面试官想听**：你有没有"多层兜底"的意识，还是只会一个 Redis 就以为万事大吉。
- **参考答案要点**：
  1. **第一层 Redis 预扣**：用 Lua 脚本把「判断库存 > 0 → 判断一人一单 → 扣减库存 → 记录用户」放在一条脚本里，Redis 单线程执行 Lua 是原子的，避免 check-then-act 竞态；**库存判断必须在扣减之前，不能扣完再看结果，否则会出现负库存**。
  2. **第二层 MySQL 条件更新**：`UPDATE wms_stock SET stock = stock - 1 WHERE sku_id = ? AND stock >= 1`，判断 `affectedRows == 1`；InnoDB 在 `sku_id` 唯一索引上加 X 行锁，条件在最新数据上判断（当前读），并发安全。
  3. **第三层唯一索引兜底**：`sms_seckill_record` 建 `uk(user_id, activity_id, sku_id)`，重复请求插不进去，捕获 `DuplicateKeyException` 视为"已抢过"。
  4. **第四层对账**：所有扣减写 `wms_stock_log` 流水，定时任务核对「初始库存 = 剩余库存 + 已扣减流水」，不一致就告警。
  5. 表结构上 `stock` 用 `INT UNSIGNED`（或加 `CHECK (stock >= 0)`）作为最底层的物理约束。
- **常见错误回答**：
  - 「我用 Redis 的 `decr` 保证不超卖」——只说了第一层，且没提库存判断；**追问"Redis 挂了怎么办"就崩了**。
  - 「加个 synchronized 或者分布式锁就不会超卖」——单机 `synchronized` 在集群下无效；给每个 SKU 加分布式锁能把 QPS 打到个位数。
  - 「先 select 查库存，再 update 减一」——经典 check-then-act，两请求都能查到 stock=1。

#### Q3.1.2 Redis 预扣成功了，但 DB 扣减失败怎么办？

- **面试官想听**：你有没有想过"中间态"和"补偿"，还是只画了 happy path。
- **参考答案要点**：
  1. 先明确后果：这是**少卖**（库存被占住但没生成订单），比超卖轻但同样必须修。
  2. **同事务写本地消息表**：预扣成功后在本地事务里往 `sys_message` 写一条「秒杀落库」待处理记录，谁发消息、谁重试都以这张表为准。
  3. **重试**：`@Scheduled` 定时任务扫 `sys_message` 中 `status = 待处理` 且 `next_retry_time <= now()` 的记录，指数退避（如 10s/30s/1m/5m…），超过最大次数置为失败并**告警**。
  4. **幂等回滚**：确认 DB 无法扣减（例如库存已经被别人扣完，理论上不该发生），要把 Redis 库存加回去；回滚必须**按预扣流水号幂等**，同一流水号只回滚一次，可在 Redis 用 `SADD rollback:{activityId} {ticket}` 判断。
  5. **对账兜底**：每日对账任务比对 Redis 库存、`wms_stock`、`sms_seckill_record`、订单数，差异进人工处理队列。
  6. 顺序上强调：**先保证消息一定能发出去（本地消息表），再保证消息能被消费（幂等）**，最后才是对账。
- **常见错误回答**：
  - 「失败了就回滚 Redis」——**只说了结果，没说幂等**；MQ 重试 + 定时补偿同时回滚就是重复加库存，反而超卖。
  - 「不会失败」/「加个 try-catch 就好了」——典型没考虑中间态。
  - 「用 Seata 回滚」——本项目单库单机，引入 Seata 是过度设计（见 `00` §4.1、ADR-7）。

#### Q3.1.3 Redis 挂了怎么办？

- **面试官想听**：你有没有"权威数据源"的概念，会不会把缓存当真相。
- **参考答案要点**：
  1. **定位清晰**：Redis 是加速层/预扣额度层，**MySQL 是权威数据源**。Redis 全挂最坏结果是性能下降，绝不能是数据错误。
  2. **高可用**：生产用哨兵或 Cluster + 主从（本项目本地是单机，但要知道 RDB/AOF 与主从的意义）。注意**主从异步复制 + 主节点宕机可能丢最后一批写**，所以预扣结果不能当成最终事实。
  3. **降级策略**（按优先级）：① 直接快速失败 + 限流，返回「活动太火爆，请稍后再试」，保护 DB；② 小批量放行，走 MySQL 条件更新（`where stock >= 1`）作为唯一防线，同时把应用层限流阈值降到 DB 能承受的量级。
  4. **降级开关**：用 `@ConditionalOnProperty` 或配置中心（本项目用配置文件 + 启动参数）控制秒杀是否走 Redis；降级后要**熔断**，避免请求把线程池和 HikariCP 连接池打满，拖垮主站。
  5. **不要做的事**：不要在 Redis 挂掉时用本地缓存（Caffeine）当库存来源——多实例各自扣减等于必然超卖。
- **常见错误回答**：
  - 「Redis 不会挂」/「上集群就不会挂」——集群也会整体故障，也可能网络分区。
  - 「Redis 挂了就直接查 DB」——没说清 DB 能不能扛、要不要限流，等于把 DB 一起打挂。
  - 「用本地缓存兜底库存」——多实例场景下的严重错误。

#### Q3.1.4 怎么防刷（黄牛/脚本）？

- **面试官想听**：你有没有"安全/风控"视角，而不只是性能视角。
- **参考答案要点**：
  1. **接入层**：Nginx `limit_req`（漏桶）+ `limit_conn` 限制单 IP 连接数；封禁异常 UA、空 Referer、代理 IP 段。
  2. **接口层**：`@RateLimit`（Redis + Lua 令牌桶）按 **IP + userId + 设备指纹** 多维度限流；同一 userId 每秒最多 N 次。
  3. **业务层**：① 秒杀 URL 带**时间戳签名/一次性 token**（活动开始前接口不暴露，防止脚本提前刷）；② 强校验登录态与实名/手机号绑定；③ 下单需要前置动作（答题、滑块验证码），把机器成本抬高；④ `sms_seckill_record` 唯一索引保证**一人一单**（不只是前端置灰按钮）。
  4. **风控**：统计同 IP/同设备的账号数，超过阈值进黑名单（Redis Set，带 TTL）；可疑请求直接返回排队中但**不真正预扣**（蜜罐）。
  5. 强调一句：**前端置灰按钮、倒计时不是防刷**，它只防君子。
- **常见错误回答**：
  - 「前端按钮点了就置灰」——任何脚本都能绕过前端。
  - 「加验证码就行」——只提高成本，不解决刷单；且验证码本身有用户体验和刷验证码接口的成本。
  - 「按用户 ID 限流就够了」——黄牛有大量账号。

#### Q3.1.5 限流怎么做？放在哪几层？

- **面试官想听**：是否理解"分层过滤"，以及限流算法本身。
- **参考答案要点**：
  1. **三层**：Nginx（`limit_req_zone` 漏桶，按 IP）→ 应用层自定义 `@RateLimit`（Redis + Lua **令牌桶**，按 IP/userId/接口）→ 业务层（秒杀接口独立线程池 + HikariCP 连接池上限 + MQ 生产端限流）。
  2. **算法对比**：固定窗口（简单但有临界突刺）、滑动窗口（ZSet 存时间戳，精确但内存大，可分段）、**令牌桶**（允许突发，本项目用这个）、漏桶（恒定速率，Nginx 用这个）。Redis + Lua 保证"取令牌判断扣减"原子。
  3. **分布式限流的关键**：计数必须在 Redis 里，本地 `RateLimiter`（Guava）只能在单机生效，集群下总量会被放大成 N 倍。
  4. **超限后的行为**：秒杀场景**快速失败**（返回业务错误码 + 友好提示）比排队更好，因为用户等 10 秒也没意义；非核心接口可以排队或降级。
  5. **要考虑 Redis 本身**：限流依赖 Redis，Redis 抖动时限流要"失败开放还是失败关闭"——秒杀场景应**失败关闭**（宁可少放流量，不可放开打 DB）。
- **常见错误回答**：
  - 「用 Guava 的 RateLimiter」——单机方案，集群下失效（除非配合网关按实例分片）。
  - 「用 `incr` + `expire` 做固定窗口」——没提 Lua 原子性，也没提两条命令之间可能失败导致 key 永不过期。
  - 「限流用 Sentinel」——本项目技术栈未引入 Sentinel（见 `00` §4），说了就要能解释为什么自己用 Redis + Lua 实现。

#### Q3.1.6 MQ 消息丢了怎么办？

- **面试官想听**：能不能按"生产 → 存储 → 消费"三段拆解，而不是笼统说"消息不会丢"。
- **参考答案要点**：
  1. **生产端**：`RocketMQTemplate` 用**同步发送**并判断 `SendStatus.SEND_OK`，非 OK 要重试（`producer.setRetryTimesWhenSendFailed`）；更稳的是**本地消息表**（`sys_message`）：业务事务里写消息记录 → 定时任务扫描发送 → 成功改状态。这样应用崩溃也不会丢。
  2. **Broker 端**：刷盘策略 `SYNC_FLUSH`（同步刷盘，可靠性高、吞吐下降）vs `ASYNC_FLUSH`（默认）；主从复制 `SYNC_MASTER`（主从同步复制）vs `ASYNC_MASTER`。要求不丢必须两者都同步，代价是 RT 上升。RocketMQ 5 用 DLedger/RAFT 做高可用。
  3. **消费端**：业务处理成功后再返回 `CONSUME_SUCCESS`；失败返回 `RECONSUME_LATER` 进 `%RETRY%{consumerGroup}` 重试队列（默认 16 次，间隔递增），最终进死信队列 `%DLQ%` 并告警。**绝不能"先 ack 再处理"**。
  4. **补充**：不要用 `sendOneWay`（发了不管）；异步发送要处理回调失败；消费端抛异常会被重试，但**重试必须幂等**（见 Q3.1.7），否则一次丢消息变成多次扣库存。
  5. 一句话总结：**端到端不丢 = 生产端有本地消息表兜底 + Broker 同步刷盘/同步复制 + 消费端处理成功才 ack + 死信队列告警**。
- **常见错误回答**：
  - 「RocketMQ 保证消息不丢」——MQ 只保证"存下来的不丢"，生产端发失败、消费端提前 ack 都会丢。
  - 「开事务消息就不会丢」——事务消息解决的是"本地事务与发消息的原子性"，不是全部。
  - 「消费端用一个 `try-catch` 包起来不出异常就不会重试」——那是把消息吃掉，问题更大。

#### Q3.1.7 消息重复了怎么办（怎么保证幂等）？

- **面试官想听**：你知不知道 RocketMQ 只保证 **at-least-once**，以及幂等的落地手段层次。
- **参考答案要点**：
  1. **前提**：任何 MQ 都只能做到至少一次（或至多一次，但会丢），所以**幂等必须由消费端保证**。
  2. **手段（按可靠性排序）**：
     ① **数据库唯一索引（最强兜底）**：`sms_seckill_record` 的 `uk(user_id, activity_id, sku_id)`、`wms_stock_log` 的 `uk(business_no)`；插入冲突即视为已处理。
     ② **状态机 CAS**：`UPDATE oms_order SET status = 已支付 WHERE order_no = ? AND status = 待支付`，`affectedRows = 0` 说明已被处理过。
     ③ **本地消息表状态位**：`sys_message` 用 `status + version` 做乐观锁更新。
     ④ **Redis 去重**：`SETNX msg:{msgId} 1 EX 3600`，处理完再落库；**只能作为前置过滤，不能作为唯一手段**（Redis 可能丢、key 可能过期、并发下处理失败后 key 已存在会导致漏处理）。
  3. **区分"消息 ID 去重"和"业务去重"**：`msgId` 去重只能防"同一条消息重复投递"，防不了"业务上重复下单"。**业务唯一键去重才是根本**（一人一单的本质是业务唯一性）。
  4. 强调：**幂等键要设计成业务键**，比如 `order_no`、`out_trade_no`、`(user_id, activity_id, sku_id)`，不要用自增 ID。
- **常见错误回答**：
  - 「用 Redis 的 `setnx` 就够了」——没提持久化和过期，也没提失败重试时的漏处理。
  - 「RocketMQ 有去重机制」——RocketMQ 不保证不重复。
  - 「消费前先 `select` 一下有没有处理过」——**check-then-act**，并发下两个消费者都能查到"没处理过"。

#### Q3.1.8 如何保证 Redis 与 DB 的数据一致？

- **面试官想听**：能不能区分"缓存一致性"和"库存预扣一致性"两种不同问题。
- **参考答案要点**：
  1. **先分类**，这是最容易出彩的地方：
     - **缓存场景**（商品详情等）：Redis 是 DB 的副本，目标是"最终看起来一致"。
     - **预扣场景**（秒杀库存）：Redis 是"额度"，DB 是"账本"，两者语义不同，靠**对账**而非"双写"保证。
  2. **缓存一致性（Cache Aside）**：**先更新 DB，再删除缓存**（不是更新缓存，避免并发写覆盖）。为什么不先删缓存再更新 DB：并发下会长期脏。**延迟双删**（更新后延迟 500ms 再删一次）只能缓解，不能根治。
  3. **更强的方案**：订阅 binlog（Canal）+ MQ 异步删缓存，保证"DB 提交后再删"，但会引入组件与延迟（本项目未引入，能说出原理即可）。
  4. **预扣一致性**：本地消息表 + 定时重试 + 幂等回滚 + 每日对账任务（见 Q3.1.2）。
  5. **兜底设计**：缓存设置**逻辑过期或较短 TTL**，即使某次没删成功，过期后也能自愈——**"允许短暂不一致 + 有自愈机制"是工程上正确的答案**，别追求强一致。
- **常见错误回答**：
  - 「用事务包住 Redis 和 MySQL 的操作」——两个不同的存储，本地事务管不了 Redis。
  - 「先更新缓存再更新 DB」/「双写」——并发下极易脏数据。
  - 「用 `@Transactional` 保证一致」——同上，事务只覆盖 DB 连接。

#### Q3.1.9 百万请求抢 100 件商品，怎么扛？

- **面试官想听**：量级意识 + 分层过滤的漏斗思维。**这题答"扛住"是错的，正确姿势是"不需要全扛"**。
- **参考答案要点**：
  1. **先算账**：100 件商品，只有 100 个请求需要真正落库；其余 99.99% 的目标是**被便宜地拒掉**。所以要设计一个逐层收敛的漏斗：

     | 层 | 手段 | 剩余量级 |
     |---|---|---|
     | CDN/Nginx | 静态资源、`limit_req` 按 IP 限流、活动未开始直接拒绝 | 10 万级 |
     | 应用前置 | 活动状态本地缓存（Caffeine，秒级刷新）、参数校验、登录态校验 | 万级 |
     | 限流 | Redis+Lua 令牌桶（userId/IP 维度） | 万级 |
     | Redis 预扣 | Lua 原子扣减 + 一人一单 | 百级 |
     | MQ 削峰 | 异步落库，消费者按 DB 能力匀速消费 | 百级 |
     | MySQL | 条件更新 + 唯一索引 | 百级 |
  2. **异步化**：接口不返回下单结果，只返回"排队中 + 排队号"，前端轮询结果接口；这样接口 RT 与落库解耦，用户体验也更好。
  3. **削峰配合**：MQ 消费者并发数要按 DB 承受能力设置，宁可堆积也不要打穿 DB（RocketMQ 落磁盘，堆积不怕）。
  4. **保护主站**：秒杀接口独立线程池 + 独立 HikariCP 连接池，避免次生灾害（秒杀挂了把支付/下单也拖死）。
  5. **容量预估要诚实**：单机 MySQL 写入极限大概几千 TPS，所以压测目标是"验证漏斗有效、验证不超卖"，而不是"证明单机能扛百万"。
- **常见错误回答**：
  - 「加 Redis 就能扛百万」——Redis 单实例也是有上限的（10 万级 QPS 量级），而且没有考虑后续链路。
  - 「用消息队列削峰，MQ 能存几亿条」——存储不是瓶颈，消费端和 DB 才是。
  - 「部署 100 台机器」——校招场景没有这个条件，暴露你对量级无感。

#### Q3.1.10 压测怎么做的？数据从哪来？

- **面试官想听**：**数据是不是真的**，以及你有没有"控制变量、定位瓶颈"的实验素养。
- **参考答案要点**：
  1. **工具与模式**：JMeter 5 **非 GUI 模式**（`jmeter -n -t x.jmx -l r.jtl -e -o report`），线程数用 `${__P(threads)}` 参数化；**必须在 GUI 里删掉"查看结果树/聚合报告"监听器**，否则测的是 JMeter。
  2. **环境要说清**：单机【__】C【__】G、JDK 17、MySQL 8/Redis 7 同机部署；**明确说"压测机和被测服务同机，所以数据偏保守，也说明瓶颈同时包含压测机"**——主动说局限比被拆穿强得多。
  3. **变量控制**：每轮只改一个点（0：直连 DB → 1：+Redis 预扣 → 2：+MQ 削峰）；压测前 `FLUSHDB`、重启应用、固定库存、日志级别 INFO。
  4. **关注指标**：QPS（取稳定段）、TP99/TP95、错误率（**必须为 0，否则错误率高的 QPS 毫无意义**）、CPU/内存、MySQL `Questions`/`Com_update`、连接池活跃数、线程池队列长度。
  5. **正确性验证**：压测后跑对账 SQL（库存 + 订单数 = 初始库存），**这条比 QPS 更重要**。
  6. **定位瓶颈的方法**：自上而下——先看应用 `jstack`（线程都卡在哪）、`jstat -gcutil`（是不是 GC）、再 `SHOW PROCESSLIST`/`SHOW ENGINE INNODB STATUS`（是不是锁等待）、最后 `EXPLAIN` 看 SQL。**能说出"我第一轮压测的错误是 `Too many connections`，说明瓶颈在连接池而不是 CPU"**，比数字本身更能证明你真做过。
- **常见错误回答**：
  - 「用 JMeter 跑了 1 万并发，QPS 十万」——单机绝无可能，一问环境就崩。
  - 「QPS 很高，错误率 30%」——说明已经打穿了，这个 QPS 是无效数据。
  - 「没压测过，我推测性能不错」——那就别在简历上写数字。

### 3.2 MySQL（12 题）

#### Q3.2.1 索引的底层原理是什么？聚簇索引和二级索引有什么区别？

- **面试官想听**：基本功，能不能从"磁盘 IO 次数"的角度解释索引。
- **参考答案要点**：
  1. **索引是数据结构，本质是为了减少磁盘 IO 次数**（一次页读取 = 一次 IO，默认页 16KB）。
  2. **聚簇索引**：InnoDB 的主键索引，**叶子节点直接存整行数据**，数据和索引在同一个 B+ 树里（所以叫"索引组织表"）。没有主键时用唯一非空列，再没有就隐式生成 6 字节 rowid。
  3. **二级索引（辅助索引）**：叶子节点存的是**索引列 + 主键值**，因此查询非索引列需要**回表**（拿主键值再走一次聚簇索引）。
  4. **覆盖索引**：如果查询的列都在二级索引里，就不用回表（`EXPLAIN` 的 `Extra` 显示 `Using index`）——这是最常用的优化手段之一。本项目例：订单列表只查 `order_no, status, amount` 时，可以建 `idx_status_create_time` 之类的组合索引避免回表。
  5. **联合索引的最左前缀**：`(a, b, c)` 相当于按 a 排序、a 相同按 b 排序……所以能用 `a`、`a,b`、`a,b,c`，不能跳过 a 直接用 b。
- **常见错误回答**：
  - 「索引就是 B+ 树，查得快」——没有说清"数据在哪、回表是什么"。
  - 「二级索引叶子存数据行的地址」——那是 MyISAM（存的是行指针），InnoDB 存的是主键值。
  - 「索引越多越好」——写放大、占空间、优化器可能选错索引。

#### Q3.2.2 为什么用 B+ 树，不用 B 树、哈希、红黑树？

- **面试官想听**：横向对比能力，而不是背"B+ 树矮"。
- **参考答案要点**：
  1. **vs 二叉/红黑树**：树高太高（千万行 ≈ 20+ 层），每层一次磁盘 IO，无法接受。
  2. **vs B 树**：B 树的**非叶子节点也存数据**，导致单个节点能放的 key 少 → 扇出小 → 树更高；且 B 树叶子节点不相连，范围查询要中序遍历回跳。
  3. **B+ 树的优势**：① 非叶子只存 key（+ 指针），扇出极大，**3~4 层可支撑千万级数据**（第一层常驻内存，实际只需要 2~3 次 IO）；② 所有数据都在叶子且**叶子之间用双向链表连接**，范围查询/排序/`between` 只需顺序扫描；③ 查询性能稳定（每次都走到叶子）。
  4. **vs 哈希索引**：等值查询 O(1) 但**不支持范围查询、排序、最左前缀**；InnoDB 有"自适应哈希索引"（AHI）做热页加速，是内部的、不可控。
  5. 补充：MySQL 8 的 `EXPLAIN` 中 `type` 从优到劣：`system > const > eq_ref > ref > range > index > ALL`，`ALL` 就是全表扫描。
- **常见错误回答**：
  - 「B+ 树查询时间复杂度是 O(1)」——是 O(log n)，树高决定 IO 次数。
  - 「因为 B+ 树是平衡树」——B 树也平衡，这不是区别点。

#### Q3.2.3 索引失效的场景有哪些？

- **面试官想听**：能不能结合实际 SQL 说，而不是背列表。
- **参考答案要点**：
  1. **对索引列做运算/函数**：`WHERE DATE(create_time) = '2025-01-01'`、`WHERE amount + 1 = 100` → 改成范围查询 `create_time >= '2025-01-01' AND create_time < '2025-01-02'`。
  2. **隐式类型转换**：`user_id` 是 `varchar` 却传数字 `WHERE user_id = 123` → MySQL 把列转成数字，索引失效；反之列是 `bigint` 传字符串则通常仍可用（是常量转列类型）。**记住结论：varchar 列传数字会失效**。
  3. **前导模糊**：`LIKE '%abc'`、`LIKE '%abc%'` 失效（`LIKE 'abc%'` 可用，可用范围扫描）。
  4. **违反最左前缀**：联合索引 `(a, b, c)`，`WHERE b = ? AND c = ?` 用不上；但 `WHERE a = ? AND c = ?` 能用上 a（c 用不上，MySQL 5.6+ 有**索引下推 ICP** 在存储引擎层过滤 c，减少回表但**不减少扫描范围**）。
  5. **OR 连接非索引列**：`WHERE a = 1 OR b = 2`，b 无索引则整体走全表（可用 `UNION ALL` 改写）。
  6. **范围查询右侧失效**：`WHERE a > ? AND b = ?` 中 b 用不上（ICP 可部分缓解）；`WHERE a = ? AND b > ? AND c = ?` 中 c 用不上。
  7. **`!=` / `NOT IN` / `IS NOT NULL`**：优化器可能判断全表扫描更便宜而放弃索引（不是绝对失效）。
  8. **`ORDER BY` 与索引顺序不一致 / 排序方向不同**（`ORDER BY a ASC, b DESC` 在 MySQL 8 可用降序索引 `DESC` 解决）。
  9. **优化器成本判断**：即使索引可用，若**区分度太低**（如 `status` 只有 0/1 且各占 50%），回表成本高于全表扫描，优化器会主动放弃索引——**这不是"失效"，是"选择不划算"**。
  10. **验证方式**：用 `EXPLAIN` 看 `key`（实际用的索引）、`rows`（预估扫描行数）、`filtered`、`Extra`（`Using index` / `Using filesort` / `Using temporary`）；MySQL 8.0.18+ 用 `EXPLAIN ANALYZE` 看真实耗时。
- **常见错误回答**：
  - 只说"函数、类型转换、like %"，不说怎么验证和怎么改写。
  - 「只要建了索引就一定会用」/「`!=` 一定失效」——过于绝对，缺少"优化器成本"这一层。

#### Q3.2.4 MySQL 的事务隔离级别有哪些？默认是哪个？

- **面试官想听**：能否把隔离级别、解决的问题（脏读/不可重复读/幻读）和实现手段（MVCC/锁）串起来。
- **参考答案要点**：
  1. **四个级别**：读未提交（RU）、读已提交（RC）、**可重复读（RR，MySQL 默认）**、串行化（Serializable）。
  2. **解决的问题**：RU 有脏读；RC 解决脏读、有不可重复读和幻读；RR 解决不可重复读（加上 Next-Key Lock 在**当前读**下也防幻读）；串行化全解决但并发最差。
  3. **实现**：RC/RR 靠 **MVCC + ReadView**；RR 下还有 **Next-Key Lock（记录锁 + 间隙锁）** 用于当前读防幻读。
  4. **RC 与 RR 的核心区别**：RC **每条语句**都生成新的 ReadView，所以同一事务两次查询可能看到不同结果；RR **只在第一次快照读时生成 ReadView 并复用**，所以可重复读。
  5. **RR 下幻读仍然可能的例外**：先快照读、再当前读（`for update`）会看到别的事务新插入的行——这就是常被追问的"RR 到底能不能防幻读"：**快照读靠 MVCC，当前读靠间隙锁**。
  6. **实践取舍**：互联网业务很多公司把默认改成 RC（减少间隙锁、降低死锁概率、提升并发），靠业务层保证一致性；本项目用默认 RR，因为秒杀依赖行锁语义且并发量在校招可控范围。
- **常见错误回答**：
  - 「RR 完全不会幻读」——漏了"当前读"这个前提。
  - 「隔离级别是用锁实现的」——RC/RR 的主要手段是 MVCC。

#### Q3.2.5 讲一下 MVCC 的实现原理。

- **面试官想听**：能不能把隐藏列、undo log 版本链、ReadView 可见性判断讲全。
- **参考答案要点**：
  1. **三个组件**：隐藏列（`DB_TRX_ID` 最近修改的事务 ID、`DB_ROLL_PTR` 回滚指针、`DB_ROW_ID`）+ **undo log 版本链** + **ReadView**。
  2. **版本链**：每次更新都会把旧版本写进 undo log，`DB_ROLL_PTR` 串成链表，形成该行的历史版本。
  3. **ReadView 四个字段**：`m_ids`（活跃事务 ID 列表）、`min_trx_id`（活跃最小）、`max_trx_id`（下一个要分配的事务 ID）、`creator_trx_id`（当前事务）。
  4. **可见性判断**（拿到版本链上某个版本的 trx_id）：`trx_id < min_trx_id` → 可见（已提交）；`trx_id >= max_trx_id` → 不可见（ReadView 之后才开启）；在 `[min, max)` 之间：如果**在 m_ids 中**说明事务还活跃 → 不可见，**不在 m_ids 中** → 可见（已提交）。不可见就顺着 `DB_ROLL_PTR` 找上一个版本，直到找到可见版本或链表结束（此时用 `DB_TRX_ID` 判断回退到最早版本）。
  5. **RC vs RR 的差异就在 ReadView 的生成时机**（见 Q3.2.4）。
  6. **只有"快照读"（普通 SELECT）走 MVCC**；`SELECT ... FOR UPDATE`、`UPDATE`、`DELETE` 是**当前读**，读最新已提交数据并加锁。
  7. **undo log 何时删**：没有比它更早的 ReadView 引用时可以 purge（由后台 purge 线程做）；**长事务会导致 undo 无法清理、版本链过长、回滚段膨胀**——这是"事务要短"的一个硬理由。
- **常见错误回答**：
  - 「MVCC 是 copy 一份数据给每个事务」——是版本链 + 指针，不是复制。
  - 「MVCC 解决了幻读」——只解决快照读。
  - 说不清 `m_ids` 的作用。

#### Q3.2.6 间隙锁是什么？什么时候会加？

- **面试官想听**：知不知道间隙锁的触发条件与危害（死锁、锁范围扩大）。
- **参考答案要点**：
  1. **定义**：间隙锁（Gap Lock）锁的是**两个索引记录之间的开区间**（以及第一个记录前、最后一个记录后），目的是阻止其他事务在区间内插入，从而防幻读。**间隙锁之间不互斥**（都是"阻止插入"），只有插入意向锁（Insert Intention Lock）会与它们互斥。
  2. **Next-Key Lock** = 记录锁 + 该记录之前的间隙锁（左开右闭区间），RR 下加锁的基本单位。
  3. **退化规则（重点）**：在**唯一索引**上做**等值查询且记录存在** → Next-Key Lock 退化为**记录锁**（不加间隙）；等值查询**记录不存在** → 退化为**间隙锁**；范围查询 → 用 Next-Key Lock。
  4. **危害**：① 锁范围大，并发插入被阻塞；② **极易死锁**（两个事务各持一个间隙锁，再各自插入对方区间等待）；③ 在**非唯一索引/无索引**的列上做 `for update` 或 `update`，会锁住大量间隙甚至全表（无索引更新 = 锁所有扫描到的行 → 近似表锁）。
  5. **实践建议**：秒杀/下单这类高并发写，**WHERE 条件一定走唯一索引等值查询**（如 `sku_id`），避免间隙锁；把隔离级别降到 RC 也能消除大部分间隙锁（RC 下只有外键和唯一键冲突检查会加间隙锁）。
  6. **观察方式**：`SHOW ENGINE INNODB STATUS` 的 `LATEST DETECTED DEADLOCK` 段落能看到双方持锁与等待锁的详细信息。
- **常见错误回答**：
  - 「间隙锁是锁一条不存在的记录」——它锁的是区间，不是一个记录。
  - 「间隙锁会互相阻塞」——间隙锁之间兼容，是插入意向锁与之冲突。
  - 「MySQL 只在 RR 下加锁」——RC 也会加行锁，只是不加间隙锁。

#### Q3.2.7 行锁竞争（锁等待/死锁）怎么排查和优化？

- **面试官想听**：有没有实战排查路径，以及本项目里具体怎么降低竞争。
- **参考答案要点**：
  1. **现象**：接口 RT 抖动、`innodb_row_lock_waits`、`innodb_row_lock_time` 上升、出现 `Lock wait timeout exceeded (1205)` 或 `Deadlock found (1213)`。
  2. **排查步骤**：`SHOW ENGINE INNODB STATUS` 看 `LATEST DETECTED DEADLOCK` 和 `TRANSACTIONS` 段（谁在等谁的什么锁）→ `SHOW PROCESSLIST` / `information_schema.INNODB_TRX` 看长事务 → 业务日志 + traceId 定位到具体 SQL。
  3. **常见成因**：① 更新条件没走索引 → 锁住大量行；② **加锁顺序不一致**（两个事务分别先更 A 再更 B）→ 交叉死锁；③ 大事务（事务里做了 RPC、发了 MQ、循环更新上千行）；④ 间隙锁（见 Q3.2.6）；⑤ 唯一索引冲突插入也会互相等待。
  4. **优化手段**：
     - **缩小事务范围**：只包住 DB 写操作，RPC/MQ 放到事务提交后（`TransactionSynchronizationManager.registerSynchronization` 的 `afterCommit`）。
     - **统一加锁顺序**：多 SKU 订单按 `sku_id` **排序后**再依次扣减。
     - **把竞争前置到 Redis**：秒杀用 Redis 预扣把 DB 行锁竞争从"万级并发抢一行"降到"库存数量级的串行扣减"——**这是本项目最核心的优化**。
     - 合理设置 `innodb_lock_wait_timeout`（默认 50s 太长，可降到 5~10s 快速失败），并让应用层重试。
     - 用 `INSERT ... ON DUPLICATE KEY UPDATE` 或乐观锁（version 字段）替代悲观锁。
  5. **别忘了**：死锁是正常现象，MySQL 会自动回滚代价小的事务；应用只需捕获 `DeadlockLoserDataAccessException` 并**有限次重试**。
- **常见错误回答**：
  - 「加个 `synchronized` 就不会死锁」——单机且只保护单个 JVM，跨实例无效，还会拖慢 RT。
  - 「把 `innodb_lock_wait_timeout` 调大」——那是掩盖问题，会让 RT 更差。
  - 只会说"加索引"，说不出加锁顺序和事务拆分。

#### Q3.2.8 慢 SQL 怎么排查？

- **面试官想听**：完整的工具链和优化闭环，而不是"加索引"。
- **参考答案要点**：
  1. **先定位**，按顺序：
     - MySQL 侧：`slow_query_log = ON`、`long_query_time = 1`、`log_queries_not_using_indexes = ON`，用 `mysqldumpslow` 或 `pt-query-digest` 聚合分析；项目里我在 Logback 配了慢 SQL 打印（MyBatis-Plus 性能拦截器 / p6spy），超过 500ms 打 WARN 并带上 traceId。
     - 实时：`SHOW PROCESSLIST`（看是否被锁住）、`performance_schema`、MySQL 8 的 `sys.schema` 视图。
  2. **再分析**：`EXPLAIN` 看 `type`（有没有 `ALL`）、`key`、`rows`、`filtered`、`Extra`；MySQL 8.0.18+ 用 **`EXPLAIN ANALYZE`** 看真实执行耗时（不是估算）；`SHOW PROFILE`（已 deprecated）看各阶段耗时。
  3. **常见病与药**：

     | 症状（Extra） | 病因 | 药 |
     |---|---|---|
     | `Using filesort` | 排序用不上索引 | 建覆盖排序的联合索引，或减少排序字段 |
     | `Using temporary` | `GROUP BY`/`DISTINCT` 无合适索引 | 建索引、改写 SQL |
     | `Using join buffer` | 被驱动表无索引 | 给关联列加索引 |
     | `type: ALL` + `rows` 巨大 | 缺索引/索引失效 | 加索引、改写条件、避免 `select *` |
     | 扫描行数不多但慢 | 回表多、锁等待、网络 | 覆盖索引、拆分、检查锁 |
  4. **其他优化**：分批处理（大 `update`/`delete` 拆成多次小批，避免大事务和锁范围过大）、避免在 SQL 里做计算、用 `IN` 代替多个 `OR`、冷热数据归档。
  5. 强调闭环：**定位 → EXPLAIN → 改 SQL/索引 → 再压测验证 → 记录优化前后数据**，本项目把每次优化的 `rows` 变化记在了 README 里。
- **常见错误回答**：
  - 「加索引就快了」——有些慢是锁等待/回表/网络，加索引无效。
  - 「用 `SHOW PROFILE`」——要注意它已被标记废弃（MySQL 8 仍在但推荐 performance_schema），能提 `EXPLAIN ANALYZE` 更加分。

#### Q3.2.9 深分页怎么优化？

- **面试官想听**：知不知道 `limit 1000000, 10` 的真实代价。
- **参考答案要点**：
  1. **代价**：`LIMIT offset, n` 会**先扫描并回表 offset + n 行，然后丢弃前 offset 行**。`limit 1000000, 10` 意味着 100 万次回表，越翻越慢。
  2. **方案一：延迟关联（子查询先取主键）**
     ```sql
     SELECT o.* FROM oms_order o
     JOIN (SELECT id FROM oms_order WHERE user_id = ? ORDER BY id DESC LIMIT 1000000, 10) t
       ON o.id = t.id;
     ```
     子查询走覆盖索引（只扫主键，不回表），再把 10 个 id 回表。
  3. **方案二：游标 / seek method（订单类最推荐）**
     ```sql
     SELECT * FROM oms_order WHERE user_id = ? AND id < 【上一页最后一个id】 ORDER BY id DESC LIMIT 10;
     ```
     用 `id > last_id` 把 offset 变成 `range` 查询，**性能与页码无关，恒定为 O(n)**。代价是不能跳页，适合"下拉加载"和订单流水。
  4. **方案三：业务限制**。禁止翻到 100 页以后（京东/淘宝都限制页数），或者只允许按时间范围 + 游标翻页。
  5. **方案四：覆盖索引 + 只查需要的列**，避免 `select *` 导致大量回表。
  6. **本项目实践**：管理端订单列表用延迟关联（要支持跳页）；C 端"我的订单"用游标分页（`last_id`）。
  7. 补充：`count(*)` 深分页时的全表统计也很贵，可以缓存总数或用近似值。
- **常见错误回答**：
  - 「加索引就好了」——索引已经在 `id` 上，`offset` 的扫描丢弃成本消不掉。
  - 「用 `limit` 加 `between` 但不知道上一页的值」——那就落入方案一的范畴，要分清楚。

#### Q3.2.10 `update ... where stock >= 1` 这条 SQL 的原理是什么？为什么能防超卖？

- **面试官想听**：**这是本项目的核心 SQL**，必须讲透，尤其是"当前读 + 行锁 + affectedRows 判断"。
- **参考答案要点**：
  1. **语句**：`UPDATE wms_stock SET stock = stock - 1, update_time = NOW() WHERE sku_id = ? AND stock >= 1`。
  2. **为什么安全**：
     - `UPDATE` 是**当前读**，读取的是**最新已提交版本**，不受本事务 MVCC 快照影响，所以不会"读到旧库存然后减出负数"。
     - InnoDB 在 `sku_id`（**唯一索引**）等值命中时加 **X 记录锁**，同一 SKU 的并发更新被串行化。
     - 条件 `stock >= 1` 在锁定后基于最新值判断，MySQL 在 server 层过滤后返回 `affectedRows`：**1 表示扣减成功，0 表示库存不足或行不存在**。应用只认 `affectedRows == 1`，天然防止"先查后减"的竞态。
  3. **为什么不用 `SELECT ... FOR UPDATE` + `UPDATE`**：多一次网络往返；必须自己写判断逻辑容易出错；且如果先用快照读查、再更新，逻辑就错了。**一条条件更新就够了**。
  4. **注意事项（易错点）**：
     - 事务必须短，锁在提交时释放；`update` 后面连着 RPC/MQ 会把锁持有时间拉长。
     - **不要在 `stock` 上再建索引**，也不要在 `WHERE` 里加无法走索引的条件（比如 `AND status = 1` 而 status 无索引），否则会扩大锁范围。
     - 记得 `stock` 列加非负约束（`INT UNSIGNED`）作最后一道物理防线。
     - 若业务是"锁定库存 + 后续扣减"，要区分**锁定（stock_locked）**和**可用库存（stock_available）**，用 `WHERE stock_available >= n` 更新两列。
  5. 本项目里它的位置：**第二层防线**（第一层 Redis 预扣、第三层唯一索引），由 MQ 消费者调用。
- **常见错误回答**：
  - 「先 `select stock`，如果大于 0 就 `update stock = stock - 1`」——check-then-act，必然超卖。
  - 「靠 `synchronized` 或 Redis 锁保证」——DB 层没有兜底，Redis 一旦丢数据就完蛋。
  - 「因为加了事务所以不会超卖」——事务只保证原子性，**默认 RR 下两个事务同时读到 stock=1 依然都会去减**（除非走当前读+行锁）。

#### Q3.2.11 逻辑删除和唯一索引冲突怎么解决？

- **面试官想听**：有没有踩过这个坑（相对冷门，答出来很加分）。
- **参考答案要点**：
  1. **问题**：项目里 `ums_user.username` 建了唯一索引，用户注销后 `deleted = 1`，此时再注册同名账号 → `Duplicate entry`，因为**唯一索引不看 `deleted`，已逻辑删除的行仍然占着这个值**。
  2. **方案 A（可用但受限）**：联合唯一索引 `uk_username_deleted(username, deleted)`。因为 `deleted` 只有 0/1，**同一 username 只能保留一条已删除记录**，删第二条就冲突。
  3. **方案 B（推荐，本项目采用）**：把 `deleted` 从 `tinyint` 改成 `bigint`，**删除时写入删除时的时间戳或删除行自身的雪花主键**（`UPDATE ... SET deleted = 【id 或 当前毫秒】`），配合 `uk(username, deleted)`。因为每条记录的 `deleted` 值都不同，等于"逻辑删除后自动腾出唯一键"，可以无限次删除重建。
  4. **方案 C**：真删除 + 归档表（历史数据移到 `xxx_archive`），主表保持干净的唯一约束。适合对历史数据查询要求低的场景。
  5. **方案 D**：MySQL 不支持 PostgreSQL 那种部分索引（`WHERE deleted = 0`），所以只能靠上面几种。
  6. **落地细节**：MyBatis-Plus 的 `@TableLogic` 默认只支持固定值（`logic-delete-value: 1`），要用方案 B 需要**自定义 SQL 或用 `@TableLogic(delval = "NOW()")` 类写法/自己写 UpdateWrapper**，同时查询条件仍是 `deleted = 0`，所以要注意"逻辑删除标记的取值域"和"未删除的判定条件"不再对称——本项目是在需要唯一约束的几张表（`ums_user`、`pms_brand` 等）上单独处理，并把这个取舍写进了设计文档。
  7. 顺便答一句：**唯一索引和逻辑删除冲突的本质是"唯一约束的语义"与"逻辑删除的语义"打架**，要么让删除后的值不唯一，要么让唯一键带上删除标记。
- **常见错误回答**：
  - 「用物理删除不就行了」——那就丢掉了逻辑删除的可追溯性，且 `ADR-8` 已经定了逻辑删除。
  - 「查重的时候加 `deleted = 0`」——查询能过，插入依然会撞唯一索引，**根本没解决问题**。
  - 不知道 MySQL 不支持部分索引。

#### Q3.2.12 为什么金额用 bigint 存分，不用 decimal 或 double？

- **面试官想听**：ADR-3 的取舍，能否说清"精度"和"工程成本"两面。
- **参考答案要点**：
  1. **double/float 绝对不行**：IEEE 754 二进制浮点无法精确表示 0.1、0.2 这类十进制小数，`0.1 + 0.2 != 0.3`，金额累加/对账必然出现误差。
  2. **decimal 正确但有成本**：MySQL `DECIMAL(18,2)` 是精确十进制，DB 侧没问题；但**Java 侧要用 `BigDecimal`**，`BigDecimal` 是不可变对象、比较必须用 `compareTo` 而不是 `==`/`equals`（`equals` 会比较 scale，`1.0` 与 `1.00` 不等）、运算要指定舍入模式（`HALF_UP`）、序列化/反序列化容易踩坑，代码里到处是 `BigDecimal` 会明显增加出错概率。
  3. **bigint 存分（本项目方案）**：① 整数运算无精度问题；② `long` 表示范围 ±9.2×10^18 分 ≈ 9.2×10^16 元，够用；③ 索引和比较更快、占用更小（8 字节定长）；④ Java 侧就是 `Long`，简单直接。
  4. **必须配套的规范**：① 字段命名带单位，如 `pay_amount` 注释写明"单位：分"；② **前端展示时统一除以 100**，且只在一处转换（VO 层）；③ 除法/分摊要用统一的舍入规则（本项目用 `HALF_UP`）并把差额调整到最后一项，避免"分账后总额对不上"；④ 涉及汇率/多币种要额外存币种字段。
  5. 一句收尾：**"分"方案的代价是每次展示都要转，收益是彻底消灭浮点误差和 BigDecimal 的心智负担**——这是典型的工程取舍。
- **常见错误回答**：
  - 「用 decimal 也可以」但说不出为什么最终选 bigint —— 要能给出 Java 侧的取舍理由。
  - 「用 double 但保留两位小数」——错误只是被隐藏，没有消失。

### 3.3 Redis（10 题）

#### Q3.3.1 缓存穿透、击穿、雪崩分别是什么？怎么解决？

- **面试官想听**：三个概念能不能区分清楚（很多人把击穿和雪崩讲反），以及方案的代价。
- **参考答案要点**：

  | 问题 | 定义 | 解决方案 | 代价 |
  |---|---|---|---|
  | **穿透** | 查**根本不存在**的数据，缓存永远不命中，请求全打到 DB | ① 缓存空值（`null` 也写 Redis，TTL 短，如 30~60s）；② **布隆过滤器**在入口拦截（Redisson `RBloomFilter`，基于位数组 + 多次 hash，**有误判率、不支持删除**）；③ 入参校验 + 限流 | 空值占内存；布隆过滤器需要预热、不能删元素（可用计数布隆/Cuckoo Filter 解决） |
  | **击穿** | **单个热点 key** 过期瞬间，大量并发请求同时打到 DB | ① **互斥锁重建**（Redisson 锁 / `SETNX`，只有一个线程查 DB 并回填，其他线程等待或快速失败）；② **逻辑过期**（value 里不设 Redis TTL，而是存一个逻辑过期时间，过期后异步线程重建，旧值继续服务）；③ 热点 key **永不过期** + 后台定时刷新 | 互斥锁会降低吞吐、有锁等待；逻辑过期会短暂返回旧数据 |
  | **雪崩** | **大量 key 同时过期**或 **Redis 整体宕机**，请求一起打向 DB | ① 过期时间加**随机扰动**（`base + random`）；② **多级缓存**（Caffeine 本地 + Redis + DB）；③ 限流降级 + 熔断（此时**返回兜底数据或友好错误**比打挂 DB 好）；④ Redis 高可用（哨兵/Cluster）；⑤ 活动前**缓存预热** | 多级缓存有一致性成本（本地缓存要设短 TTL 或依赖 MQ 广播失效） |

  4. 本项目落地：商品详情用「缓存空值 + TTL 随机化 + 逻辑过期」，秒杀活动信息**提前预热**（活动开始前 5 分钟写 Redis）并设置与活动结束时间对齐的 TTL。
- **常见错误回答**：
  - 把击穿和雪崩讲反（击穿是**单个热点 key**，雪崩是**大面积**）。
  - 「加个布隆过滤器就能解决穿透」——没说误判率、不支持删除、要预热。
  - 「热点 key 永不过期」但没说怎么更新（必须有后台刷新，否则数据永远脏）。

#### Q3.3.2 RDB 和 AOF 的区别？怎么选？

- **面试官想听**：持久化机制、数据安全边界、重启时的加载顺序。
- **参考答案要点**：
  1. **RDB（快照）**：某个时间点的全量二进制快照。触发方式 `save`（阻塞）/`bgsave`（`fork` 子进程 + 写时复制 COW）；配置 `save 900 1` 等。**优点**：文件紧凑、恢复速度快（加载即重建）。**缺点**：`fork` 时内存翻倍风险（COW 写时复制，写入量大时内存峰值高）、**会丢最后一次快照之后的数据**。
  2. **AOF（追加日志）**：把写命令按 RESP 协议追加到文件。`appendfsync` 三档：`always`（每条都刷盘，最安全、最慢）、`everysec`（每秒刷，**默认，最多丢 1 秒**）、`no`（交给内核，可能丢更多）。**优点**：数据更安全。**缺点**：文件大、恢复慢（要重放命令）。
  3. **AOF 重写**：`BGREWRITEAOF` 通过 `fork` 子进程，用当前数据状态生成最小命令集，解决文件膨胀；重写期间新命令写入 `aof_rewrite_buf` 再合并。
  4. **混合持久化（Redis 4.0+）**：`aof-use-rdb-preamble yes`，AOF 文件前半部分是 RDB 格式的全量、后半部分是增量命令，**兼顾恢复速度和安全性**，Redis 7 默认开启。
  5. **加载顺序**：重启时**优先加载 AOF**（因为更完整），AOF 关闭时才用 RDB。
  6. **本项目取舍**：本地单机用**默认的 RDB + AOF everysec**；但要清楚——在本项目里 Redis 存的是**秒杀预扣额度**，它**不是权威数据**，真正的兜底是 `wms_stock` + 库存流水 + 对账任务。所以**不能只靠持久化解决一致性问题**。
  7. 加分点：主从架构下建议**只在从节点开持久化**（避免主节点 fork 造成卡顿）。
- **常见错误回答**：
  - 「AOF 不会丢数据」——`everysec` 会丢最多 1 秒。
  - 「RDB 和 AOF 不能同时开」——可以且推荐同时开。
  - 不知道重启时的加载优先级。

#### Q3.3.3 Redis 的过期删除策略和内存淘汰策略是什么？

- **面试官想听**：知不知道"惰性 + 定期"组合，以及淘汰策略的适用场景。
- **参考答案要点**：
  1. **过期删除（两部分配合）**：
     - **惰性删除**：访问 key 时才判断是否过期，过期就删并返回 nil。**缺点**：不访问就永远不删，占内存。
     - **定期删除**：每 100ms 随机抽取 20 个设置了 TTL 的 key，删掉过期的；**若过期比例 > 25%，立刻再抽一轮**（`ACTIVE_EXPIRE_CYCLE_FAST`），避免过期 key 长时间堆积。
  2. **内存淘汰**：当 `used_memory` 达到 `maxmemory` 时按 `maxmemory-policy` 淘汰：

     | 策略 | 范围 | 说明 |
     |---|---|---|
     | `noeviction` | — | 默认，写命令直接报错（读可用） |
     | `allkeys-lru` / `volatile-lru` | 全部 / 仅带 TTL | 近似 LRU：**采样（默认 5 个）+ 24 位时钟**，不是精确 LRU |
     | `allkeys-lfu` / `volatile-lfu` | 全部 / 仅带 TTL | 按访问频率（8 位 logc 计数 + 衰减 ldt），**适合热点稳定的缓存** |
     | `allkeys-random` / `volatile-random` | 全部 / 仅带 TTL | 随机 |
     | `volatile-ttl` | 仅带 TTL | 优先淘汰剩余 TTL 短的 |
  3. **本项目配置**：缓存类业务用 `allkeys-lfu`（热点商品、秒杀商品详情访问频次差异极大，LFU 比 LRU 更合适）；**永远不要用 `noeviction` 跑缓存**（会直接报错 `OOM command not allowed`）。
  4. **注意点**：如果 `volatile-*` 策略但 key 都没设 TTL，则等价于 `noeviction`；`maxmemory` 要留出约 25%~50% 余量，因为**主从复制缓冲区和 AOF 重写缓冲区不计入 `maxmemory`**，可能导致实际内存超限被 OOM Killer 杀掉。
- **常见错误回答**：
  - 「Redis 是定时删除 / 到点就删」——单线程做精确定时删除成本极高。
  - 只说 LRU，不知道 Redis 是近似 LRU，也不知道 LFU 的存在。
  - 「淘汰策略选 noeviction 最安全」——缓存场景下会导致写入报错。

#### Q3.3.4 Redis 分布式锁怎么实现？手写 SETNX 有什么坑？

- **面试官想听**：从简单实现到工程化实现的演进，以及每个坑对应的解法。
- **参考答案要点**：
  1. **手写版本**：
     ```
     加锁：SET lock:key <唯一value> NX PX 30000     -- 一条命令，保证原子
     解锁：Lua 脚本 —— if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end
     ```
  2. **四个坑（必须能说出来）**：
     - **① 忘了设过期时间 → 死锁**：进程崩溃锁不释放。所以必须 `PX`。
     - **② 误删别人的锁**：A 超时释放了锁，B 拿到锁，A 执行完把 B 的锁删了 → 所以 value 要放**唯一标识（UUID + 线程 ID）**，解锁用 **Lua 比较后删除**，保证"判断 + 删除"原子。
     - **③ 业务执行超过锁过期时间 → 锁提前失效、并发进入**：手写版本无解，必须靠**续期（看门狗）**或人工估时（不可靠）。
     - **④ 不可重入**：同一线程重复加锁会自己把自己挡住（或者需要自己维护计数）。
  3. **其他**：`SETNX + EXPIRE` 两条命令不是原子的（中间崩溃就没有 TTL），必须用 `SET NX PX` 一条命令；主从异步复制下**主节点宕机可能丢锁**（Redlock 试图解决，但 Martin Kleppmann 对其有经典质疑，要知道这个争议点）。
  4. **结论**：正因为有这些坑，本项目直接用 **Redisson**（见 Q3.3.5）。
- **常见错误回答**：
  - `if (setnx(key)) { expire(key, 30); }` 分开两条命令。
  - 解锁直接 `del(key)`。
  - 「用 `synchronized` 就够了」——集群下无效。

#### Q3.3.5 Redisson 的锁和手写 SETNX 有什么区别？看门狗是什么？

- **面试官想听**：这是最容易被追问的"你是不是真的用过 Redisson"。必须讲出 4 个以上差异点。
- **参考答案要点**：
  1. **可重入**：Redisson 用 **Hash 结构**存锁，`field = 客户端UUID:线程ID`，`value = 重入次数`；同一线程再次加锁是 `HINCRBY +1` 并刷新过期时间，解锁 `-1`，减到 0 才 `DEL` 并发布解锁消息。
  2. **看门狗（Watch Dog）自动续期**：
     - **触发条件**：`lock()` 不指定 `leaseTime` 时（即走 `lock.lock()`），Redisson 用默认 `lockWatchdogTimeout = 30s`；**如果显式写了 `lock(10, TimeUnit.SECONDS)`，则不会启用看门狗**（这一点是最高频的追问点，必须答对）。
     - **机制**：加锁成功后注册一个延迟任务（底层是 Netty 的 `HashedWheelTimer`），**每 `30 / 3 = 10s` 续期一次**，把 TTL 重置为 30s；解锁时取消续期任务并从 `ExpirationRenewalMap` 移除。
     - **注意**：看门狗只在**客户端进程还活着**时有效；进程被 `kill -9` 后无法续期，锁会在 30s 后自动释放（这正是我们要的）。
  3. **等待机制用发布订阅，而不是自旋**：未获取到锁的线程订阅 `redisson_lock__channel:{lockName}`，锁释放时 `publish` 唤醒，避免了"while 循环 tryLock"式的空转（对 Redis 压力大很多）。
  4. **解锁安全**：解锁同样用 Lua 脚本，校验 `field` 是不是自己的 `UUID:threadId`，防止误删。
  5. **丰富的锁类型**：`RLock`（可重入）、`RReadWriteLock`（读写锁）、`RMultiLock`（联锁）、`RSemaphore`、`RCountDownLatch`、`RFairLock`（公平锁）、`RedissonRedLock`（多主 RedLock）。
  6. **本项目用法**：库存扣减/优惠券领取用 `redissonClient.getLock("lock:stock:" + skuId)`，**锁粒度到 SKU**（不是一把大锁），加锁只在必要区间，且用 `tryLock(waitTime, leaseTime, unit)` 设置**等待超时**避免无限阻塞。**但要强调：秒杀主链路上没有用分布式锁，因为 Redis + Lua 预扣已经保证了原子性，加锁反而会成为瓶颈**——能说出这一点非常加分。
- **常见错误回答**：
  - 「Redisson 就是封装了 SETNX」——没提可重入、看门狗、pub/sub。
  - 「看门狗默认 30 秒续期一次」——是 30s 超时、**每 10s 续一次**。
  - 「用了 `lock(10, SECONDS)` 也会有看门狗」——**错，显式 leaseTime 会关闭看门狗**。

#### Q3.3.6 Redis 单线程为什么快？6.0 的多线程是怎么回事？

- **面试官想听**：能不能区分"命令执行"和"网络 IO"，别把 Redis 6 的多线程说成"命令多线程执行"。
- **参考答案要点**：
  1. **"单线程"指命令执行是单线程**（`redis-server` 主线程），好处是**无需加锁、没有线程切换和锁竞争开销**。
  2. **快的原因**：
     - **纯内存操作**，没有磁盘 IO（持久化是异步 `fork` 子进程做的）。
     - **IO 多路复用**：Linux 下用 `epoll`（+ 非阻塞 IO），单线程即可管理大量连接，避免"一连接一线程"的上下文切换。
     - **高效的数据结构与编码**：SDS（带长度、二进制安全）、`listpack`/`ziplist`（小对象压缩存储）、`intset`、`quicklist`（链表 + listpack）、`skiplist`（ZSet 有序）、渐进式 rehash。
     - **RESP 协议简单**，解析开销小；命令执行是内存操作，单条命令耗时通常在纳秒~微秒级。
  3. **Redis 6.0 的多线程 IO**：引入 `io-threads`，**把网络读写（socket 读写、协议解析）分给多个 IO 线程**，**命令执行仍然是主线程串行**。所以不会破坏原子性，也无法用多线程提升 CPU 密集命令（如 `KEYS`）的性能。
  4. **单线程的代价（要能说出来）**：一条慢命令（`KEYS *`、`FLUSHALL`、大 key 的 `DEL`、复杂 Lua、`SMEMBERS` 大集合）会**阻塞所有请求**，所以线上禁用 `KEYS`（用 `SCAN`）、大 key 用 `UNLINK`。
- **常见错误回答**：
  - 「Redis 6 多线程了，命令并行执行」——错。
  - 「因为用了多路复用所以是并行的」——多路复用只是让单线程能处理更多连接。
  - 不知道慢命令会阻塞全局。

#### Q3.3.7 大 key 和热 key 分别有什么危害？怎么发现和解决？

- **面试官想听**：这是线上运维视角的问题，能答出来会明显区别于"只会写 demo"的候选人。
- **参考答案要点**：
  1. **大 key**：
     - 判定经验值：String 类型 value > 10KB，或集合类型元素数 > 5000（也可用 `MEMORY USAGE key` 实测）。
     - 危害：① 单线程执行，读写/删除大 key 会**阻塞其他请求**（`DEL` 一个百万元素的 set 可能卡几百毫秒）；② 网络带宽被打满；③ 在 Cluster 下造成**数据倾斜**（槽分布不均）；④ 持久化（AOF 重写、RDB、主从全量同步）变慢。
     - 发现：`redis-cli --bigkeys`（统计各类型最大的 key）、`--memkeys`、`MEMORY USAGE <key>`、`redis-rdb-tools` 离线分析 RDB、`SCAN` 抽样统计。
     - 解决：**拆分**（按 hash 分片：`product:attr:{id%16}`）、**压缩**（`gzip` 后存 String，或用 `listpack` 友好的小集合）、**异步删除**（`UNLINK` 代替 `DEL`）、`HSCAN`/`SSCAN` 分批遍历而不是 `HGETALL`、定期清理无 TTL 的大 key。
  2. **热 key**：
     - 定义：短时间内被**极高频率访问**的 key（如秒杀商品详情、爆款库存）。
     - 危害：① 单节点 CPU 打满（Cluster 下该 key 只落在一个分片上，其他节点闲着）；② 网络成为瓶颈；③ 拖慢同节点上的其他请求。
     - 发现：`redis-cli --hotkeys`（**需要 `maxmemory-policy` 为 LFU 才可用**）、`MONITOR` 抽样（线上慎用，影响性能）、客户端埋点统计（本项目在缓存工具类里记录 key 访问计数，定时上报）、`redis-faina`。
     - 解决：① **本地缓存**（Caffeine，几秒 TTL，牺牲一点一致性换吞吐——本项目商品详情用的就是多级缓存）；② 集群下**多副本读**（`READONLY` + 从节点随机读，复制 N 份 key 到不同节点）、`key` 加随机后缀打散成 N 份（读时随机选一个，更新时全量更新，适合只读热点）；③ **限流**（热 key 场景下最直接的保命手段）；④ 秒杀场景直接**把库存判断放进 Lua**，避免读整块数据。
  3. 一句总结：**大 key 是"单个 key 太大"，热 key 是"单个 key 太热"，前者伤内存和阻塞，后者伤 CPU 和带宽。**
- **常见错误回答**：
  - 「用 `KEYS *` 找大 key」——线上禁用，会阻塞。
  - 「热 key 就加缓存」——它本来就在 Redis 里，需要的是本地缓存或打散分片。

#### Q3.3.8 Redis 的常见数据结构和使用场景？

- **面试官想听**：能不能把数据结构和业务场景对应起来，而不是背 API。
- **参考答案要点**：
  1. **String**：缓存对象（JSON）、**计数器**（`INCR` 做限流计数）、分布式锁（`SET NX PX`）、**库存**（本项目秒杀库存用 String + Lua）。
  2. **Hash**：对象的部分字段更新（`HSET user:1 name x`）、购物车（`field = skuId, value = 数量`）、Redisson 的锁实现。
  3. **List**：简单队列/栈（`LPUSH + BRPOP`）、最新消息列表（`LPUSH + LTRIM`）。**生产环境不推荐用它做可靠 MQ**（没有 ack、没有持久化保证）。
  4. **Set**：去重（`SADD` + `SCARD` 统计 UV）、共同好友（`SINTER`）、**秒杀的一人一单集合**（本项目用 `SISMEMBER`/`SADD`，也可用 Hash）。
  5. **ZSet**：排行榜（`ZINCRBY` + `ZREVRANGE`）、**延迟队列**（score 存到期时间戳，定时 `ZRANGEBYSCORE` 拉取）、滑动窗口限流（按时间戳存）。
  6. **Bitmap**：签到、活跃用户统计（`SETBIT`/`BITCOUNT`），内存极省。
  7. **HyperLogLog**：基数统计（UV 估算），**标准误差 0.81%**，占用固定 12KB。
  8. **GEO / Stream**：附近的人、Redis 5 的消息流（支持消费组，接近 MQ，但本项目用 RocketMQ）。
  9. **底层编码要点**（被追问时加分）：`String` → `int`/`embstr`/`raw`；`Hash`/`ZSet`/`List` 小数据量时用 `listpack`（Redis 7 已用 listpack 取代 ziplist），超过阈值转 `hashtable`/`skiplist`；`Set` 整数集合用 `intset`。阈值由 `*-max-listpack-entries`（默认 128）和 `*-max-listpack-value`（默认 64 字节）控制。
- **常见错误回答**：
  - 「ZSet 底层是平衡树」——是**跳表 + 哈希表**。
  - 只会说 String 和 Hash。

#### Q3.3.9 你怎么保证缓存和数据库的最终一致？延迟双删有必要吗？

- **面试官想听**：知道几种方案及各自的缺陷，而不是背"延迟双删"。
- **参考答案要点**：
  1. **Cache Aside（最常用）**：读 → 未命中查 DB → 回填并设 TTL；写 → **先更新 DB，再删除缓存**。
  2. **为什么是"删除"不是"更新"**：并发下"更新缓存"会因为写入顺序与 DB 不一致而产生长期脏数据（缓存可能是旧值）；删除是幂等的，代价是下一次读会 miss（可接受）。
  3. **为什么"先更新 DB 再删"而不是"先删再更新 DB"**：先删缓存 + 后更新 DB 在并发读下更易脏（读线程在删缓存后、更新 DB 前把旧值回填，且长时间不失效）。
  4. **仍有极小概率不一致**：读线程在缓存 miss 后查 DB（旧值）→ 写线程更新 DB 并删缓存 → 读线程把旧值回填。概率低但存在，缓解手段：
     - **延迟双删**：更新 DB 后删一次，延迟约「一次读请求耗时 + 主从延迟」（如 500ms~1s）再删一次。**做法粗糙、依赖延迟估算，通常是兜底而非主力**。
     - **给缓存设较短的 TTL**（最终一定会自愈）。
     - **订阅 binlog（Canal）+ MQ 异步删缓存**：只在 DB 提交成功后删，时序最可靠（本项目未引入，能说清原理即可）。
     - **读写加锁**（性能差，只在极端要求下用）。
  5. **结论话术**：**"缓存一致性追求的是最终一致 + 自愈能力，不是强一致；与其纠结延迟双删，不如把 TTL 设合理、把删缓存的时机放在事务提交之后。"**
  6. **本项目实践**：商品详情缓存 TTL 随机化 5~10 分钟；后台改商品时在**事务提交后**（`afterCommit`）删缓存，不用"事务内删"（否则事务回滚了缓存已删，虽然不算错，但可能删在 DB 提交前，另一个读线程会回填旧值）。
- **常见错误回答**：
  - 「更新 DB 的同时更新缓存，用事务保证」——Redis 和 MySQL 不在一个事务里。
  - 「延迟双删是银弹」——说不清延迟多久、为什么这个时间、失败怎么办。
  - 只背方案，说不出如何"自愈"。

#### Q3.3.10 如果不是秒杀，普通下单流程你会用 Redis 锁吗？

- **面试官想听**：你有没有"能不用就不用"的克制，会不会到处加锁。
- **参考答案要点**：
  1. **优先用 DB 的原子性代替锁**：库存扣减用 `WHERE stock >= 1` 条件更新；幂等用唯一索引；状态流转用 `WHERE status = 旧状态` 的 CAS——**这些都不需要分布式锁**。
  2. **需要分布式锁的场景**：① 同一用户重复提交（也可用幂等 token 替代）；② 定时任务在集群下只允许一个实例执行（也可用"抢占式 DB 更新/Redis SETNX"替代）；③ 跨资源的复杂校验（如"判断券可用 + 扣券"）。
  3. **加锁的代价**：串行化降低吞吐、锁等待放大 RT、有锁超时/续期/误删等一堆边界问题、还要考虑锁粒度（锁 SKU 而不是锁整个活动）。
  4. **原则**：
     - **能用原子操作（DB 条件更新 / Redis Lua）解决的，绝不上锁**；
     - 一定要加锁时，**锁粒度要尽可能小**（`lock:stock:{skuId}`），并设置**等待超时**快速失败；
     - 锁内的代码要**尽可能短**，绝不在锁内做 RPC/发 MQ/循环。
  5. 本项目中的分布式锁实际用在哪：优惠券领取（Redis Lua 也能做，锁是"二次保险"）、定时任务选主、后台批量操作；**秒杀主链路明确不用锁**。
- **常见错误回答**：
  - 「哪里并发就加锁」——典型的新手思维，会把自己锁死。
  - 用 `synchronized` 处理跨实例并发。

### 3.4 消息队列（10 题）

#### Q3.4.1 为什么要用消息队列？解决了什么问题？

- **面试官想听**：不要背"解耦、异步、削峰"三个词，要说清**用在本项目的哪个场景、解决了什么具体问题、带来了什么新问题**。
- **参考答案要点**：
  1. **三大价值**：
     - **异步**：秒杀下单链路里，把"库存 + 订单 + 流水"的落库从同步请求中剥离，接口 RT 从"DB 写入耗时"降为"发消息耗时"。
     - **削峰填谷**：瞬时 1 万 TPS 的预扣成功请求，通过 MQ 摊平成 DB 能承受的几百 TPS 匀速消费。
     - **解耦**：订单支付成功后要触发"扣库存真实化、发通知、加积分、写流水"等多个下游动作，用一条消息广播，下单模块不依赖下游的可用性。
  2. **具体到本项目**：① 秒杀预扣成功 → 发消息异步落库（削峰）；② 下单成功 → 发**延迟消息** 30 分钟后检查支付状态并关单（替代定时任务扫表）；③ 支付成功后 → 发消息驱动库存/积分/通知（解耦）；④ 本地消息表的重试发送（最终一致）。
  3. **引入的代价（必须主动说）**：系统复杂度上升（要处理消息丢失、重复、顺序、积压）、链路由同步变异步导致**排查变难**（所以我把 traceId 透传到消息头）、以及**最终一致**需要额外的对账与补偿机制。
  4. **为什么选 RocketMQ 5**：① **延迟消息**开箱即用（正好匹配"订单超时关单"，不用自己写扫表）；② **事务消息**支持本地事务与发消息的原子性；③ 支持**顺序消息**和消息轨迹；④ 高吞吐、低延迟、堆积能力强（落磁盘，磁盘够就能扛）；⑤ 国内生态与文档成熟，面试也常问。对比：Kafka 吞吐更高但延迟消息/事务消息支持弱、运维重；RabbitMQ 延迟靠插件、吞吐较低。
- **常见错误回答**：
  - 只背"解耦异步削峰"，说不出本项目的具体消息。
  - 「用了 MQ 就不怕高并发了」——MQ 只是把压力后移，消费端和 DB 仍是瓶颈。

#### Q3.4.2 怎么保证消息不丢？（三段论）

- **面试官想听**：能否系统化拆解（生产 / 存储 / 消费），以及"本地消息表"是你自己的实践。
- **参考答案要点**：
  1. **生产端**：
     - 用**同步发送**并校验返回的 `SendStatus.SEND_OK`；失败重试（`retryTimesWhenSendFailed`，默认 2 次）。
     - 更进一步：**本地消息表**——在业务事务中写一条 `sys_message`（`status = 待发送`），事务提交后由定时任务扫描并发送，`SEND_OK` 后置为已发送；发失败就按指数退避重试。**这是不丢消息的关键兜底，因为它把"消息一定要发出去"变成了可恢复的本地状态机**。
     - `sendOneWay`（单向发送）不关心结果，可靠性要求高的场景绝不能用。
  2. **Broker 存储端**：
     - **刷盘**：`flushDiskType = SYNC_FLUSH`（同步刷盘，消息写入 PageCache 后立即刷盘才返回成功）；默认 `ASYNC_FLUSH` 更依赖 OS 刷盘，宕机可能丢少量消息。
     - **复制**：`brokerRole = SYNC_MASTER`（主从同步复制，主等从写成功才返回）；默认 `ASYNC_MASTER` 主节点宕机可能丢消息。RocketMQ 5 推荐用 **DLedger（Raft）** 做高可用。
     - 两者都开 = 可靠性最高、吞吐下降。**面试要说清这是"可靠性与性能的取舍"，不是无脑全开。**
  3. **消费端**：
     - **业务处理成功后才返回 `CONSUME_SUCCESS`**；异常返回 `RECONSUME_LATER`，进入 `%RETRY%{consumerGroup}` 重试队列（RocketMQ 默认重试 16 次，间隔按等级递增 10s/30s/1m…2h）。
     - 超过最大重试次数进入**死信队列 `%DLQ%{consumerGroup}`**，必须配置**监控告警 + 人工处理入口**，否则消息等于悄悄丢了。
     - **绝不能"先提交 offset / 先 ack 再处理业务"**。
  4. **端到端口诀**：**生产端有本地消息表兜底 + Broker 同步刷盘与同步复制 + 消费端处理成功才 ack + 死信队列告警**。
- **常见错误回答**：
  - 「RocketMQ 保证不丢消息」——没有端到端的保证，只有各环节的机制。
  - 「开事务消息就不丢了」——事务消息解决原子性，不解决消费端。
  - 「重试 16 次之后就没事了」——不说死信队列和告警，等于丢失。

#### Q3.4.3 怎么保证消息不被重复消费？

- **面试官想听**：明确 at-least-once 语义 + 幂等的分层落地。
- **参考答案要点**：
  1. **前提**：RocketMQ 保证 **at-least-once**（至少一次），重复投递的来源包括：生产者重试、Broker 主从切换、消费者 ack 丢失后重投、消费者重平衡（rebalance）。所以**不重复是做不到的，能做的是"重复消费不影响结果"（幂等）**。
  2. **落地手段（本项目四层）**：
     - **唯一索引兜底**（最强）：`sms_seckill_record` 的 `uk(user_id, activity_id, sku_id)`、`wms_stock_log` 的 `uk(business_no)`；捕获 `DuplicateKeyException` 当作成功。
     - **状态机 CAS**：`UPDATE oms_order SET status = 已支付 WHERE order_no = ? AND status = 待支付`，`affectedRows = 0` 直接返回成功（已处理）。
     - **本地消息表状态位**：`sys_message` 用 `status` + `version` 乐观锁更新，保证同一条待发消息只有一个线程在发。
     - **Redis 前置去重**：`SETNX consume:{msgId} 1 EX 3600`，作为**快速过滤**减少无效 DB 访问。**注意它的两个风险**：Redis 挂了就失效（所以不能作唯一手段）；如果先 setnx 再处理、处理失败后 key 已存在，会导致**漏处理**——正确做法是 setnx 成功后立即处理，失败时删除 key 或依赖 DB 唯一索引兜底。
  3. **关键区分**：`msgId` 去重只能防"同一条消息重复投递"，**防不了业务层面的重复**（用户点了两次、两个不同的消息都要给同一订单扣库存）。所以**幂等键必须是业务键**（`order_no`、`biz_no`、`(user_id, activity_id, sku_id)`）。
  4. **不要**：不要在消费端"先 select 查有没有处理过再 insert"——这是 check-then-act，并发下必然穿透。
- **常见错误回答**：
  - 「RocketMQ 自带去重」——没有。
  - 「用消息 ID 去重就够了」——不同消息做同一件业务事就失效了。
  - 用 `select` + `insert` 的判断。

#### Q3.4.4 顺序消息怎么实现？你项目里需要顺序吗？

- **面试官想听**：知不知道 RocketMQ 的顺序是"局部顺序"，以及顺序的代价。
- **参考答案要点**：
  1. **RocketMQ 的顺序语义**：**分区（队列）内有序，全局无序**。因为一个 Topic 有多个 MessageQueue，消息被分散到不同队列后并发消费，跨队列无法保证顺序。
  2. **实现方式**：
     - 生产端用 `MessageQueueSelector`（或 `RocketMQTemplate.sendOrderly`）按**业务 key hash 选队列**（如 `orderNo`），保证同一订单的消息进同一队列。
     - 消费端必须用 **`MessageListenerOrderly`**（`consumeMode = ConsumeMode.ORDERLY`），它对每个队列**加锁单线程消费**；用默认的 `MessageListenerConcurrently` 即使生产端有序也会乱。
  3. **代价（要主动说）**：① 并发度下降到"队列数"级别；② **热点订单哈希倾斜**（某个订单消息特别多会拖慢整个队列）；③ 顺序消费时遇到异常**不能跳过**，只能返回 `SUSPEND_CURRENT_QUEUE_A_MOMENT` 稍后重试（不像并发消费可以进重试队列），**一个坏消息会阻塞整个队列**。
  4. **本项目的取舍**：**尽量不依赖顺序**。订单状态流转用**状态机 CAS** 保证"乱序到达也不会走错状态"（比如"已支付"事件先到、"已创建"事件后到，CAS 会让后者失败而不是把状态改回去）；库存扣减/回滚都用业务流水号幂等。**"用状态机和幂等把顺序问题消解掉"比"强行保证顺序"更工程化**——这是很好的加分回答。
  5. 如果确实需要：支付回调 → 发货通知这类同一订单的强顺序事件，用 `orderNo` 做 hash key + `ORDERLY` 消费。
- **常见错误回答**：
  - 「RocketMQ 保证全局顺序」——没有任何 MQ 能在多队列下保证全局顺序。
  - 「把 Topic 队列数设为 1 就是全局有序」——对，但吞吐等于放弃，要说清代价。

#### Q3.4.5 延迟消息的实现原理是什么？为什么不用定时任务扫表？

- **面试官想听**：这是本项目的 ADR-5，必须能讲清原理和取舍。
- **参考答案要点**：
  1. **RocketMQ 4.x 的固定延迟等级**：18 个等级（`1s 5s 10s 30s 1m 2m 3m 4m 5m 6m 7m 8m 9m 10m 20m 30m 1h 2h`）。发送时指定 `delayTimeLevel`，Broker 做的事是：
     - 把消息的**原始 Topic 和 queueId 备份**到消息属性里；
     - 把消息的 Topic 改写为内部 Topic **`SCHEDULE_TOPIC_XXXX`**，`queueId = delayTimeLevel - 1`（**每个延迟等级一个队列，队列内按到期时间有序**）；
     - **`ScheduleMessageService`** 为每个等级启动一个定时任务（默认每 100ms），从对应队列拉取消息，用 `deliverTimestamp = 消息存储时间 + 延迟时间` 与当前时间比较，**到期的消息把 Topic 还原成真实 Topic 并重新写入 CommitLog**（对消费者可见），同时删除调度队列里的消息。
  2. **RocketMQ 5.0 的定时消息**：支持**任意秒级精度**（基于时间轮 `TimerWheel` 实现），通过消息属性 `deliverTimeMs` 指定投递时间，可以理解为"改良版的延迟队列"，不再受 18 个等级限制。**回答时把 4.x 的等级机制和 5.0 的任意时间都说到，会显得理解更深。**
  3. **为什么不用 `@Scheduled` 扫表**（ADR-5 的取舍）：

     | 维度 | 定时任务扫表 | RocketMQ 延迟消息 |
     |---|---|---|
     | 精度 | 取决于扫描间隔（秒级/分钟级），最坏误差一个周期 | 秒级，误差小 |
     | 成本 | **空扫大量未超时订单**，随订单量增长而恶化；需要给 `status + create_time` 建索引 | 无空扫，Broker 按到期时间调度 |
     | 扩展性 | 多实例需要分布式锁/分片（否则重复关单） | 天然分布式，消息只被一个消费者消费 |
     | 可靠性 | 任务失败要自己重试与补偿 | 消息持久化 + 重试机制 |
     | 复杂度 | 简单直观 | 需要引入 MQ（本项目本来就有） |
  4. **本项目的具体用法**：下单成功 → 发一条 `delayTimeLevel = 16`（30m）的消息 → 消费者收到后查订单，**如果仍是"待支付"就关单并回滚库存，否则直接丢弃（幂等）**。
  5. **注意事项**：延迟消息**不等于可靠定时**（极端情况下有秒级偏差）；消费者必须**幂等**（重复投递很正常）；关单时要**再次检查状态**，因为用户可能正好在这时支付。
- **常见错误回答**：
  - 「RocketMQ 用定时器把消息放回去」——太笼统，说不出内部 Topic 和队列机制。
  - 「延迟消息精度是毫秒级」——4.x 是固定等级，5.0 才支持任意时间。
  - 说不出为什么不用扫表（只会说"扫表性能差"，没有量化维度）。

#### Q3.4.6 消息积压了怎么办？

- **面试官想听**：应急处理能力 + 根因分析，而不是"加机器"。
- **参考答案要点**：
  1. **先判断原因**（顺序很重要，否则加机器也没用）：
     - 消费者端：消费逻辑变慢（新增了慢 SQL、调用了不稳定的外部 RPC）、**消费线程池被阻塞**、消费者挂了没重启、消费异常导致大量重试。
     - 流量端：活动/大促导致生产量突增，消费能力没跟上。
     - Broker 端：磁盘快满、PageCache 命中率低、主从同步慢。
  2. **应急处理**：
     - **临时扩容消费者实例**（关键前提：**消费者数不能超过 Topic 的队列数**，多出来的消费者会空转；所以建 Topic 时队列数要留足，本项目秒杀 Topic 设 8~16 个队列）。
     - **提高消费并发**：调大 `consumeThreadMin/Max`（并发消费）。
     - **紧急"转存 + 并行消费"**：写一个临时消费者，把积压消息原样转发到一个**队列数很多的新 Topic**（如 64 个），再用大量消费者并行消费——这是 RocketMQ 官方推荐的应急手段。
     - **降级非核心逻辑**：暂时跳过积分、通知、埋点等非关键消费逻辑，只做核心落库。
     - **生产端限流**：暂时降低上游发送速率（秒杀场景可直接快速失败），先止血。
  3. **恢复后处理**：把降级跳过的逻辑用补偿任务补回来（消费的是消息，不能凭空补，所以要在转存时保留原始消息或落一份补偿表）。
  4. **长期治理**：监控 **consumer lag / 堆积量**（`mqadmin consumerProgress -g group`）并配告警；压测时把"消费能力"也纳入容量评估；消费逻辑里禁止做重 IO，重活异步化。
  5. **一句话总结**：**"MQ 堆积本身不可怕（RocketMQ 落磁盘，磁盘够就能扛），可怕的是不知道堆积、或者堆积之后才发现消费端有慢 SQL。"**
- **常见错误回答**：
  - 「加机器」——不提队列数上限，会被追问到崩。
  - 「把消息清掉重新生产」——数据会丢。
  - 「提高消费者线程数就行」——如果是外部 RPC 慢，加线程只会把连接池打满。

#### Q3.4.7 事务消息的原理是什么？和本地消息表怎么选？

- **面试官想听**：能否把 half 消息、回查机制讲清，并说出本项目为什么选本地消息表。
- **参考答案要点**：
  1. **要解决的问题**：本地事务（如"创建订单"）与"发送消息"这两个操作无法在同一个事务里，可能出现"订单建了但消息没发"或"消息发了但订单回滚了"。
  2. **RocketMQ 事务消息流程**：
     - 生产者发送**半消息（Half Message）**到 `RMQ_SYS_TRANS_HALF_TOPIC`，此时消息对消费者**不可见**；Broker 返回成功即表示半消息已存储。
     - 生产者执行**本地事务**。
     - 根据结果向 Broker 发送 **Commit / Rollback**：Commit 把消息从 half topic 恢复到真实 Topic（消费者可见），Rollback 则删除。
     - **如果 Broker 长时间没收到 Commit/Rollback（生产者宕机）**，会**回查生产者**（`TransactionListener#checkLocalTransaction`，默认最多 15 次、间隔递增）。所以生产者**必须实现回查逻辑**：去查本地事务状态表（如 `sys_message` 或专门的 `transaction_log`）来判断该 Commit 还是 Rollback。
  3. **事务消息的局限**：① 回查要求本地事务有**可查询的状态**（必须落库）；② 半消息对消费者不可见但会占用存储；③ 只保证"消息与本地事务的最终一致"，不保证消费者已处理；④ RocketMQ 5 的事务消息实现有调整（`TransactionMQProducer` 在 Proxy 模式下的用法），版本兼容要注意。
  4. **本地消息表方案**：业务事务内写 `sys_message`（`status = 待发送`）→ 定时任务扫描发送 → 成功后改为已发送。**优点**：不依赖 MQ 特性、实现简单、状态可查可人工介入、重试可控。**缺点**：有发送延迟（取决于扫描间隔）、需要额外的表和定时任务、扫表有性能成本。
  5. **本项目选择（ADR-7）**：用**本地消息表**。理由：① 单库单机，不引入分布式事务框架（也排除 Seata）；② 本地消息表逻辑我完全可控，出问题能人工介入，**比事务消息更容易讲清楚**；③ 顺便可以作为"支付回调、库存补偿"等多个场景的统一可靠消息基础设施。
  6. **如果被问"那什么时候该用事务消息"**：当业务方**不想引入额外的表和定时任务**、且已有 MQ、且本地事务状态可以查询时，事务消息更省事；反之（要严格控制重试节奏、需要人工兜底、要多场景复用）本地消息表更合适。
- **常见错误回答**：
  - 「事务消息就是给消息加了事务，保证一定成功」——说不清 half message 和回查。
  - 「我用了事务消息，所以不需要幂等」——消费端幂等仍然必需。
  - 不知道事务消息需要实现回查接口。

#### Q3.4.8 消费失败怎么处理？重试机制和死信队列？

- **面试官想听**：有没有处理过"这条消息永远消费不成功"的情况。
- **参考答案要点**：
  1. **重试机制**：消费返回 `RECONSUME_LATER`（或用 `ConsumeConcurrentlyStatus.RECONSUME_LATER`）时，消息被投递到 `%RETRY%{consumerGroup}` 重试队列，**默认最多重试 16 次**，每次间隔按等级递增（10s、30s、1m、2m、3m、4m、5m、6m、7m、8m、9m、10m、20m、30m、1h、2h）——是**按等级递增不是指数**。
  2. **死信队列**：超过最大重试次数后进入 `%DLQ%{consumerGroup}`，**RocketMQ 不会自动处理，必须有人管**。本项目的做法：监控 DLQ 的消息量并**告警**，同时提供一个"死信重投"的后台接口（人工确认后重新发送）。
  3. **区分"可重试"和"不可重试"错误**：
     - `RECONSUME_LATER`：DB 连接闪断、超时、死锁——**重试有意义**。
     - 参数错误、数据不存在、业务校验失败——**重试无意义**，应该记录日志 + 落异常表 + 返回 `CONSUME_SUCCESS`（否则会占满重试队列），这需要**在消费端做异常分类**（本项目抛 `BizException` 视为不可重试并落 `异常记录`，其他异常才重试）。
  4. **重试必须幂等**（否则一次业务失败变成多次扣减）。
  5. **并发消费 vs 顺序消费的重试**：并发消费可以进重试队列；**顺序消费（`MessageListenerOrderly`）本地重试，不能进重试队列，失败会阻塞当前队列**。
  6. **加分点**：RocketMQ 5 可以用 `SimpleConsumer` / `PushConsumer` 的 `ConsumeResult` 表达更细的语义（成功/失败/稍后重试），也可以用 `ackIndex` 做位点提交，但要能说清和你项目里用法的区别。
- **常见错误回答**：
  - 「消费失败重试就行了」——不说重试次数上限和死信队列。
  - 「所有异常都重试」——业务性错误重试 16 次是纯粹的浪费，还会堆积。

#### Q3.4.9 RocketMQ 怎么保证高可用和消息的顺序写性能？

- **面试官想听**：知不知道 CommitLog、ConsumeQueue、IndexFile 的存储结构和零拷贝。
- **参考答案要点**：
  1. **存储结构（核心）**：
     - **CommitLog**：所有消息**顺序追加**写同一个文件（默认 1GB 一个文件，写满滚动），这是 RocketMQ 高吞吐的根本——**顺序写磁盘**接近内存随机写的性能。
     - **ConsumeQueue**：消费索引，按 `Topic + QueueId` 组织，每条记录固定 20 字节（`commitLogOffset + size + tagCode`），**用 mmap（内存映射）**，读起来快。
     - **IndexFile**：按 key/时间范围的哈希索引，支持按 `msgId`/`key` 查询消息。
  2. **为什么快**：① 顺序写 CommitLog（避免随机 IO）；② **OS PageCache + mmap**；③ **零拷贝**——消费时用 `FileChannel.transferTo` / `mmap` 直接把数据从 PageCache 发到网卡（`sendfile`），避免内核态与用户态多次拷贝；④ 支持批量/异步刷盘。
  3. **高可用**：
     - **主从复制**：`ASYNC_MASTER`（异步，主宕机可能丢少量消息、切换要人工或 Dledger 自动）vs `SYNC_MASTER`（同步双写，可靠性高、RT 上升）；从节点可提供**读**（消费可从从节点拉，减轻主节点压力）。
     - **DLedger / Raft**：RocketMQ 4.5+ 支持基于 Raft 的自动选主（`enableDLegerCommitLog`），避免主节点挂掉后手动切换。
     - **RocketMQ 5 的 Proxy 模式**：客户端连 Proxy，Proxy 无状态、可水平扩容，NameServer 依然轻量。
  4. **本项目实践**：本地用 Docker Compose 起**单 Master**（`SYNC_FLUSH` 关闭以降低本地资源占用），并在 README 里说明"生产环境应是 2 主 2 从 + DLedger"——**能说清"本地配置 ≠ 生产配置"是加分的诚实**。
- **常见错误回答**：
  - 「RocketMQ 把消息存在 MySQL 里」——存储在 CommitLog 文件。
  - 「所有消息写多个小文件，所以快」——恰恰相反，是**顺序写单一大文件**才快。
  - 不知道 ConsumeQueue 的存在。

#### Q3.4.10 如果 MQ 整个挂掉了，你的秒杀怎么办？

- **面试官想听**：依赖治理与降级意识。
- **参考答案要点**：
  1. **先分层判断**：
     - 只是**生产端**发不出去：本地消息表兜底，`sys_message` 里是"待发送"，MQ 恢复后定时任务自动补发。**前端可以对用户返回"抢购成功，订单确认中"**（因为 Redis 已预扣成功）。
     - **Broker 整体不可用**：预扣成功的请求无法落库 → 短期内应**降级为"直接同步落库"**（限量放行，走 DB 条件更新），或者**直接关闭秒杀入口**（返回"活动太火爆"）并保证已预扣的用户最终能落库。
  2. **关键设计**：**MQ 的不可用不能导致数据错误**。因为权威库存仍在 `wms_stock`，Redis 预扣只是额度，落库延迟只会让用户等待，最终靠本地消息表补齐。
  3. **熔断与开关**：把秒杀入口做成**可远程开关**（配置项 / 数据库开关 / Redis 标志位），出问题时一键关闭比现场改代码快得多；同时**限流阈值动态可调**。
  4. **监控与预案**：MQ 堆积、DLQ、发送失败率都要有告警；提前写好"降级 SOP"（谁关开关、怎么通知用户、怎么补偿已预扣的用户）。
  5. **诚实的边界**：「我本地是单 Master 部署，所以确实存在 MQ 不可用的窗口，我的设计目标是**不产生错误数据 + 用户可感知的排队**，而不是"高可用到零故障"——真要做到零故障需要多副本 + DLedger + 跨机房，那是另一个量级的成本。」
- **常见错误回答**：
  - 「MQ 不会挂」。
  - 「那就直接查数据库下单」——不说限量限流，反而把 DB 打挂。
  - 「用 Redis 存消息做队列」——Redis 可靠性弱于 MQ，且 Redis 本身就可能是同一个故障域。

### 3.5 Spring（9 题）

#### Q3.5.1 讲一下 IOC 和 DI，Spring 容器启动都做了什么？

- **面试官想听**：能不能把"容器刷新"的主干流程说出来，而不是只说"把对象交给 Spring 管理"。
- **参考答案要点**：
  1. **IOC（控制反转）**：对象的创建、装配、生命周期由容器负责，而不是 `new`；**DI（依赖注入）** 是 IOC 的实现方式（构造器 / setter / 字段注入）。
  2. **核心概念**：`BeanDefinition`（Bean 的元数据：类名、作用域、依赖、初始化方法等）、`BeanFactory`（基础容器，懒加载）、`ApplicationContext`（增强容器，启动时预实例化单例、支持事件、国际化、资源加载）。
  3. **`AbstractApplicationContext#refresh()` 主干**（Spring Boot 3 / Spring 6，12 步）：
     ① `prepareRefresh`（记录启动时间、初始化属性源）；
     ② `obtainFreshBeanFactory`（创建/获取 `DefaultListableBeanFactory`，加载 BeanDefinition）；
     ③ `prepareBeanFactory`（注册 `ApplicationContextAwareProcessor`、依赖解析器、`BeanPostProcessor` 等）；
     ④ `postProcessBeanFactory`（子类扩展）；
     ⑤ **`invokeBeanFactoryPostProcessors`**（执行 `BeanFactoryPostProcessor`，**`ConfigurationClassPostProcessor` 在这里解析 `@Configuration`/`@ComponentScan`/`@Import`/`@Bean`，把配置类变成 BeanDefinition**）；
     ⑥ `registerBeanPostProcessors`（注册 `BeanPostProcessor`，AOP 就靠它）；
     ⑦ `initMessageSource`、⑧ `initApplicationEventMulticaster`、⑨ `onRefresh`（**Spring Boot 在这里创建并启动 Tomcat**）；
     ⑩ `registerListeners`、⑪ **`finishBeanFactoryInitialization`（实例化所有非懒加载单例 Bean）**、⑫ `finishRefresh`（发布 `ContextRefreshedEvent`）。
  4. **依赖注入方式取舍**：**构造器注入**（推荐）——依赖不可变（`final`）、启动时即可发现循环依赖、便于单测；`@Autowired` 字段注入——简洁但无法 `final`、隐藏依赖、不利于测试。本项目 Service 统一用构造器注入（配合 Lombok `@RequiredArgsConstructor`）。
  5. 加分点：`@Autowired` 按类型注入，多个候选时配合 `@Primary` / `@Qualifier` / `@Resource`（按名称）。
- **常见错误回答**：
  - 「IOC 就是把 new 变成 @Autowired」——只有现象没有机制。
  - 说不出 `BeanFactoryPostProcessor` 和 `BeanPostProcessor` 的区别（前者改 BeanDefinition，后者改 Bean 实例）。

#### Q3.5.2 AOP 的原理是什么？为什么有时会失效？

- **面试官想听**：动态代理的选择 + 失效场景（这题最常被追问第二部分）。
- **参考答案要点**：
  1. **原理**：AOP 通过**动态代理**在目标方法前后织入增强逻辑。Spring AOP 是**运行期代理**（不是 AspectJ 的编译期/字节码织入），只支持**方法级**连接点。
  2. **两种代理**：
     - **JDK 动态代理**：目标类**实现了接口**时默认使用，基于 `InvocationHandler` + `Proxy.newProxyInstance`，生成接口的实现类。
     - **CGLIB**：目标类**没有接口**时使用，通过继承生成子类并覆写方法（所以 **`final` 类/方法无法代理**，`private` 方法也不可）。Spring Boot 2.x 起 `spring.aop.proxy-target-class=true`（默认），**也就是默认都走 CGLIB**。
  3. **代理对象的生成时机**：`AbstractAutoProxyCreator`（一个 `BeanPostProcessor`）在 Bean **初始化后**（`postProcessAfterInitialization`）判断是否需要代理，需要则用 `ProxyFactory` 生成代理对象放进容器。
  4. **失效场景（重点）**：
     - **同类内部方法自调用**：`this.methodB()` 不走代理对象，所以 `methodB` 上的 `@Transactional`/`@Cacheable`/自定义注解**全部失效**。解法：注入自身（`@Lazy` 或 `AopContext.currentProxy()`，需 `@EnableAspectJAutoProxy(exposeProxy = true)`）、拆到另一个 Bean、或用 `ApplicationContext.getBean`。
     - **方法不是 `public`**（`private`/`protected` 不生效，`protected` 在 CGLIB 下也不建议）。
     - **`final`/`static` 方法**。
     - **对象不是 Spring 管理的**（自己 `new` 出来的）。
     - **切点表达式写错**（`execution` 包路径不匹配）。
     - **注解加在接口上而代理是 CGLIB**、或注解不在方法上。
  5. **本项目实践**：`@RateLimit`（Redis+Lua 限流）、`@DistributedLock`（Redisson）、`@Idempotent`（幂等）三个注解**都是通过 AOP 实现的**；切点用 `@annotation(...)` 精确匹配，并**注意把注解加在 Service 实现类的方法上**（加在接口上在 CGLIB 代理下可能拿不到）。
  6. **多切面顺序**：用 `@Order` 控制（限流应该在最外层，锁在限流之内）。
- **常见错误回答**：
  - 「AOP 是 AspectJ 实现的」——Spring AOP 用自己的动态代理，只有注解语法借鉴 AspectJ。
  - 「AOP 可以给字段赋值、可以拦截构造器」——Spring AOP 只能方法级。
  - 说不出自调用失效，或者只说"加 `@Transactional` 就好"。

#### Q3.5.3 Bean 的生命周期是怎样的？

- **面试官想听**：能否按顺序说出关键扩展点，尤其"代理对象是在哪一步生成的"。
- **参考答案要点**：
  1. **主流程**：
     ① 实例化（`createBeanInstance`，构造器反射）；
     ② **属性填充**（`populateBean`，依赖注入）；
     ③ **Aware 接口回调**（`BeanNameAware` → `BeanFactoryAware` → `ApplicationContextAware` 等，`ApplicationContextAwareProcessor` 处理）；
     ④ **`BeanPostProcessor#postProcessBeforeInitialization`**；
     ⑤ **初始化**：`@PostConstruct`（由 `CommonAnnotationBeanPostProcessor` 处理）→ `InitializingBean#afterPropertiesSet` → 自定义 `init-method`（XML 或 `@Bean(initMethod)`）；
     ⑥ **`BeanPostProcessor#postProcessAfterInitialization`** —— **AOP 代理对象就在这一步生成**（`AbstractAutoProxyCreator`）；
     ⑦ 使用（放入单例池 `singletonObjects`）；
     ⑧ 销毁：`@PreDestroy` → `DisposableBean#destroy` → `destroy-method`。
  2. **关键点**：**代理对象生成在初始化之后**，所以如果 Bean 被 AOP 代理，注入到其他 Bean 里的是**代理对象**（这就引出了循环依赖三级缓存的设计，见 Q3.5.4）。
  3. **`BeanPostProcessor` vs `BeanFactoryPostProcessor`**：前者作用于 **Bean 实例**（可返回包装/代理对象，如 `@Async`、`@Transactional`、`@Scheduled` 的后处理器）；后者作用于 **BeanDefinition**（`PropertySourcesPlaceholderConfigurer`、`ConfigurationClassPostProcessor`）。
  4. **作用域**：`singleton`（默认，容器内一个）、`prototype`（每次 getBean 都新建，**销毁不由容器管理**）、`request`/`session`/`application`（Web）。
  5. **本项目相关**：`ShoppingApplication` 启动后，`MybatisPlusConfig`（分页插件）、`RedisConfig`、`Knife4jConfig` 都是配置类；`SecurityConfig` 注册过滤器链，属于 Spring Security 的自动装配扩展点。
- **常见错误回答**：
  - 「先初始化再注入属性」——顺序反了，是**先属性填充再初始化**（因为初始化方法可能用到注入的依赖）。
  - 「AOP 代理在实例化时生成」——在初始化后的 `postProcessAfterInitialization`。

#### Q3.5.4 循环依赖 Spring 怎么解决的？三级缓存分别是什么？

- **面试官想听**：**这题的杀伤力在于第三级缓存为什么必须存在**，很多人只会说"三级缓存解决循环依赖"。
- **参考答案要点**：
  1. **三级缓存**：
     - **一级 `singletonObjects`**：完整的单例（成品）。
     - **二级 `earlySingletonObjects`**：提前暴露的"半成品"（实例化完成但未属性填充/初始化）。
     - **三级 `singletonFactories`**：`ObjectFactory`（工厂），用于在需要时**生成早期引用**（可能返回代理对象），且**只用一次**（被取走后从三级移除、放入二级）。
  2. **A↔B 流程**：创建 A → 实例化 A（此时先往三级缓存放 A 的 `ObjectFactory`）→ 属性填充发现需要 B → 创建 B → B 属性填充需要 A → 从三级缓存拿到 A 的 `ObjectFactory` 生成早期引用（必要时包装成代理）→ 放入二级 → B 完成 → 回到 A，A 完成并放入一级。
  3. **为什么需要第三级而不是只用二级**：为了让**需要 AOP 代理**的 Bean 也能正确工作。如果 A 被切面代理，直接暴露原始对象会导致 B 注入的是"原始 A"，而容器最终放的是"代理 A"，一个 Bean 出现两个实例。第三级的 `ObjectFactory#getObject()` 里会调用 `getEarlyBeanReference()` 提前生成代理，**保证注入的早期引用与最终 Bean 一致**。
  4. **不能解决的场景**：
     - **构造器注入的循环依赖**（实例化阶段就死锁）→ 抛 `BeanCurrentlyInCreationException`，必须改成 setter/字段注入或重构。
     - **`prototype` 作用域的循环依赖** → 直接抛异常，因为不缓存。
     - `@Async` 等由后置处理器在新代理链上生成的 Bean 可能报错。
  5. **Spring Boot 2.6+ 默认禁止循环依赖**：`spring.main.allow-circular-references` 默认 `false`，出现循环依赖会启动失败。**这其实是好事**——循环依赖本身就是设计问题，本项目通过分层（web → service → dao）刻意避免。
  6. **面试加分收尾**：**"不过更好的答案是不要有循环依赖。我这边的分层是严格单向的，所以没依赖这个机制。"**
- **常见错误回答**：
  - 「三级缓存是为了性能」——是为了处理 AOP 代理的一致性。
  - 「三级缓存存的是 Bean 实例」——存的是 `ObjectFactory`。
  - 「构造器注入也能解决循环依赖」——不能。

#### Q3.5.5 `@Transactional` 在哪些情况下会失效？

- **面试官想听**：这是事务的实操题，能答出 6 条以上说明你真写过。
- **参考答案要点**：
  1. **同类内部自调用**（最高频）：`this.otherTxMethod()` 不走代理 → 事务不生效。**这是本项目中我在写"订单状态流转"时踩过的坑**：一个 `cancelOrder` 内部调用 `rollbackStock`，后者上的 `@Transactional(propagation = REQUIRES_NEW)` 完全不生效。
  2. **方法不是 `public`**：Spring 事务拦截器默认只对 `public` 方法生效（`protected`/`private`/包级不生效）。
  3. **异常被吞掉**：`try-catch` 后不抛出，事务管理器感知不到异常 → 不回滚。
  4. **异常类型不对**：默认**只对 `RuntimeException` 和 `Error` 回滚**，`Exception`（受检异常）不回滚 → 必须写 `@Transactional(rollbackFor = Exception.class)`（本项目统一都写上）。
  5. **多线程/异步**：事务上下文存在 `ThreadLocal`（`TransactionSynchronizationManager`），**新线程不继承**，`@Async` 方法里的事务是新事务，外层回滚不影响它（这也是"异步落库不能靠外层事务保证"的原因）。
  6. **数据库/引擎不支持**：MyISAM 不支持事务（本项目全 InnoDB）。
  7. **传播行为配置不当**：`NOT_SUPPORTED`、`NEVER`、`SUPPORTS`（外层无事务时就不开事务）；或外层把异常吞了导致外层提交。
  8. **类没被 Spring 管理**（自己 `new`、`static` 方法、`final` 方法）。
  9. **事务超时/只读配置**：`@Transactional(readOnly = true)` 下写操作会报错（不是失效但要注意）；或者事务里做了远程调用导致超时。
  10. **注意 `@Transactional` 与 `@Async`、`@Cacheable` 等的顺序问题**，以及**事务里发 MQ/调 RPC 的经典错误**——应该用 `TransactionSynchronizationManager.registerSynchronization()` 的 `afterCommit` 在**事务提交后**再发消息。
- **常见错误回答**：
  - 「只要加了 `@Transactional` 就有事务」。
  - 「默认所有异常都回滚」——受检异常不回滚。
  - 说不出自调用，或者给出的解法是"加 `@EnableTransactionManagement`"（Boot 已自动开启，没用）。

#### Q3.5.6 `@Transactional` 的传播行为有哪些？项目里怎么用的？

- **面试官想听**：7 种传播行为 + 至少一个真实的使用场景。
- **参考答案要点**：
  1. **七种**：

     | 传播行为 | 含义 |
     |---|---|
     | `REQUIRED`（默认） | 有事务就加入，没有就新建 |
     | `REQUIRES_NEW` | 总是新建事务，**挂起当前事务** |
     | `NESTED` | 嵌套事务，用 **Savepoint** 实现，内层回滚不影响外层 |
     | `SUPPORTS` | 有就用，没有就以非事务方式执行 |
     | `NOT_SUPPORTED` | 以非事务方式执行，挂起当前事务 |
     | `MANDATORY` | 必须在事务中，否则抛异常 |
     | `NEVER` | 必须不在事务中，否则抛异常 |
  2. **`REQUIRES_NEW` vs `NESTED`**：前者是**两个独立事务、两个数据库连接**（外层回滚不影响内层已提交的结果），后者是**同一个连接上的 Savepoint**（外层回滚内层也回滚）。**`REQUIRES_NEW` 会多占一个连接，高并发下可能耗尽连接池；且如果外层持有行锁、内层又要更新同一行，会自己把自己锁死（自死锁）**——这是必须知道的坑。
  3. **本项目用法**：
     - **下单主流程**：`REQUIRED`（订单 + 订单明细 + 库存扣减 + 库存流水是一个原子操作，要么全成要么全败）。
     - **支付回调的幂等记录**：先插 `pay_notify_log` 用 `REQUIRES_NEW`，保证"即使后续业务处理失败回滚，回调日志也已经落库"，从而能识别重复回调。
     - **操作日志**：`REQUIRES_NEW` 或者更好——**异步 + 独立事务**，避免日志写失败影响主业务。
     - **秒杀落库消费**：MQ 消费者方法上标 `REQUIRED`，一次消费一个事务。
  4. **实践原则**：**事务尽量小**；不要在事务里做 RPC、发消息、循环大更新；`REQUIRES_NEW` 慎用（连接占用与自死锁）。
- **常见错误回答**：
  - 只背七种名字，说不出 `NESTED` 用 Savepoint 实现。
  - 把所有方法都加 `REQUIRES_NEW`"更安全"——这会导致连接耗尽和外层回滚后内层已提交的数据不一致。

#### Q3.5.7 Spring Boot 自动装配的原理是什么？

- **面试官想听**：`@SpringBootApplication` 拆解 + 条件装配 + 新版的 `AutoConfiguration.imports`。
- **参考答案要点**：
  1. **`@SpringBootApplication` = 三个注解**：
     - `@SpringBootConfiguration`（本质是 `@Configuration`）；
     - `@ComponentScan`（扫描当前包及子包，**所以启动类必须放在根包 `com.shopping` 下**）；
     - **`@EnableAutoConfiguration`**。
  2. **`@EnableAutoConfiguration` = `@AutoConfigurationPackage` + `@Import(AutoConfigurationImportSelector.class)`**：
     - `AutoConfigurationImportSelector` 实现 `ImportSelector`，在 `selectImports` 里读取 **`META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`**（Spring Boot **2.7+ 的新文件**，之前是 `spring.factories` 里的 `EnableAutoConfiguration` 键），得到一堆自动配置类全限定名。
     - 经过**去重、排除（`spring.autoconfigure.exclude`）、条件过滤**后，把这些配置类作为 BeanDefinition 注册进容器。
  3. **条件装配（核心）**：`@ConditionalOnClass`、`@ConditionalOnMissingBean`、`@ConditionalOnBean`、`@ConditionalOnProperty`、`@ConditionalOnWebApplication`、`@ConditionalOnResource`。**"按需生效"就是这么实现的**——比如 classpath 上有 `DataSource` 才装配 `DataSourceAutoConfiguration`。
  4. **`@ConditionalOnMissingBean` 的深层含义**：它是**"用户配置优先"的实现**——自动配置只在用户没自己定义该 Bean 时生效。注意它依赖**配置类的加载顺序**（自动配置类在用户配置之后处理），所以自动配置里不能随便用 `@ConditionalOnMissingBean` 施加在普通 `@Bean` 上（会有顺序陷阱）。
  5. **自定义 Starter 怎么写**（面试高频延伸）：建一个 `xxx-spring-boot-starter` 模块 → 写 `XxxProperties`（`@ConfigurationProperties(prefix = "xxx")`）+ `XxxAutoConfiguration`（`@AutoConfiguration` + `@ConditionalOnMissingBean` 兜底）→ 在 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` 里登记类名 → 使用方引入依赖即可生效。
  6. **本项目相关**：`spring-boot-starter-web`、`mybatis-plus-boot-starter`、`spring-boot-starter-data-redis`、`redisson-spring-boot-starter`、`rocketmq-spring-boot-starter`、`knife4j-openapi3-jakarta-spring-boot-starter` 都是靠这套机制生效的；我在 `application.yml` 里改的就是它们的 `@ConfigurationProperties`。
- **常见错误回答**：
  - 「自动装配就是 `@ComponentScan` 扫描 jar 包」——扫描不到 jar 内的类，必须靠 imports 文件。
  - 只提 `spring.factories`，不知道 Boot 2.7+ 已改为 `AutoConfiguration.imports`。
  - 不知道 `@ConditionalOnMissingBean` 的作用。

#### Q3.5.8 Spring 的单例 Bean 是线程安全的吗？

- **面试官想听**：会不会在 Service 里乱放可变成员变量（这是新手最常见的线上 bug）。
- **参考答案要点**：
  1. **单例 ≠ 线程安全**。Spring 只保证"只有一个实例"，**不保证这个实例的状态在并发下安全**。
  2. **无状态 Bean 天然安全**：Service 里只有注入的依赖（不可变）和局部变量，方法内部各用各的栈空间，天然线程安全。**本项目的 Service 都是无状态的。**
  3. **有可变成员变量就不安全**：例如在 Service 里放 `private int count`、`private List<...> buffer`、`private SimpleDateFormat`（**`SimpleDateFormat` 本身不是线程安全的**，会解析出错乱结果）→ 必须改成局部变量、`ThreadLocal`（注意 remove）或 `DateTimeFormatter`（线程安全）。
  4. **本项目的实践**：
     - 所有 Service 用构造器注入 `final` 依赖，无状态；
     - `traceId` 用 **MDC（底层是 ThreadLocal）**，在 `Filter` 的 `finally` 里 `MDC.clear()`，避免线程池复用导致串号；
     - 需要每个请求独立的数据，一律用方法参数传递，不往成员变量上挂。
  5. **其他作用域**：`prototype` 每次新建（但仍可能被多个线程共享引用）、`request`/`session` 作用域是 ThreadLocal 包装（在异步线程里会失效）。
- **常见错误回答**：
  - 「Spring 的单例是线程安全的」——把"单例"和"线程安全"混淆。
  - 「加 `synchronized` 到 Service 方法上就安全了」——性能灾难。

#### Q3.5.9 拦截器（Interceptor）、过滤器（Filter）、AOP 有什么区别？项目里各用在哪？

- **面试官想听**：三者所处的位置和处理对象。
- **参考答案要点**：
  1. **归属不同**：`Filter` 是 **Servlet 规范**的组件（属于 Web 容器，由 `FilterChain` 调用）；`Interceptor` 是 **Spring MVC** 的组件（由 `DispatcherServlet` 在 `HandlerMapping` 之后调用）；`AOP` 是 **Spring 容器**层面的方法级增强（连非 Web 方法也能织入）。
  2. **执行顺序**：`Filter#doFilter`（前）→ `Interceptor#preHandle` → `HandlerAdapter` 调用 Controller → `Interceptor#postHandle` → `Interceptor#afterCompletion` → `Filter`（后）。**异常处理上**：`Interceptor#afterCompletion` 拿得到异常，`Filter` 只能靠 try-catch 包住整条链。
  3. **能力差异**：`Filter` 能拿到原始的 `ServletRequest`，可包装请求体（比如做请求日志、XSS 过滤）；`Interceptor` 能拿到 `HandlerMethod`（知道要执行哪个 Controller 方法），适合做**登录鉴权、权限校验、traceId、限流**；`AOP` 能拿到方法参数和返回值，适合做**事务、缓存、自定义注解、幂等**。
  4. **本项目用法**：
     - `Filter`：生成 **traceId** 并放入 MDC（放在最外层，保证后面所有日志都带 traceId）；
     - `Interceptor`：登录态校验（解析 JWT）、简单的接口访问日志；
     - `AOP`：`@RateLimit`、`@DistributedLock`、`@Idempotent`、操作日志记录；
     - Spring Security 的过滤器链在 `Filter` 层（比 `Filter` 更早还是更晚取决于 `FilterRegistrationBean` 的 order，`SecurityFilterChain` 通过 `DelegatingFilterProxy` 注册）。
  5. **一句话记忆**：**Filter 在最外层（容器级）、Interceptor 在 MVC 层（Handler 级）、AOP 在方法级（Bean 级）。**
- **常见错误回答**：
  - 「Filter 是 Spring 的，Interceptor 是 Servlet 的」——说反了。
  - 「AOP 可以替代 Filter 做请求日志」——AOP 拿不到原始请求上下文（需要额外注入 `RequestContextHolder`）。

### 3.6 Java 并发 / JVM（10 题）

#### Q3.6.1 线程池的核心参数有哪些？任务提交后的执行流程是什么？

- **面试官想听**：参数、流程、拒绝策略、以及"为什么不用 Executors"。
- **参考答案要点**：
  1. **七个参数**：`corePoolSize`、`maximumPoolSize`、`keepAliveTime`、`unit`、`workQueue`、`threadFactory`、`handler`（拒绝策略）。
  2. **执行流程（必须按顺序）**：
     ① 运行线程数 < core → **直接新建核心线程**执行；
     ② 否则任务**入 workQueue 排队**；
     ③ 队列满且线程数 < max → **新建非核心线程**；
     ④ 队列满且线程数 = max → **执行拒绝策略**。
     **关键易错点：是先入队，队满才扩容到 max，而不是"先扩到 max 再排队"**。这也是为什么用**无界队列**时 `maximumPoolSize` 永远不会起作用。
  3. **四种拒绝策略**：`AbortPolicy`（默认，抛 `RejectedExecutionException`）、`CallerRunsPolicy`（**由提交任务的线程自己执行**，起到反压作用）、`DiscardPolicy`（静默丢弃）、`DiscardOldestPolicy`（丢队首最老的再提交）。本项目自定义了一个"记录日志 + 抛业务异常 + 埋点计数"的策略。
  4. **为什么不用 `Executors`**：`newFixedThreadPool`/`newSingleThreadExecutor` 使用**无界 `LinkedBlockingQueue`**，任务堆积会导致 **OOM**；`newCachedThreadPool` 的 `maximumPoolSize = Integer.MAX_VALUE`，会**无限创建线程**导致 OOM。**阿里巴巴 Java 开发手册明确禁止用 `Executors` 创建线程池**，必须 `new ThreadPoolExecutor(...)` 显式指定参数。
  5. **线程数怎么定**：CPU 密集 → `N + 1`；IO 密集 → `2N` 或按公式 `N × (1 + 等待时间/计算时间)`；**最可靠的做法是压测**——从保守值开始加压，观察队列长度、RT、CPU。
  6. **`ThreadFactory` 一定要自定义**（给线程起名字 `seckill-pool-1`），否则 `jstack` 里全是 `pool-1-thread-1`，排查困难。
  7. **本项目的用法**：秒杀接口用**独立线程池隔离**（`seckillExecutor`，核心 8 / 最大 16 / 有界队列 200 / `CallerRunsPolicy`），避免秒杀把 Tomcat 线程池和主站业务打满；另有一个 `asyncExecutor` 做日志与通知。
- **常见错误回答**：
  - 「核心满了就扩到 max，max 满了才排队」——顺序错。
  - 「用 `Executors.newFixedThreadPool` 就行」——无界队列 OOM 风险。
  - 「线程数越大越好」——上下文切换开销会让吞吐下降。

#### Q3.6.2 ThreadLocal 的原理？为什么会内存泄漏？

- **面试官想听**：`ThreadLocalMap` 的结构 + 弱引用 key + `remove()` 的必要性。
- **参考答案要点**：
  1. **结构**：每个 `Thread` 里有一个 `ThreadLocal.ThreadLocalMap threadLocals`；Map 的 **key 是 `ThreadLocal` 对象的弱引用（`WeakReference<ThreadLocal<?>>`）**，**value 是强引用**。
  2. **为什么泄漏**：当外部对 `ThreadLocal` 的强引用消失（比如方法结束），**key 被 GC 回收变成 null，但 value 仍被 Thread → ThreadLocalMap → Entry 强引用着**，如果线程长期存活（**线程池场景**），value 就一直无法回收 → 内存泄漏。而且此时 entry 的 key 为 null，无法通过正常 API 访问到，只能靠 `expungeStaleEntry` 在后续操作时清理。
  3. **为什么 key 用弱引用**：如果 key 是强引用，只要线程活着，`ThreadLocal` 对象本身也永远回收不了，泄漏更严重（value 也一起泄漏）。弱引用至少让 key 可以被回收，并且 `set/get/remove` 时会顺带清理 key 为 null 的 entry。
  4. **正确用法**：**用完必须 `remove()`，且放在 `finally` 里**。在线程池里尤其重要，否则**不只是内存泄漏，还会造成数据串号**（下一个任务读到上一个任务的值）——本项目里 `MDC`（底层是 `ThreadLocal`）在 `Filter` 的 `finally` 中 `MDC.clear()` 就是为了这个。
  5. **其他坑**：
     - `InheritableThreadLocal` 能让子线程继承父线程的值，但**线程池里的线程是复用的，创建时机不确定，所以继承会失效**——要用阿里的 `TransmittableThreadLocal`（TTL）或手动传递。
     - 异步任务（`@Async`、`CompletableFuture`）中拿不到请求线程的 `ThreadLocal`（比如 Spring Security 的 `SecurityContext`、`RequestContextHolder`），需要显式传递。
  6. **本项目实践**：traceId 用 MDC 而不是自己写 ThreadLocal；需要在异步/MQ 消费端使用的上下文信息（userId、traceId）**显式放进消息头传递**。
- **常见错误回答**：
  - 「key 是强引用所以泄漏」——说反了，**key 是弱引用，value 才是强引用**，泄漏的是 value。
  - 「只要用 ThreadLocal 就会泄漏」——用完 `remove` 就没问题。
  - 说不出线程池场景为什么更严重。

#### Q3.6.3 synchronized 和 ReentrantLock 有什么区别？

- **面试官想听**：能否说到实现层面（monitor / AQS、锁升级）。
- **参考答案要点**：
  1. **层面不同**：`synchronized` 是 **JVM 关键字**（编译成 `monitorenter`/`monitorexit` 字节码，依赖对象头的 Mark Word + Monitor），**自动释放**（异常也会释放）；`ReentrantLock` 是 **JDK 层面的 API**（`java.util.concurrent`，基于 **AQS**），**必须在 `finally` 中 `unlock()`**。
  2. **功能差异**：

     | 能力 | synchronized | ReentrantLock |
     |---|---|---|
     | 可中断获取 | ✗ | ✓ `lockInterruptibly()` |
     | 超时获取 | ✗ | ✓ `tryLock(time, unit)` |
     | 公平锁 | ✗（非公平） | ✓ `new ReentrantLock(true)` |
     | 多条件队列 | ✗（一个 wait set） | ✓ 多个 `Condition` |
     | 可重入 | ✓ | ✓ |
  3. **`synchronized` 的锁升级**：无锁 → 偏向锁 → 轻量级锁（CAS 自旋）→ 重量级锁（操作系统互斥量，线程挂起）。**注意：偏向锁在 JDK 15 起已默认禁用、后续版本移除**，JDK 17 上讨论偏向锁要说明这一点（说错容易被抓）。`synchronized` 在 JDK 6 之后经过大量优化（自旋、锁消除、锁粗化），**在竞争不激烈时性能并不差**。
  4. **AQS 原理**：`state`（`volatile int`，表示锁状态/重入次数）+ **CLH 双向队列**（`Node` 存线程与 `waitStatus`）+ 模板方法（`tryAcquire/tryRelease`）。独占用 `acquire/release`，共享用 `acquireShared/releaseShared`（`Semaphore`、`CountDownLatch`、`ReadWriteLock` 都是共享/混合模式）。
  5. **怎么选**：只需要互斥、无高级需求 → `synchronized`（代码简洁、不易漏 unlock）；需要超时/中断/公平/多条件 → `ReentrantLock`。**本项目的分布式锁是跨进程的（Redisson），`synchronized`/`ReentrantLock` 只在单实例场景有意义**——被问到要主动区分。
- **常见错误回答**：
  - 「synchronized 是重量级锁，性能差」——JDK 6 后的老观念。
  - 「ReentrantLock 不需要手动释放」。
  - 不知道 `synchronized` 的锁升级（或不知道偏向锁已被废弃）。

#### Q3.6.4 CAS 是什么？ABA 问题怎么解决？

- **面试官想听**：底层指令 + 三大缺陷 + 解决方案。
- **参考答案要点**：
  1. **CAS**：`Compare And Swap`，**乐观锁**思路。包含三个值：内存地址 V、期望值 A、新值 B，只有 `V == A` 时才把 V 改成 B，返回是否成功。由 `Unsafe#compareAndSwapInt` 等 native 方法实现，底层是 CPU 的 **`cmpxchg` 指令**，在 x86 上配合 **`lock` 前缀**保证多核原子性。Java 通过 `AtomicInteger`、`AtomicReference`、`varhandle` 等暴露。
  2. **三大问题**：
     - **① ABA 问题**：值从 A 改成 B 又改回 A，CAS 无法察觉，可能造成错误（典型场景：链表/栈的节点被人挪走再放回来，指针看似没变）。**解法**：`AtomicStampedReference`（加版本号/时间戳）、`AtomicMarkableReference`（加 boolean 标记）。**注意：如果业务上"A→B→A"的结果与"A"等价（比如库存数只是加回来），ABA 无害**——要能说清"视场景而定"。
     - **② 自旋开销**：CAS 失败会循环重试，高竞争下 CPU 空转。**解法**：`LongAdder`（分段/Cell 数组，用空间换时间，适合高并发计数）、限制自旋次数、退化为锁。
     - **③ 只能保证一个变量的原子性**：多变量要用 `AtomicReference` 把多个字段封成一个不可变对象，或加锁。
  3. **本项目的关联**：单机并发用 `AtomicLong` 做计数/限流令牌（配合 `LongAdder` 统计）；**跨进程的原子性靠 Redis 单线程 + Lua，不靠 CAS**。
  4. 补充：`AtomicInteger#incrementAndGet` 底层就是 `for(;;) { if (compareAndSet(cur, cur+1)) return cur+1; }`。
- **常见错误回答**：
  - 「CAS 是加锁实现的」——恰恰是无锁（乐观），靠 CPU 指令。
  - 「ABA 用 `synchronized` 解决」——用版本号。
  - 不知道 `LongAdder` 为什么比 `AtomicLong` 快。

#### Q3.6.5 JMM 是什么？volatile 保证了什么？

- **面试官想听**：可见性/有序性/原子性三分 + happens-before + 内存屏障。
- **参考答案要点**：
  1. **JMM（Java 内存模型）**：定义了**多线程下共享变量的可见性规则**，抽象出"主内存 + 每个线程的工作内存"；它是一套**规范**，不是物理内存结构。
  2. **三大特性**：**原子性**（`synchronized`/`Atomic` 保证，`i++` 不是原子操作）、**可见性**（`volatile`/`synchronized`/`final` 保证）、**有序性**（`volatile`/`synchronized` 通过禁止重排序保证）。
  3. **volatile 保证**：**可见性**（写操作立即刷回主内存并使其他线程的副本失效）+ **有序性**（禁止指令重排）。**不保证原子性**——`volatile int i; i++` 依然线程不安全（因为 `i++` 是"读-改-写"三步）。
  4. **内存屏障**：写 volatile 前插 `StoreStore`、写后插 `StoreLoad`；读 volatile 后插 `LoadLoad`、`LoadStore`。这保证了屏障前后的指令不会被重排。
  5. **happens-before 规则**（能背 5 条以上很加分）：程序顺序规则、**监视器锁规则**（解锁先于后续加锁）、**volatile 变量规则**（写先于后续读）、**线程启动规则**（`start()` 先于线程内所有操作）、**线程终止规则**（线程所有操作先于 `join()` 返回）、传递性、`interrupt()` 规则、对象终结规则。
  6. **经典应用**：**DCL 单例为什么要加 volatile**——`instance = new Singleton()` 分三步（分配内存 → 初始化 → 赋值引用），2 和 3 可能重排，导致另一个线程拿到"引用非 null 但对象未初始化完成"的实例；`volatile` 禁止这个重排。
  7. **volatile vs synchronized**：前者轻量、只保证可见性与有序性、不阻塞；后者重量、保证原子性 + 可见性 + 有序性。
- **常见错误回答**：
  - 「volatile 保证原子性」——最常见错误。
  - 「JMM 就是 JVM 的内存结构（堆、栈）」——那叫运行时数据区，JMM 是并发规范。

#### Q3.6.6 常见的垃圾收集器有哪些？怎么选？

- **面试官想听**：分代 + 收集器演进 + 停顿目标 + **JDK 17 的默认**。
- **参考答案要点**：
  1. **分代**：新生代（Eden : Survivor0 : Survivor1 = **8:1:1**，默认 `-XX:SurvivorRatio=8`）+ 老年代；对象优先在 **Eden + TLAB** 分配。
  2. **对象晋升**：① 年龄达到 `-XX:MaxTenuringThreshold`（默认 15，CMS 是 6）；② **动态年龄判断**（Survivor 中相同年龄对象总和 > Survivor 一半，则 ≥ 该年龄的直接晋升）；③ **大对象直接进老年代**（`-XX:PretenureSizeThreshold`）；④ Survivor 空间不足时**分配担保**。
  3. **收集器**：

     | 收集器 | 区域 | 算法 | 特点 |
     |---|---|---|---|
     | Serial / Serial Old | 新生代 / 老年代 | 复制 / 标记-整理 | 单线程，客户端模式 |
     | ParNew | 新生代 | 复制 | Serial 的多线程版，配合 CMS |
     | Parallel Scavenge / Parallel Old | 新生代 / 老年代 | 复制 / 标记-整理 | **JDK 8 默认**，关注吞吐量 |
     | **CMS** | 老年代 | 标记-清除 | 并发收集、低停顿；缺点：**浮动垃圾、内存碎片、Concurrent Mode Failure**、三色标记用增量更新 |
     | **G1** | 全堆（Region 化） | 复制 + 标记-整理（整体） | **JDK 9+ 默认**；可预测停顿 `-XX:MaxGCPauseMillis`；Young GC / Mixed GC / Full GC；**SATB 原始快照**；`Humongous` 大对象区 |
     | **ZGC** | 全堆 | 并发标记-整理（染色指针 + 读屏障） | JDK 15 起生产可用，**停顿 < 1ms（与堆大小无关）**，JDK 17 已具备（分代 ZGC 在 JDK 21）；吞吐略低 |
     | Shenandoah | 全堆 | 并发整理 | RedHat 主导，低停顿 |
  4. **怎么选**：**JDK 17 上用 G1（默认）即可**；堆很大（几十上百 G）且要求极低停顿 → ZGC；追求吞吐（批处理）→ Parallel。**面试时要说："我本地/项目用默认的 G1，因为堆不大（`-Xmx2g`），G1 的 Region 化和可预测停顿够用。"**
  5. **三色标记与漏标**：并发标记时用户线程还在改引用，会漏标 → **CMS 用增量更新（Incremental Update，重新标记时重扫被修改的引用）、G1/SATB 用原始快照（Snapshot At The Beginning，记录旧引用，牺牲浮动垃圾）**。这个对比答出来非常加分。
  6. **常见参数**：`-Xms`（初始堆，**建议等于 `-Xmx` 避免动态扩容抖动**）、`-Xmx`、`-Xmn`/`-XX:NewRatio`、`-XX:MetaspaceSize`、`-XX:+UseG1GC`、`-XX:MaxGCPauseMillis=200`、`-XX:+HeapDumpOnOutOfMemoryError`、`-XX:+PrintGCDetails`（JDK 9+ 用 `-Xlog:gc*`）。
- **常见错误回答**：
  - 「JDK 8 默认是 CMS」——是 Parallel Scavenge + Parallel Old。
  - 「G1 是完全并发无停顿的」——Young GC 和 Final Mark 有 STW。
  - 说不出 CMS 的浮动垃圾和碎片问题。

#### Q3.6.7 线上 CPU 飙高 / 内存泄漏怎么排查？

- **面试官想听**：完整的工具链和步骤，**这题最能体现"你上过线"**。
- **参考答案要点**：
  1. **CPU 飙高**：
     ```
     top -Hp 【pid】            # 找到占用最高的线程 id（十进制）
     printf '%x\n' 【tid】      # 转成十六进制
     jstack 【pid】 > stack.txt  # 在文件里搜这个十六进制 nid
     ```
     看该线程栈在干什么：常见是**死循环、频繁 Full GC（`VM Thread`/`GC task` 占比高）、锁竞争自旋、正则回溯**。GC 问题转 jstat 分析。
  2. **内存泄漏 / OOM**：
     - **先看 GC 趋势**：`jstat -gcutil 【pid】 1000`，若 **Full GC 后老年代占用不下降** → 大概率泄漏。
     - **看对象分布**：`jmap -histo:live 【pid】 | head -30`。
     - **导堆**：`jmap -dump:format=b,file=heap.hprof 【pid】`（**会 STW，线上慎用**；更推荐启动参数 **`-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=...`** 让 OOM 时自动 dump）。
     - **分析**：MAT / JProfiler 看**支配树（Dominator Tree）和 Leak Suspects**，或 VisualVM；重点看"谁在 GC Roots 上强引用着这些对象"。
     - **其他 OOM 类型**：`Metaspace`（类加载器泄漏/动态代理类过多）、`Direct buffer memory`（`ByteBuffer.allocateDirect` 未释放）、`unable to create new native thread`（线程数过多）、`GC overhead limit exceeded`。
  3. **本项目的常见嫌疑对象**（能结合自己的项目说最好）：
     - **无上限的本地缓存**（`HashMap` 当缓存用）；
     - **ThreadLocal 未 `remove`**（MDC）；
     - **定时任务里批量查全表**（`select *` 几十万条进内存）；
     - **`SimpleDateFormat` 静态共享**导致数据错乱（不是泄漏但是经典 bug）；
     - **连接/流未关闭**（`try-with-resources` 解决）。
  4. **在线排查工具补充**：`arthas`（`dashboard`、`thread -n 3`、`heapdump`、`trace`、`watch`、`jad`）——**能提 arthas 会显得很有实战感**，`jcmd`、`jvmtool`、`AsyncProfiler` 也算加分。
  5. **预防**：JVM 参数统一（`-Xms=-Xmx`、开 HeapDump）、监控（GC 次数与耗时、老年代占用、线程数）、压测时观察、代码评审时禁止无界集合。
- **常见错误回答**：
  - 「重启一下就好了」。
  - 「`jmap -dump` 无脑在生产用」——会 STW。
  - 只会 `top`，不会 `jstack` 关联线程栈。

#### Q3.6.8 类加载过程和双亲委派机制？

- **面试官想听**：五个阶段 + 双亲委派的流程和好处 + 为什么会被打破。
- **参考答案要点**：
  1. **类加载过程**：**加载**（读字节码 → 方法区/元空间 → 生成 `Class` 对象）→ **验证**（文件格式、元数据、字节码、符号引用验证）→ **准备**（为静态变量分配内存并赋**零值**，`static final` 常量在编译期就放进常量池）→ **解析**（符号引用 → 直接引用，可能延迟到初始化时）→ **初始化**（执行 `<clinit>`，即静态变量赋值与静态代码块，**父类先于子类**）。
  2. **触发初始化的时机**（主动引用）：`new`、读写静态字段/调用静态方法、反射（`Class.forName`）、初始化子类时先初始化父类、`main` 类、`MethodHandle`/`invokedynamic`。
  3. **类加载器层次**：**Bootstrap（`java.lang.*` 等核心类，C++ 实现，`getClassLoader()` 返回 null）→ Platform/Extension（JDK 9 后改名，`jdk.internal.loader.ClassLoaders$PlatformClassLoader`）→ Application/System（classpath）→ 自定义**。
  4. **双亲委派**：`loadClass` 先 `findLoadedClass`，再委派 `parent.loadClass`，父加载器找不到才自己 `findClass`。**好处**：① 避免类重复加载；② **安全**——用户自己写一个 `java.lang.String` 也不会被加载，保证核心类库不被篡改。
  5. **打破双亲委派**：
     - **线程上下文类加载器（TCCL）**：SPI 场景（JDBC 的 `DriverManager` 在 Bootstrap 加载，但实现类在 classpath，只能靠 `Thread.currentThread().getContextClassLoader()` 反向委派）。
     - **Tomcat**：每个 WebApp 一个 `WebappClassLoader`，**优先自己加载**，实现应用间隔离与热部署。
     - **OSGi / 模块化**：网状委派。
     - 自定义 `ClassLoader` 覆写 `loadClass` 是最直接的打破方式。
  6. **本项目的关联**：Spring Boot 的**可执行 jar 用 `LaunchedURLClassLoader`** 加载 `BOOT-INF/classes` 和 `BOOT-INF/lib`，这也是打破双亲委派的一个典型例子（能从"我打包成 fat jar 启动"讲到这点会很亮）。
- **常见错误回答**：
  - 「准备阶段给静态变量赋初值」——是赋**零值**，赋真实值在初始化阶段。
  - 「双亲委派是继承关系」——是**组合**（`parent` 字段），不是继承。

#### Q3.6.9 强、软、弱、虚引用分别有什么用？

- **面试官想听**：四种引用的回收时机与典型用途。
- **参考答案要点**：
  1. **强引用**：`new` 出来的对象，**只要强引用还在就绝不回收**，宁可 OOM。内存泄漏通常就是"该断的强引用没断"。
  2. **软引用 `SoftReference`**：**内存不足时（即将 OOM 前）回收**。适合做**缓存**（图片缓存、本地对象缓存）；注意软引用被回收的时机不确定，不能用于要求"一定命中"的场景。
  3. **弱引用 `WeakReference`**：**只要发生 GC 就回收**（无论内存是否充足）。用途：`ThreadLocalMap` 的 key、`WeakHashMap`、`ClassLoader` 相关、监听器/注册表（避免对象无法释放）。
  4. **虚引用 `PhantomReference`**：**无法通过它获取对象**（`get()` 永远返回 null），唯一用途是**在对象被回收时收到通知**（配合 `ReferenceQueue`），用于管理**堆外内存**（`DirectByteBuffer` 的 `Cleaner` 机制就是用它来释放直接内存）。`finalize()` 的替代思路。
  5. **引用队列 `ReferenceQueue`**：软/弱/虚引用都可以注册队列，对象被回收后引用本身入队，用于做清理逻辑（这是"GC 后回调"的正规做法）。
  6. **本项目关联**：Caffeine 本地缓存内部用 **`WeakKey`/`SoftValue` 的包装 + 引用队列**做淘汰辅助；`ThreadLocal` 的泄漏问题根源就是弱引用 key + 强引用 value。
- **常见错误回答**：
  - 「软引用会立即被回收」——是内存不足时。
  - 「虚引用能拿到对象」——不能。

#### Q3.6.10 AQS 的原理是什么？

- **面试官想听**：`state` + CLH 队列 + 模板方法，以及哪些类基于它。
- **参考答案要点**：
  1. **核心三要素**：
     - **`volatile int state`**：同步状态。`ReentrantLock` 用它表示**重入次数**（0 = 未锁）；`Semaphore` 表示**可用许可数**；`CountDownLatch` 表示**剩余计数**；`ReentrantReadWriteLock` 用**高 16 位读锁、低 16 位写锁**。
     - **CLH 变体的双向 FIFO 队列**：`Node` 记录 `thread`、`waitStatus`（`SIGNAL`/`CANCELLED`/`CONDITION`/`PROPAGATE`）、`prev`/`next`；获取失败的线程包装成 Node 入队并 `LockSupport.park()`。
     - **模板方法**：`tryAcquire/tryRelease`（独占）、`tryAcquireShared/tryReleaseShared`（共享）由子类实现；`acquire/release` 由 AQS 定义流程（**模板方法模式**）。
  2. **独占获取流程**：`tryAcquire` 失败 → `addWaiter` 入队 → `acquireQueued` 中自旋：前驱是 head 就再试 `tryAcquire`，否则 `shouldParkAfterFailedAcquire` 把前驱状态置为 `SIGNAL` 后 `park()`；释放时 `tryRelease` 成功 → 唤醒 head 的后继节点。
  3. **共享模式**：`CountDownLatch`（`state` 减到 0 时 `releaseShared` 唤醒所有等待者）、`Semaphore`（`state` 表示许可，`tryAcquireShared` 用 CAS 减）。
  4. **Condition**：`await()` 把线程包装成 `CONDITION` 节点放入**条件队列**，释放锁并 `park`；`signal()` 把节点从条件队列转移到同步队列。
  5. **公平与非公平**：非公平锁在 `tryAcquire` 时**先直接 CAS 抢一次**（可能插队），公平锁会先检查 `hasQueuedPredecessors()`。**非公平吞吐更高**（减少线程唤醒开销），但可能饥饿。
  6. **基于 AQS 的类**：`ReentrantLock`、`ReentrantReadWriteLock`、`Semaphore`、`CountDownLatch`、`CyclicBarrier`（内部用 `ReentrantLock` + `Condition`）、`ThreadPoolExecutor.Worker`（自己实现 `AbstractQueuedSynchronizer` 做 `tryAcquire/tryRelease`）。
  7. **本项目关联**：单机限流/计数用 AQS 家族（`Semaphore` 控制并发、`CountDownLatch` 做压测/并发测试同步）；**跨进程的锁用 Redisson，Redisson 的 `RLock` 实现了 `java.util.concurrent.locks.Lock` 接口，但底层是 Redis + Lua + 发布订阅，不是 AQS**——能主动点出这个区别很加分。
- **常见错误回答**：
  - 「AQS 是一个锁」——是**同步器框架**，锁由子类实现。
  - 「state 就是锁的持有者」——是状态（重入次数/许可数/计数）。
  - 不知道 `LockSupport.park/unpark`。

### 3.7 项目设计类（10 题）

#### Q3.7.1 为什么不用微服务？

- **面试官想听**：**这题是送分题也是送命题**。答"因为微服务难"是减分，答出取舍维度是加分（对应 ADR-1）。
- **参考答案要点**：
  1. **先给结论**：这是个**单人、校招、演示型项目**，我评估过微服务，结论是**当前阶段不引入**。
  2. **四个维度的理由**：
     - **业务规模**：单机单库、日订单量【__】级别，垂直拆分的收益（独立扩容、独立部署）根本体现不出来；拆完反而要处理分布式事务、跨服务调用、链路追踪，**复杂度上升 80% 而收益接近 0**。
     - **团队规模**：微服务的核心价值之一是"让多个团队独立开发部署"。我一个人开发，拆开只是把方法调用变成 RPC，**把一个进程内的编译器检查变成了运行期故障**。
     - **一致性成本**：跨服务就要考虑分布式事务。Seata AT 要 `undo_log` + 全局锁，性能损耗大且被 `00` §4.1 明确排除；TCC/Saga 对业务侵入极大。而我现在用**本地消息表 + 最终一致**，在单库里是"同一个事务"，天然没有这个问题。
     - **可调试性**：单体一个断点能走完整个下单链路；微服务要起四五个进程，**调试成本会挤占我把秒杀做深的时间**——而秒杀才是这个项目真正的亮点。
  3. **主动给演进路径（这是关键加分点）**：我不排斥微服务，我做了两件为演进铺路的事——① **模块边界清晰**：`common/model/dao/service/web` 分层 + `com.shopping.service` 下按 `auth/user/product/cart/inventory/trade/payment/promotion` 划包，**包边界就是未来的服务边界**；② **预留 `merchant_id`**：商品、订单、库存等六张核心表从第一版 DDL 就带 `merchant_id`，将来从自营演进到 B2B2C 多商户**不需要重构核心表**。
  4. **如果真要做微服务我会怎么拆**（面试官很爱追问）：
     - 先按**业务能力**拆：`auth`、`product`、`trade`（下单+订单）、`inventory`、`promotion`（含秒杀）、`payment` —— **不按技术分层拆**（不要拆成"controller 服务""service 服务"）；
     - `trade` 和 `inventory` 的**一致性最难**，用本地消息表/事务消息 + 对账；秒杀库存**不拆出去**，因为它和商品库存强耦合；
     - 引入 Nacos（注册配置）+ Gateway（统一入口）+ Sentinel（限流熔断）+ 链路追踪（SkyWalking），**但必须先有真实流量压力再拆，否则就是过度设计**。
  5. **一句话收尾**：**"我的判断标准是：技术选型要匹配当前的数据量、团队规模和可维护性。我宁愿把单体做扎实，也不想做一个我讲不清楚的分布式单体。"**
- **常见错误回答**：
  - 「微服务太复杂了，我不会」——等于承认能力不足。
  - 「微服务性能更好」——**微服务不会让系统更快，只会让扩容更灵活**（多一次网络调用通常更慢）。
  - 「我们老师/视频说单体就够」——没有自己的判断。

#### Q3.7.2 为什么不用 Seata？跨模块一致性怎么保证？

- **面试官想听**：ADR-7 的取舍 + 是否真懂"最终一致"。
- **参考答案要点**：
  1. **前提事实**：本项目是**单机单库**，`wms_stock`、`oms_order`、`sms_seckill_record` 都在**同一个 MySQL 实例的同一个库**里，所以"扣库存 + 创建订单"**本来就是本地事务**，压根不存在分布式事务。
  2. **Seata 的成本**：`AT` 模式需要额外建 `undo_log` 表、要维护**全局锁**、有 `TC/TM/RM` 三个角色和一个独立部署的 Seata Server，**性能损耗（全局锁 + 前后镜像）与运维成本对一个校招项目完全不成比例**；`TCC` 需要业务写三个方法（Try/Confirm/Cancel），侵入性更强；`Saga` 要写状态机。
  3. **我实际用的方案**：**本地消息表（`sys_message`）+ 定时重试 + 消费端幂等 + 对账任务**。
     - 事务内写业务数据 + 写一条待发送消息 → 提交；
     - 定时任务扫描待发送消息投递给 RocketMQ，成功后改状态；
     - 消费端保证幂等（唯一索引 / 状态机 CAS）；
     - 失败重试到上限就告警 + 人工介入，另有**每日对账任务**兜底。
  4. **为什么这样"更好讲"**：① 逻辑完全在我自己代码里，面试官问任何一个环节我都能给出代码位置；② **能说清它的代价**：有延迟（秒级）、需要额外的表和定时任务、极端情况下要人工介入；③ 它是**通用的可靠消息基础设施**，支付回调、库存补偿、积分发放都能复用。
  5. **如果被追问"什么场景下你会用 Seata"**：当业务**真的跨多个库/多个服务**、且不允许长时间不一致（比如资金类）时，`AT` 适合"对业务侵入小、能接受性能损耗"的场景；更高一致性要求的金融场景应该用 **TCC**（明确的三阶段补偿）或者干脆**设计上避免跨库**（比如把强一致的数据放在同一个库）。
  6. 补充一句非常加分的话：**"其实最好的分布式事务方案是不要有分布式事务——把必须强一致的边界收敛到同一个库里。"**
- **常见错误回答**：
  - 「Seata 太重了所以不用」——没说清"我这里是单库，本来就不需要"。
  - 「我用 `@Transactional` 保证分布式事务」——本地事务管不了跨库/跨服务。
  - 「最终一致就是不用管，一会儿就一致了」——必须有**重试 + 幂等 + 对账**三件套。

#### Q3.7.3 订单状态机怎么设计？怎么保证状态不被乱改？

- **面试官想听**：ADR-4 的落地细节 + 并发安全（CAS）。
- **参考答案要点**：
  1. **状态定义**（枚举放 `common.enums`）：`待支付(1) → 已支付(2) → 待发货(3) → 已发货(4) → 已完成(5)`；旁支：`已取消(6)`（超时/用户主动）、`已退款(7)`（售后）。
  2. **流转规则集中管理**：用一张**状态转移表**（`Map<状态, Set<允许的下一个状态>>` 或枚举里的 `canTransferTo`）描述合法流转，而不是散落各处的 `if-else`。
  3. **统一入口**：`OrderStateMachine#transfer(orderNo, fromStatus, toStatus, operator, remark)`：
     - ① 校验 `canTransfer(from, to)`，非法直接抛 `BizException`；
     - ② **DB 层 CAS**：`UPDATE oms_order SET status = #{to}, update_time = NOW() WHERE order_no = #{orderNo} AND status = #{from}`，**`affectedRows == 0` 说明状态已被别人改过 → 抛异常或幂等返回**；
     - ③ 写 `oms_order_operate_history`（`order_no, from_status, to_status, operator, remark, create_time`）作为完整审计流水；
     - ④ 触发后续动作（发延迟消息、发通知）**放在事务提交之后**（`afterCommit`）。
  4. **为什么用状态机**：① 避免非法流转（"已取消"的订单被改成"已发货"）；② 新增状态时改动集中；③ **CAS 更新天然解决并发**（支付回调和超时关单同时到达时，只有一个能成功）。
  5. **为什么不用工作流引擎**（如 Flowable/Activiti）：订单状态是**线性加少量旁支**的简单流转，引入工作流引擎要建十几张表、写 BPMN 文件，**复杂度与收益完全不成比例**；工作流引擎适合人工审批链长、流程经常变（如 OA 审批）的场景。
  6. **状态与时间统一口径**：所有时间字段用 `datetime`/`timestamp` 且统一时区（本项目统一 UTC+8 存储并在配置里锁定），避免"超时关单算错时间"。
- **常见错误回答**：
  - 「用 switch-case 判断当前状态」——没有集中约束，容易漏分支、写出非法流转。
  - 「先 select 查状态，再 update」——check-then-act，并发下会双写。
  - 「用状态机框架（Spring StateMachine）」——能提，但要说明**为什么本项目不需要**（引依赖、增加理解成本）。

#### Q3.7.4 幂等是怎么做的？（项目级回答）

- **面试官想听**：能不能把幂等做成"分层机制"，而不是单点方案。
- **参考答案要点**：
  1. **先列场景**：① 用户重复点击下单；② 支付平台重复回调；③ MQ 重复消费；④ 库存回滚重复执行；⑤ 超时关单与支付回调并发。
  2. **分层方案**：

     | 层 | 手段 | 适用 |
     |---|---|---|
     | 前端 | 按钮置灰 + 一次性 token | 降低误触，**不可信** |
     | 接口 | 自定义 `@Idempotent`（AOP）：`SETNX idem:{业务标识} 1 EX 10`，冲突则直接返回"处理中" | 防重复提交 |
     | 业务 | **状态机 CAS**（`WHERE status = 旧状态`）、业务唯一键校验 | 状态流转类 |
     | 存储 | **唯一索引**（`uk(user_id, activity_id, sku_id)`、`uk(business_no)`、`uk(out_trade_no)`） | **最后一道防线** |
     | 对账 | 定时核对流水与余额/库存 | 兜底 |
  3. **`@Idempotent` 的实现细节（要能讲清并发陷阱）**：
     - 幂等键从哪来：`userId + 接口 + 关键参数 hash`（不能只用 userId，否则同一用户不同商品会被误拦）。
     - **`SETNX` 成功才执行业务**；执行业务失败时**要删掉 key**（否则用户无法重试），但这会引入"删 key 与并发请求"的窗口，所以最终仍靠 DB 唯一索引兜底。
     - key 的 TTL 要覆盖"最长的重试窗口"，比如 10 秒；不能太长（用户 5 分钟后重试应被允许）。
     - 返回"重复请求"时用统一的业务错误码，前端提示"请勿重复提交"。
  4. **支付回调的幂等（最典型的场景）**：
     - 先落 `pay_notify_log`（`out_trade_no` 唯一索引）记录原始报文 → 验签 → **`UPDATE pay_payment SET status = 已支付 WHERE out_trade_no = ? AND status = 待支付`**，`affectedRows = 0` 就直接返回"成功"给支付平台（**注意：重复回调必须返回成功，否则平台会一直重试**）。
  5. 一句总结：**"幂等的本质是把'是否处理过'的判断交给一个具备原子性的存储——唯一索引或 CAS 更新，而不是应用层的 `select` 判断。"**
- **常见错误回答**：
  - 「用 Redis 的 `setnx` 就够了」——没说失败时删 key、没说 DB 兜底。
  - 「用 `select` 查一下有没有处理过」——check-then-act。
  - 重复回调时返回失败给支付平台 → 导致平台无限重试。

#### Q3.7.5 库存扣减放在下单时还是支付时？各自的风险？

- **面试官想听**：两种模式的取舍（这是电商设计题的经典分水岭）。
- **参考答案要点**：
  1. **下单减库存（本项目采用）**：
     - 优点：**不会超卖**——库存一被占用，其他人就买不到，用户下单时的体验是确定的。
     - 缺点：**恶意下单占库存**（下 100 单不付款，30 分钟后才释放）；用**限购（每人 N 件）+ 超时关单回滚 + 风控**缓解。
     - 实现：下单事务内 `UPDATE wms_stock SET stock = stock - 1 WHERE sku_id = ? AND stock >= 1`，同时写 `wms_stock_log`；超时关单时把库存加回（**按流水号幂等**）。
  2. **支付减库存**：
     - 优点：不会被占库存。
     - 缺点：**有超卖风险**（多人同时支付，可能库存不够），需要额外的预占/排队机制。
  3. **预占 + 支付确认（更工程的方案）**：`wms_stock` 拆成 `stock_available`（可售）和 `stock_locked`（锁定）两列；下单时 `available -1, locked +1`（条件更新 `WHERE stock_available >= n`）；支付成功后 `locked -1`（真正扣掉）；超时/取消则 `locked -1, available +1`。**超时释放必须幂等**。这样既能防超卖，又能明确区分"已卖"和"被占"。
  4. **本项目的实际选择与理由**：Phase 2 用**下单减库存 + 超时回滚**（简单直观、闭环完整、便于演示）；秒杀场景用 **Redis 预扣 + DB 条件更新**（因为秒杀要先过滤掉 99% 的请求，不能直接怼 DB）。
  5. **必须补一句"回滚也要幂等"**：超时关单和用户主动取消可能并发，两个都去加库存就会多卖；用 `wms_stock_log` 里"回滚"类型的流水唯一 + 订单状态 CAS 保证只回滚一次。
- **常见错误回答**：
  - 「下单减库存不会超卖，所以最大问题是恶意下单」之后答不出缓解方案。
  - 「用支付减库存 + 加锁」——加锁只能解决单机，且锁住库存行会让并发极差。
  - 「超时关单用定时任务扫表」——可以用，但要能对比 RocketMQ 延迟消息（ADR-5）。

#### Q3.7.6 优惠券怎么防超发？领取和使用的一致性怎么保证？

- **面试官想听**：能不能把秒杀那套思路迁移到另一个场景（**举一反三**）。
- **参考答案要点**：
  1. **防超发**：
     - `sms_coupon` 有总量，RocketMQ/Redis 预热后，用 **Redis + Lua** 原子判断"是否已领过 + 剩余量 > 0 + 扣减 + 记录 `(userId, couponId)` 集合"；
     - DB 层 `UPDATE sms_coupon SET remain = remain - 1 WHERE id = ? AND remain >= 1` 兜底；
     - `sms_coupon_record` 上建 **`uk(user_id, coupon_id)`（限领一张）** 或 `uk(user_id, coupon_id, batch_no)`（按批次限领）。
  2. **库存与优惠券的区别**：优惠券是**"发出去的数量上限"**，不是"实物库存"，所以不需要像库存那样精细的回滚；但要注意**"发出去的券可能被退回"**（活动取消/订单退款）→ 退回也要幂等。
  3. **使用一致性（领了券、下单用券）**：
     - 下单时**锁定券**：`UPDATE sms_coupon_record SET status = 已锁定, order_no = ? WHERE id = ? AND status = 未使用 AND user_id = ?`（CAS，`affectedRows = 0` 说明券已被用）；
     - 支付成功 → 把券状态改为**已使用**；订单取消/超时 → 改回**未使用**并清空 `order_no`；
     - 全部靠**状态机 CAS**，不用分布式锁。
  4. **价格计算**：下单时把**优惠金额、券ID 快照写进 `oms_order`**（而不是运行时再算），避免后续改活动导致历史订单金额变化——**订单要存价格的"快照"，这是电商铁律**（商品名、SKU 规格、单价、优惠金额都要快照到 `oms_order_item`）。
  5. 用一句话把话题引回秒杀：**"防超发和防超卖是同一个套路：Redis 原子预扣做过滤、DB 条件更新做权威扣减、唯一索引做最后防线。"**
- **常见错误回答**：
  - 「查一下券的余额，够就减一」——check-then-act。
  - 「用分布式锁锁住优惠券」——券有几十万张，锁粒度太粗。
  - 订单不存价格快照，直接关联 `pms_sku` 查现价 → 商品改价后历史订单金额全变。

#### Q3.7.7 如果重做这个项目，你会改什么？

- **面试官想听**：**反思能力**。这题是"送分题"，答不出来（"没什么要改的"）是最差的答案。
- **参考答案要点**（挑 3~4 条，按你实际做过的说）：
  1. **把秒杀入口彻底异步化**：现在接口是同步返回"抢购结果"，可以改成"返回排队号 + 前端轮询/SSE 推送结果"，让接口 RT 与落库彻底解耦（对应 Q3.1.9 的思路）。
  2. **把"库存流水 + 对账任务"提到一等公民**：一开始我只把 `wms_stock_log` 当日志表，后来发现它才是**幂等和对账的依据**。重做的话我会在设计阶段就定义清楚流水类型（扣减/回滚/锁定/释放）和唯一键，并**上线第一天就跑对账任务**。
  3. **traceId 打通异步链路**：把 traceId 放进 RocketMQ 消息头，消费端从消息头恢复到 MDC，这样"用户点击 → 秒杀 → MQ → 落库"能串成一条完整链路，排查效率提升明显（现在异步段是断的）。
  4. **加集成测试**：用 **Testcontainers** 启动真实的 MySQL/Redis，把"并发抢购 100 件商品，最后库存为 0 且订单数 = 100"写成**自动化并发测试**——比人工压测更可靠，也更能放进 CI。
  5. **配置外置 + 功能开关**：秒杀开关、限流阈值、降级开关都做成可动态调整的（现在只能改配置重启），出问题能一键兜底。
  6. **接口幂等前置统一**：把 `@Idempotent` 的幂等键生成规则做成可配置的 SpEL 表达式（像 `@Cacheable` 的 key 那样），而不是每种业务手写。
  7. **数据一致性监控**：把"Redis 库存 vs DB 库存 vs 订单数"做成一个定时巡检 + Prometheus 指标 + 告警，而不是等出问题才去查。
  8. **（诚实边界）**C 端商城前台（`Vue 3 + Vite + Vant`）我**只做了商品列表、详情、购物车、下单结算 4 个页面**——这是刻意取舍：演示动线只需要这 4 页就能走完一次完整购物，其余页面对求职没有增量价值。如果时间再多一点，我会补个人中心、地址管理、订单列表、评价，并给这 4 页补上端到端的自动化测试。
- **常见错误回答**：
  - 「没什么要改的，已经很完善了」——**这是最差的答案**，说明没有反思能力或者项目不是自己做的。
  - 「改成微服务」——见 Q3.7.1，且"重做"的重点应该是具体问题而不是换架构。
  - 改的方向全是"加技术"（加 ES、加分库分表）而不是"改设计缺陷"。

#### Q3.7.8 你的接口是怎么设计的？统一返回和异常处理怎么做的？

- **面试官想听**：工程规范意识（应届生最容易忽略，答好很加分）。
- **参考答案要点**：
  1. **路径规范**：C 端 `/api/app/**`、管理端 `/api/admin/**`（与 `00` 号文档 §6 一致）；资源用名词复数（`/api/app/orders`、`/api/app/carts/items`），动作用 HTTP 方法表达（GET 查询、POST 创建、PUT 更新、DELETE 删除），少量"动作型"接口用动词（`POST /api/app/orders/{orderNo}/cancel`、`POST /api/app/seckill/{activityId}`）。
  2. **统一响应 `Result<T>`**：`{ code, message, data, traceId }`；`code` 用业务错误码枚举（`A0001 库存不足`、`A0002 已参与过`），**不要用 HTTP 状态码表达业务错误**（业务失败返回 HTTP 200 + 业务码，鉴权失败用 401/403）。
  3. **分页 `PageResult<T>`**：`{ total, pageNum, pageSize, list }`；查询条件用 `Query` 对象（放 `model` 的 `query` 包）。
  4. **全局异常处理**：`@RestControllerAdvice` + `@ExceptionHandler`：
     - `BizException` → 返回对应业务码，日志 WARN（**业务异常不打堆栈**，否则日志爆炸）；
     - `MethodArgumentNotValidException`/`BindException`（参数校验）→ 返回 400 + 具体字段错误（`@Valid` + `@NotBlank/@Min` 等 Jakarta Validation 注解）；
     - `DuplicateKeyException` → 转成业务码（如"已参与过"）；
     - 兜底 `Exception` → 返回 500 + traceId，**日志 ERROR 打完整堆栈**，但**响应里绝不能带堆栈**（安全）。
  5. **参数校验**：`@Valid` + `jakarta.validation` 注解；分组校验（`@Validated(groups)`）区分新增和更新；秒杀参数还要做业务校验（活动是否存在、时间是否在窗口内）。
  6. **文档**：Knife4j（基于 springdoc）注解 `@Tag`/`@Operation`/`@Schema`；**生产环境关闭**（`springdoc.api-docs.enabled=false`）或加鉴权，避免暴露接口。
  7. **其他规范**：接口**必须幂等**的加 `@Idempotent`；日志打 `traceId`；敏感字段（手机号、身份证）脱敏；写操作统一在 Service 层做权限校验（不能只靠前端隐藏按钮）。
- **常见错误回答**：
  - 「返回 map 或直接返回对象」——没有统一结构，前端无法统一处理。
  - 「异常直接往外抛」——用户看到的就是 500 堆栈。
  - 「管理端接口不做权限校验，前端会隐藏菜单」——**水平越权**是校招项目最常见的严重漏洞。

#### Q3.7.9 你这个项目最难的地方是什么？你最大的收获是什么？

- **面试官想听**：真实感 + 成长性。**这题几乎 100% 会被问**，必须有准备。
- **参考答案要点**（选一个你真正做过的，下面给三个可选素材）：
  1. **素材 A：Redis 预扣与 DB 扣减不一致（最推荐）**
     - 现象：压测后对账发现"少卖"——Redis 库存少了但订单没生成。
     - 定位：看 `sys_message` 里有失败记录，消息发送超时 + 应用重启导致内存里的重试丢失。
     - 解决：把"发消息"落成**本地消息表状态机**（事务内写入、定时任务扫描、指数退避重试、超上限告警），并加每日对账任务。
     - 收获：**"异步链路的可靠性，靠的是本地持久化的状态机，而不是内存里的重试。"**
  2. **素材 B：MySQL 行锁竞争导致秒杀接口 RT 飙升**
     - 现象：压测第一轮 QPS 只有【】，`SHOW ENGINE INNODB STATUS` 里大量锁等待；`jstack` 显示线程都卡在 `update wms_stock`。
     - 定位：`EXPLAIN` 发现当初 `wms_stock` 上只有 `uk(sku_id)` 但我的 SQL 里带了一个未加索引的 `AND status = 1`，导致**锁范围扩大**（虽然走了 sku_id 索引，但过滤条件复杂化让优化器行为变化）；同时事务里还做了写日志的额外操作，事务过长。
     - 解决：把过滤条件下推/移出 SQL、缩短事务、把库存扣减前置到 Redis 预扣。
     - 收获：**"高并发下最贵的不是 CPU，是锁。"**
  3. **素材 C：逻辑删除与唯一索引冲突**
     - 现象：测试注销账号后无法再注册同名账号，报 `Duplicate entry`。
     - 定位：唯一索引不含 `deleted`，逻辑删除的行仍占位。
     - 解决：把 `deleted` 改成 `bigint` 存"删除时刻的时间戳/该行主键"，唯一索引改为 `uk(username, deleted)`。
     - 收获：**"数据库的约束是全局的，业务上的'删除'在存储层并没有消失。"**
  4. **最大收获模板**（收尾，体现工程思维）：
     > "最大的收获不是学会了某个技术，而是明白了**先设计后编码**的价值。比如金额单位、逻辑删除方案、是否预留 `merchant_id` 这些决定，一旦定错，后面改的成本是设计时多花两小时的几十倍。另外我也理解了**性能优化不是加缓存**，而是分层过滤 + 削峰 + 兜底；以及**一致性最终靠对账**，任何补偿逻辑都必须幂等。"
- **常见错误回答**：
  - 「最难的是配置环境/装数据库」——那是困难不是难点，会显得没有技术深度。
  - 「最难的是代码量太大」——同样的意思，没有技术含量。
  - 「没什么难点」——等于说项目没含金量。
  - 讲的"难点"里没有任何**定位过程**（只有结论），听起来像背的。

#### Q3.7.10 你用了消息队列，那你这算微服务吗？为什么不用微服务？

> 这道题是 Q3.7.1 的"前置陷阱版"：面试官不是问架构选型，而是**先设一个概念混淆的坑**，看你分不分得清「中间件」和「架构风格」。

- **面试官想听**：**概念边界**。他用"你用了 MQ，那算微服务吗"来试探你是不是把技术栈当成积木乱堆——答错会直接暴露"跟着教程做项目"的底色。答得清楚，反而能顺势把话题引到你的取舍能力上。
- **参考答案要点**：
  1. **先给结论（一秒都别犹豫）**：**不算。MQ 是中间件，微服务是架构风格，两者维度不同。** 我的项目是**单体应用**，用 RocketMQ 和"是不是微服务"没有关系。
  2. **用一张表把边界说清**（这张表可以直接画在白板上）：

     | | 消息队列（MQ） | 微服务 |
     |---|---|---|
     | 它是什么 | **一个中间件**，提供异步通信能力 | **一种架构风格**，把应用拆成多个独立部署的服务 |
     | 解决什么问题 | 异步解耦、流量削峰、最终一致 | 独立部署、独立扩缩容、团队并行开发 |
     | 单体应用能用吗 | ✅ **能，而且很常见** | ❌ 用不上，微服务的前提就是「多服务」 |
     | 本项目用吗 | ✅ **用**（RocketMQ） | ❌ **不用** |

  3. **说明我在项目里怎么用 MQ**：只有两个场景——① **削峰**，秒杀请求 Redis 预扣成功后丢进 MQ，消费者在**同一个应用进程里**异步落库；② **延迟消息**，订单创建后 30 分钟检查是否仍为待支付，是则关单并回滚库存。**这两件事在单体里做和微服务里做，代码几乎一样**——区别只在微服务里消费者会独立部署。引入 MQ 不等于引入微服务：我只是"一个进程往一个中间件发消息"，和"拆成多个服务互相调用"是两件完全不同的事。
  4. **顺带讲清"为什么不用微服务"**（与 Q3.7.1 呼应）：**单体 + MQ 才是最经典、最容易讲清楚的秒杀方案**——请求进来 → Redis 预扣 → 丢进 MQ → 立即返回 → 消费者在同一个应用里慢慢落库；全程只有一个应用，**不需要服务发现、不需要网关、不需要分布式事务**。我之所以不拆微服务，是因为单人开发、单机部署的场景下，拆分的收益远小于它的运维和调试成本。
  5. **一句话收尾**：**"微服务是一种架构风格，MQ 是一个中间件；我用 MQ 是因为我的场景需要异步和削峰，而不是因为我想上微服务。"**
- **常见错误回答**：
  - 「用了 MQ 应该就算微服务了吧」——**直接把两个维度搞混**；面试官会顺着问"那你的服务注册发现和网关呢"，场面会很难看。
  - 「单体应用不能用 MQ，得先把服务拆开」——事实正好相反，**单体 + MQ 是最常见也最好讲的组合**。
  - 「我本来想上微服务，但时间不够」——把架构决策说成妥协，显得没有判断力；正确说法是"评估过，收益小于成本，所以不引入"。

## 4. 面试官视角：这个项目最容易被抓住的 10 个漏洞

> 这一章是"防守"。下面 10 个点是面试官（尤其是有电商经验的中高级工程师）在你讲完项目后**最可能开火的地方**。
> 每一条都给出：「面试官为什么盯这里」→「诚实且加分的答法」→「❌ 绝对不要说的话」。
> **总原则：不要吹牛。不会的就说不了解，但要说清你知道的边界。** 面试官不指望应届生什么都懂，他怕的是"不懂还硬编"——因为你一旦编，他会顺着往下挖，最后你会自己打自己脸，那才是真正的失分。
> **支付模块的红线**：**不得在简历上写「对接了支付宝 / 微信支付」（也不要写「接入支付宝沙箱 SDK」），只能写「自建模拟支付网关，实现异步回调、验签与幂等」。** 面试时主动说明「没有对接真实渠道（真实渠道需要商户资质），但把真实渠道的异步回调、验签、幂等、重推行为完整模拟了」。**主动说清边界是加分，假装对接了真实支付是致命的——它会让你简历上所有其他数据一起失去可信度。**

#### 🔴 漏洞 1：压测数据不可信 / 环境说不清

- **为什么盯这里**：单机项目却报出"万级 QPS"，是最常见的翻车点。面试官只要问"几台机器、什么配置、瓶颈在哪"就能验证。
- **诚实且加分的答法**：
  > "我的压测是**单机自测**：压测机和服务在同一台【__】C【__】G 的机器上，MySQL 和 Redis 也在同一台，所以这个数据是**偏保守**的，因为压测机自身也在抢 CPU。我主要用它做**同环境下的横向对比**——优化前 QPS【__】，加 Redis 预扣后【__】，加 MQ 削峰后 TP99 从【__】降到【__】。**绝对值没有太大的参考意义，我更看重的是每一轮的变化趋势和正确性验证**：压测后库存 + 订单数 = 初始库存，没有超卖也没有少卖。"
- **❌ 不要说**：「我测出来 QPS 十万」；「生产环境也是这个性能」；「压测报告我找不到了」。

#### 🔴 漏洞 2：只说"用 Redis 保证不超卖"，没有 DB 兜底

- **为什么盯这里**：面试官会立刻想到"Redis 丢数据怎么办""主从切换怎么办"。只靠 Redis = 只做了一层。
- **诚实且加分的答法**：
  > "Redis 只是**第一层过滤**，不是唯一防线。真正的权威数据在 MySQL：`UPDATE wms_stock SET stock = stock - 1 WHERE sku_id = ? AND stock >= 1` 判断影响行数。即使 Redis 完全丢数据，DB 这道条件更新也不会超卖，最坏情况是**性能退化**而不是**数据错误**。第三层是 `sms_seckill_record` 的唯一索引防重。**我把 Redis 定位成"额度"而不是"账本"。**"
- **❌ 不要说**：「Redis 单线程不会出问题」；「Redis 有持久化所以不会丢」；「我上了集群就万无一失」。

#### 🔴 漏洞 3：用分布式锁去保护秒杀库存

- **为什么盯这里**：这是"设计方向性错误"。给每个 SKU 加锁会把并发串行化，QPS 直接掉到个位数。
- **诚实且加分的答法**：
  > "秒杀主链路上我**没有用分布式锁**。原因是库存扣减本身可以用原子操作解决——Redis 用 Lua 保证'判断+扣减'原子、MySQL 用条件更新保证并发安全，**加锁等于把"本身能并发的操作"人为串行化**，还会引入锁等待、续期、误删等一堆边界问题。我的 Redisson 锁用在别的地方：优惠券领取、定时任务选主、后台批量操作。**能用原子操作解决的，我不上锁。**"
- **❌ 不要说**：「我加了 Redis 分布式锁所以不会超卖」——这会把面试官引到"那你 QPS 多少"的死路上。

#### 🔴 漏洞 4：宣称消息"绝对不丢/不重复"

- **为什么盯这里**：这是典型的话说太满。任何 MQ 都只能做到 **at-least-once**。
- **诚实且加分的答法**：
  > "我不会说绝对不丢也不会说绝对不重复。**RocketMQ 的语义是至少一次投递**，所以我的设计目标是'丢不丢都不出错'：不丢靠本地消息表 + Broker 同步刷盘/同步复制 + 消费成功才 ack + 死信队列告警；不重复靠**消费端幂等**——唯一索引兜底、状态机 CAS。**换句话说，我用"幂等 + 对账"把"可能重复"这个事实消化掉了，而不是假装它不存在。**"
- **❌ 不要说**：「RocketMQ 保证不丢不重」；「我用了事务消息所以一定不丢」。

#### 🔴 漏洞 5：本地消息表只说不做（没有重试和对账）

- **为什么盯这里**：本地消息表的关键在**重试策略、上限、告警、对账**，只说"我写了个本地消息表"经不起追问。
- **诚实且加分的答法**：
  > "`sys_message` 的字段是：`biz_type`、`biz_no`、`payload`、`status`（待发送/已发送/失败）、`retry_count`、`next_retry_time`。定时任务每 30 秒扫一批 `status = 待发送 AND next_retry_time <= now()` 的记录，按 **10s → 30s → 1m → 5m → 30m** 指数退避，失败 5 次置为"失败"并**告警**（日志 ERROR + 我留了后台人工重投接口）。另外有一个**每日对账任务**，比对 Redis 库存、`wms_stock`、`sms_seckill_record` 和订单数。**说实话，人工对账这块我只做到了"能查出差异"，没有做完整的运营后台。**"
- **❌ 不要说**：「我有本地消息表所以不会不一致」——被问"重试几次、间隔多少、失败了呢"就答不上来。

#### 🔴 漏洞 6：项目没跑起来 / 给不出代码

- **为什么盯这里**：这是**一票否决**项。没有 GitHub、不能演示，"我做过"就是空话。
- **诚实且加分的答法**：
  > "代码在 GitHub：`github.com/【用户名】/shopping-mall`，README 里有架构图、ER 图、启动方式和压测报告。你可以 `docker compose up -d` 把 MySQL/Redis/RocketMQ 起来，然后跑 `shopping-web` 的启动类就能访问 Knife4j 文档 `http://localhost:8080/doc.html`。我也可以现在给你演示一遍秒杀。"
  - **如果项目确实还没做完**：**如实说进度**。"目前 Phase 1 到 Phase 3 的核心链路完成了，多商户的 Phase 4 只做了表设计，没做接口。"——**这比"我做完了"然后被问崩要好一万倍**，因为 `00` 号文档本来就定义了 Phase 划分，讲进度本身就是加分。
- **❌ 不要说**：「代码在公司/在另一个电脑上」；「等项目完善了再给你看」；给不存在的仓库链接（面试官真的会点开）。

#### 🔴 漏洞 7：表结构和索引说不清

- **为什么盯这里**：电商项目表和索引是基本功，`wms_stock` 的索引、`oms_order` 的查询条件说不清，说明你不是作者。
- **诚实且加分的答法**：把下面这几个背下来，随时能画出来：
  - `wms_stock`：`uk(sku_id)`，字段 `stock`、`locked_stock`、`version`、`update_time`；扣减 SQL 只走 `sku_id` 等值。
  - `sms_seckill_record`：`uk(user_id, activity_id, sku_id)` + `idx_activity_id`；唯一索引是防重核心。
  - `oms_order`：`uk(order_no)`、`idx_user_id_create_time`（我的订单列表按用户 + 时间倒序）、`idx_status_create_time`（后台按状态筛选）；**深分页用游标 `id < last_id`**。
  - `sms_seckill_activity` / `sms_seckill_sku`：活动时间用 `start_time`/`end_time`，**加 `merchant_id` 预留多商户**。
  - 金额字段：`pay_amount bigint`，注释"单位：分"。
  - 通用：`id`（雪花）、`create_time`、`update_time`、`deleted`。
  - **不会的就说**："这张表的索引我是按查询条件建的，`idx_status_create_time` 用的是最左前缀，另外我在 `EXPLAIN` 里验证过 type 是 `range`。"
- **❌ 不要说**：含糊地说"索引都加了""该加的都加了"；或者把 `uk` 和 `idx` 说混。

#### 🔴 漏洞 8：量级对不上（"百万并发" vs 单机 MySQL）

- **为什么盯这里**：对有经验的面试官来说，量级不匹配=吹牛。单机 MySQL 写 TPS 通常在几千量级。
- **诚实且加分的答法**：
  > "我不会说我扛住了百万并发——**单机 MySQL 的写入极限就在几千 TPS 量级**，这是物理上限。我的设计思路是**让百万请求不必都到达数据库**：Nginx 限流、应用本地缓存、Redis 令牌桶、Redis Lua 预扣，每一层过滤掉一大截，最后只有库存数量级的写请求进 MySQL，再通过 MQ 把它们摊平。**我压测验证的是"漏斗是否有效、数据是否正确"，而不是"单机能扛百万"。**"
- **❌ 不要说**：「我系统支持百万 QPS」；「用了 Redis 就能扛百万」。

#### 🔴 漏洞 9：只讲技术，不讲业务价值和取舍

- **为什么盯这里**：面试官要判断你是"完成任务的人"还是"思考的人"。
- **诚实且加分的答法**：每讲一个技术点，**补一句"为什么"和"代价"**：
  - "我用 RocketMQ 延迟消息而不是定时任务扫表，**省掉了空扫，但代价是延迟有秒级误差，而且引入了 MQ 依赖**。"
  - "我金额用 bigint 存分，**避免了浮点误差，代价是展示层要统一转换**。"
  - "我不上微服务，**因为我的数据量和团队规模撑不起它的复杂度**。"
  - **"我选 A 不是因为 A 更高级，是因为在当前约束下它的总成本最低。"**
- **❌ 不要说**：只念技术名词清单；被问"为什么"时回答"因为主流/教程都这么用"。

#### 🔴 漏洞 10：代码不是自己写的（说不出细节）

- **为什么盯这里**：面试官会问"你的 `SeckillService` 大概多少行""拦截器注册在哪个类里""Lua 脚本文件名是什么"这类**只有作者才知道的问题**。
- **诚实且加分的答法**：
  - 面试前**必须重新过一遍自己的代码**（见第 8 章 checklist）：包结构、核心类名、关键方法、Lua 脚本、配置文件、启动命令。
  - 如果真的参考了开源项目/教程：**大方承认，并说清你改了什么**。
    > "秒杀的表结构我参考了【某开源项目】的思路，但我的实现和它不一样：它用的是 MQ 事务消息 + DB 乐观锁，我用的是 Redis Lua 预扣 + 本地消息表，因为我更想控制重试节奏，也更容易讲清楚每一步的失败处理。另外它的库存回滚没有幂等，我这里加了流水号唯一约束。"
    **"参考并改进"是加分的，"抄了说原创"是致命的。**
- **❌ 不要说**：随口编类名；被问到具体代码时反复说"记不清了"。

### 4.1 三条通用保命话术（背下来）

**话术 1：完全不会的问题**
> "这个我确实没有深入研究过，不敢乱说。**我只能从我的理解猜一下方向**：大概是【说出你唯一知道的那一句】。如果让我做，我会先去查【官方文档/具体资料】，再结合项目的实际数据量决定要不要引入。**这块是我的知识盲区，我回去会补。**"
- 要点：**承认 → 给出边界 → 表达学习路径**。不要说"这个我们没用过"然后沉默。

**话术 2：会一半的问题**
> "我了解它的**原理层面**，但**没在生产环境实操过**。原理上是【正确答案】，我项目里用的是【你的方案】，选它的原因是【取舍】。**如果要用它，我担心的点是【某个真实的技术风险】。**"
- 要点：**主动划出"我会到哪、不会到哪"的边界**，面试官会认为你诚实且清楚自己的水平。

**话术 3：被质疑设计不合理**
> "你指出的这个问题确实存在。**当时的考虑是【你的理由】，现在的代价是【对方的顾虑】**。如果按你说的改，我会这么处理：【给出具体方案，并说明新引入的成本】。**你更倾向于哪种取舍？**"
- 要点：**不硬顶、不谄媚**。承认问题 → 给出当时的取舍 → 给出改进方案 → 把球传回去。这是成熟的工程师对话方式。

## 5. 项目演示准备

> 目标：**在任何环境下，5 分钟内让面试官看到"这个系统真的能跑、数据真的对得上、这个人真的理解自己的代码"。**

### 5.1 演示脚本（推荐顺序）

**核心原则：先讲清楚"业务闭环"，再展示"高并发亮点"。** 因为闭环证明项目完整、你能独立完成复杂系统；亮点证明你有深度。**只演示秒杀不演示下单闭环，会让人觉得你只抄了一个秒杀 demo。**

| 步骤 | 时长 | 演示内容 | 你要说的话（关键句） |
|---|---|---|---|
| 0. 环境就绪 | — | 提前起好：MySQL / Redis / RocketMQ / 应用 / 前端 | "我已经把依赖起好了，避免占用你的时间。" |
| 1. 架构开场 | 40s | 打开 README 里的**架构图 + 模块依赖图** | "五个模块，依赖严格单向；C 端和管理端接口前缀分开。" |
| 2. 数据库 | 40s | 打开 ER 图 + 几张核心表 | "65 张表，金额统一 bigint 存分；这六张表预留了 `merchant_id`。" |
| 3. **交易闭环（重点）** | 2min | 后台建商品 → **切到手机模式（F12 → iPhone）打开商城前台**：商品列表 → 详情选规格 → 加购 → 下单结算 → 模拟支付网关 → 订单状态变化 → 查看库存流水 | "注意这里下单后库存减了，`wms_stock_log` 多了一条扣减流水，订单状态从待支付变成已支付。" |
| 3b. **商城前台（手机版动线）** | 1min（时间紧时用截图讲，30s） | 单独把 C 端 4 页再走一遍：商品列表（分页/类目）→ 商品详情（规格选择）→ 购物车（改数量/勾选/合计）→ 下单结算页 | "C 端我只做了这 4 个页面，是刻意取舍——演示动线只需要这 4 页就能走完一次完整购物，其余页面对求职没有增量价值。" |
| 4. **超时关单** | 40s | 下一个不支付的订单，**把延迟等级临时调成 5s**（或直接用配置的短延迟演示） | "正常是 30 分钟，我为了方便演示改成了 5 秒——用的是 RocketMQ 延迟消息，不是定时扫表。" |
| 5. **秒杀（亮点）** | 1min30s | 打开秒杀页面 → 抢购 → 展示"一人一单"再点一次被拒 → 展示 `sms_seckill_record` | "再点一次会被 Lua 里的 `SISMEMBER` 拦掉，DB 层还有唯一索引兜底。" |
| 6. **压测数据** | 1min | 展示**压测对比表格 + 聚合报告截图 + 对账 SQL 结果** | "三轮压测只改一个变量，最后一轮的库存 + 订单数是完全对得上的。" |
| 7. 接口文档 | 30s | 打开 Knife4j `http://localhost:8080/doc.html` | "所有接口都在线文档里，可以直接调。" |

**顺序建议（回答"先秒杀还是先下单闭环"）：先下单闭环，后秒杀。** 理由：

- 闭环体现了**业务完整度**和你的耐力（65 张表、11 个模块是加分项）；秒杀只体现单点深度。
- 如果时间不够被中途打断，闭环已经讲完了，秒杀是"锦上添花"；反过来则可能只讲了一个 demo。
- 秒杀环节更容易出意外（缓存没预热、活动时间已过），放在后面，万一失败也有前面的内容托底。

**如果面试官明确说"只想看秒杀"**：那就跳过闭环，直接 5 → 6 → 7，但**口头补一句**"下单闭环我也做了，包括支付和售后，需要的话可以回来看"。别真的把闭环从项目里抹掉。

### 6.3 要不要部署到云上？成本与推荐方案

**结论：如果时间允许，强烈建议部署。** 因为"能在公网访问"能带来三个好处：① 简历上可以写在线地址（**面试官真的会点**）；② 远程面试时不用本地起服务，稳定性更高；③ 部署过程本身（Docker Compose、Nginx、安全组、日志排查）就是可以讲的工程经验。

**但不要因为部署而耽误主线**：部署是"锦上添花"，秒杀做扎实才是主线。**如果只有 1 天时间，选择录屏 + 本地演示，而不是折腾部署。**

#### 推荐方案（按预算从低到高）

| 方案 | 成本 | 优点 | 缺点 | 适合 |
|---|---|---|---|---|
| **A. 纯本地 + 录屏** | 0 元 | 零成本、零风险、演示最稳 | 面试官不能自己访问 | 时间紧、预算为零 |
| **B. 本地 + 内网穿透**（cpolar / frp / ngrok / 花生壳） | 0~30 元/月 | 成本低、能给出公网地址 | 地址会变、不稳定、免费版有流量/并发限制 | 想让面试官看一眼 Knife4j |
| **C. 云服务器 + Docker Compose（推荐）** | **学生认证后 2C2G 约 10 元/月（年付 100 元左右）；轻量应用服务器 2C4G 约 24~60 元/月** | 稳定、可写进简历、能讲部署经验 | 需要配置安全组、注意备案 | 大多数人选这个 |
| **D. 拆分部署：后端上云 + 前端 Vercel/Cloudflare Pages** | C 的成本 + 0 | 前端访问快、免费 | 需要处理跨域与域名 | 有 C 端页面时 |
| **E. 不用云服务器，只用 Serverless/托管数据库** | 按量，可能 0 元 | 无需运维 | RocketMQ 基本没有合适的托管免费额度；改造量大 | 不推荐 |

**成本估算（C 方案，能跑全套依赖）**：

- **CPU/内存是硬约束**：项目要同时跑 MySQL + Redis + RocketMQ + 应用 + Nginx。
  - **1C2G**：**不够**（RocketMQ 的 Broker 默认 JVM `-Xms8g -Xmx8g`，一启动就 OOM）。
  - **2C2G**：勉强，但**必须改 RocketMQ 的 JVM 参数**（`-Xms512m -Xmx512m -XX:MaxDirectMemorySize=256m`）+ 限制 MySQL `innodb_buffer_pool_size=256M` + 应用 `-Xmx512m`；压测就免了，只能演示功能。
  - **2C4G（推荐）**：能稳定跑全套 + 轻量演示；MySQL 512M、RocketMQ 1G、应用 1G、Redis 256M。
  - **4C8G**：能跑压测（但仍不建议在云上公开压测，容易被云厂商限速/封禁）。
- **磁盘**：40~60G 系统盘足够（MySQL 数据 + 镜像 + 日志）；注意 **Docker 镜像很占空间**（MySQL + Redis + RocketMQ 镜像加起来 1.5G+）。
- **带宽**：**1~5Mbps 足够演示**（Knife4j 页面和接口都是小报文）；不要买高带宽，贵且没用。
- **备案**：**国内服务器的 80/443 端口需要域名备案**（耗时 1~2 周，且需要企业/个人资质）。**三个绕开办法**：① 用非 80 端口（如 `8080`，但部分云厂商要求端口备案）；② 用香港/新加坡等境外节点（**免备案，但延迟高、价格略贵**）；③ 只给 IP，不给域名（面试时给 `http://【IP】:8080/doc.html` 也完全能接受）。
- **HTTPS**：如果买了域名，用 Nginx + Let's Encrypt（certbot）免费证书，5 分钟搞定；`00` 号文档的部署选型就是 **Docker Compose + Nginx**，不要上 K8s。

**部署时的 8 个必做项**：

1. **改密码**：MySQL、Redis 必须设密码；Redis **不要暴露公网**（`bind` 到内网或只允许 Docker 网络访问）——**未授权的 Redis 是黑客最爱，会被挖矿**。
2. **安全组只开必要端口**：`22`（限制来源 IP）、`8080`（或 `80/443`）；**MySQL 3306、Redis 6379、RocketMQ 9876/10911 一律不开公网**。
3. **JVM 参数按内存调小**：`java -Xms512m -Xmx512m -jar shopping-web.jar`。
4. **生产环境关闭 Knife4j 的公开访问**或加简单鉴权：`springdoc.api-docs.enabled=false`（**面试演示时可以临时打开**，但要在 README 里说明"演示环境"）。
5. **日志与数据持久化到宿主机 volume**（`docker-compose.yml` 里配 `volumes`），否则重启容器数据全丢。
6. **`restart: always`**（或 `unless-stopped`），机器重启后服务自动起来。
7. **准备一个"演示数据重置脚本"**，避免面试官访问时活动已过期/库存已售罄。
8. **别把真实密码提交到 GitHub**：用 `.env` 文件 + `docker-compose` 的变量替换，`.env` 加入 `.gitignore`。

**面试话术（被问到部署）**：
> "我用 Docker Compose 把 MySQL、Redis、RocketMQ、应用和 Nginx 编排在一起，一行命令拉起全套依赖。云上部署时我把 MySQL/Redis 都设了密码、只对内网开放，安全组只放开了应用端口；因为 RocketMQ 默认 JVM 是 8G，我在 2C4G 的机器上把它调成了 512M，MySQL 的 buffer pool 也限制到 512M。**我也知道了本地配置和生产配置是两回事**——比如生产应该用 2 主 2 从 + DLedger，而我本地只起了单 Master。"

### 6.4 接口文档怎么展示（Knife4j）

**Knife4j 4.x 基于 springdoc（Jakarta），访问地址是 `/doc.html`**：

- 本地：`http://localhost:8080/doc.html`
- 线上：`http://【你的IP或域名】:8080/doc.html`
- OpenAPI JSON：`http://localhost:8080/v3/api-docs`（springdoc 的默认路径，Knife4j 基于它渲染）

**要点**：

1. **简历和 README 里一定要写这个地址**——它是最直观的"我做过"的证据。**写之前先自己点一遍确认能打开**。
2. **接口分组**：用 `@Tag(name = "秒杀")`、`@Tag(name = "订单")` 给 Controller 分组；用 `springdoc.group-configs` 按路径分组（`/api/app/**` 和 `/api/admin/**`）。
3. **加鉴权头配置**：在 `Knife4jConfig` 里配置 `SecurityScheme`（Bearer JWT），这样在文档页面上能直接填 token 调接口——**演示时非常方便，面试官会觉得你很专业**。
4. **关键接口要写示例**：`@Operation(summary = "秒杀下单")`、`@Schema(description = "秒杀活动ID")`；秒杀接口的响应示例要能看出"排队中/已抢到/已参与过"的区分。
5. **生产环境的安全处理**（必须知道）：`application-prod.yml` 里配
   ```yaml
   springdoc:
     api-docs:
       enabled: false
     swagger-ui:
       enabled: false
   ```
   或者用 Nginx 对 `/doc.html`、`/v3/api-docs` 加 Basic Auth（面试演示环境可以留着，但要能说清"生产要关掉或加鉴权"）。
6. **备一份离线文档**：把 `/v3/api-docs` 的 JSON 导出，或者用 Postman 集合导出成 `docs/api.md` / `docs/shopping-mall.postman_collection.json` 提交到仓库。**面试官不一定能访问你的服务器，但一定能打开 GitHub。**

### 7.4 如何针对 JD 做微调（关键词对齐）

**原则：只调整"顺序和措辞"，绝不更改事实。** 不要把没做过的写上去。

**做法**：把 JD 里的技术关键词提取出来，把项目描述里**对应的那句提到最前面**，并把措辞对齐 JD。

| JD 里高频出现 | 你该怎么调整项目描述 |
|---|---|
| **高并发 / 性能优化 / QPS** | 把**秒杀那条放第一条**，QPS/TP99 数据写在最前面 |
| **消息队列 / RocketMQ / Kafka** | 把 **MQ 削峰 + 延迟消息关单 + 本地消息表**那条提前，明确写"RocketMQ 延迟消息（ADR-5）" |
| **Redis / 缓存** | 提前 **Redis + Lua 预扣、缓存穿透/击穿/雪崩、Redisson 看门狗**那条 |
| **MySQL / 索引优化 / SQL 调优** | 提前"65 张表设计 + 索引优化 + 深分页改写 + 慢 SQL 排查"那条，并补上 `EXPLAIN` 的字眼 |
| **分布式 / 一致性 / 事务** | 提前 **本地消息表 + 最终一致 + 幂等**那条，写清"替代 Seata 的方案" |
| **Spring / Spring Boot 原理** | 技能栏把 Spring 相关提到第一行，项目里补一句"通过 AOP + 自定义注解实现横切逻辑复用" |
| **微服务 / Spring Cloud / Nacos** | **不要假装用过！** 写明"单体多模块 + 预留演进路径"，面试时主动讲"如果拆微服务我会怎么拆"（见 Q3.7.1）——**校招面试官更看重取舍能力** |
| **Docker / K8s / CI-CD** | 提前"Docker Compose 编排 + Nginx"那条；**K8s 没做过就不要写** |
| **单元测试 / 工程规范** | 补上"JUnit 5 + Mockito + Testcontainers"那条（**前提是你真的写了测试**） |
| **算法 / 数据结构** | 与项目无关，去刷题 |

**微调示例（同一句话的三种写法）**：

- 投"高并发"岗：**「秒杀模块基于 Redis + Lua 原子预扣 + MySQL 条件更新三层防超卖，JMeter 压测 1000 并发下 QPS 从【__】提升到【__】、0 超卖」**
- 投"消息队列"岗：**「用 RocketMQ 延迟消息实现 30 分钟超时关单（替代定时任务扫表），用本地消息表 + 消费端幂等保证 Redis 预扣与 DB 扣减的最终一致」**
- 投"数据库/中间件"岗：**「独立设计 65 张表（金额 bigint 存分、雪花 ID、逻辑删除），通过 EXPLAIN 定位慢 SQL，把订单列表深分页从 limit 万级 offset 改写为游标分页，扫描行数从【__】降至【__】」**

**重要提醒**：微调后**必须自己再读一遍**，确认每一句你都能在面试里展开讲 2 分钟。**改动过的句子 = 新的面试考点。**
